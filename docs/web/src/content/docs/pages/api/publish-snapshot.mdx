---
title: Publish snapshot
api: "PUT /{bucket}/{stream}/snapshot/{offset}"
---

Publishes a new checkpoint blob at the given offset. The snapshot replaces any previously published snapshot, but does not delete stream history. Retention advances only through the separate `/retention` endpoint.

<ParamField path="bucket" type="string" required>
 Bucket ID.
</ParamField>

<ParamField path="stream" type="string" required>
 Stream ID.
</ParamField>

<ParamField path="offset" type="string" required>
 Stream offset this snapshot represents: the 20-character zero-padded decimal token.
</ParamField>

For an `application/json` stream the offset must be a message boundary: a `Stream-Next-Offset` that Ursula returned, or any offset just after a message's LF.

<ParamField header="Content-Type" type="string">
 Content type of the snapshot blob, stored separately from the stream's own content type. Defaults to `application/octet-stream`.
</ParamField>

<ParamField body="body" type="binary" required>
 The snapshot blob bytes, at most `Ursula-Max-Request-Bytes` (**32 MiB** from a node). Bodies are stored inline in the stream's replicated state. On a node with a cold backend, a body of at least `runtime.external_payload_min_size` (1 MiB by default) is streamed into the cold tier instead. A larger snapshot goes up [in parts](#upload-in-parts).
</ParamField>

<ParamField header="Stream-Incarnation" type="string">
 Optional precondition: the stream's incarnation token, as a previous response's `Stream-Incarnation` header returned it. The request applies only if the stream is still that incarnation, checked atomically with the write; otherwise it answers `412` and changes nothing. Without the header, the request behaves exactly as described here. A malformed value answers `400`. See [`Stream-Incarnation`](/docs/specs/extensions#24-snapshot-metadata-on-head-and-stream-incarnation).
</ParamField>

## Response

| Status | Meaning |
| ------ | --------------------------------------------------------------- |
| `204` | Snapshot published successfully. |
| `400` | Invalid offset or content type, or, on a JSON stream, an offset inside a message. |
| `404` | Stream not found or expired. |
| `409` | Another snapshot is the latest: a newer one (this publish is superseded) or a different one at the same offset. The response names it in `Stream-Snapshot-Offset` and `Stream-Snapshot-Digest`. A `409` without them means the offset is beyond the stream's tail. |
| `410` | Snapshot offset is older than the retained stream history. |
| `412` | `Stream-Incarnation` did not match: the stream was deleted and recreated. Nothing was published; the response's `Stream-Incarnation` is the current token. |
| `413` | The body is above `Ursula-Max-Request-Bytes`, which the response names. For a commit of parts, the assembled snapshot is above `Ursula-Max-Snapshot-Bytes`, which the response names instead. |
| `501` | A commit of parts on a node without a cold backend. |
| `502` | The cold backend failed while storing the body or copying the parts. |
| `503` | Retry after `Retry-After`. Nothing was published. The error body names the cause: `SNAPSHOT_COMMITS_BUSY` (every copy slot taken, or no room in the in-flight budget beside a request), `SNAPSHOT_COMMIT_IN_PROGRESS` (this commit runs now), `INGRESS_BODY_BYTES_LIMIT_REACHED`, `WAL_DISK_PRESSURE`, `RAFT_LOG_PRESSURE`, `NO_LEADER` (no leader is known), or `JSON_BOUNDARY_UNVERIFIED` (on a JSON stream, Ursula could not read the byte before the offset to check the boundary). |

Every error answer carries a JSON body with its code and a human-readable message, such as `{"error":{"code":"SNAPSHOT_CONFLICT","message":"..."}}`. See [errors](/docs/api/overview#errors).

A `204` carries `Stream-Snapshot-Offset`, `Stream-Snapshot-Digest`, and `Stream-Incarnation`. A publish is keyed by its offset and digest. Repeating the same offset, content type, and body returns the same digest while that snapshot is the latest. Reusing an offset with different content returns `409`.

<RequestExample>
```bash Example
curl -X PUT 'http://127.0.0.1:4437/demo/hello/snapshot/00000000000000000042' \
  -H 'Content-Type: application/json' \
  --data-binary '{"state": "aggregated snapshot data"}'
```
</RequestExample>

## Upload in parts

On a node with a cold backend, a snapshot above `Ursula-Max-Request-Bytes` goes up in parts, up to `Ursula-Max-Snapshot-Bytes` (**1 GiB**) in at most 4,096 parts. `HEAD` advertises both limits.

1. Stage each part with `POST /{bucket}/{stream}/snapshot/{offset}/parts`. Its body is the part's bytes, at most `Ursula-Max-Request-Bytes`. The answer is `201` with the part's id in `Stream-Snapshot-Part`. Staging changes nothing a reader sees, and repeating it stages another part. The stream must exist (`404` otherwise), and the request may carry `Stream-Incarnation`. A part belongs to the stream's current incarnation, not to the offset in its path, which is checked and otherwise ignored. A part is charged against the node's in-flight body budget but is not refused for WAL or Raft-log pressure. A stream holds at most 8,192 staged parts that no commit used, and at most 2 GiB of them (see [staged parts](#staged-parts)).
2. Commit with `PUT /{bucket}/{stream}/snapshot/{offset}`, `Stream-Snapshot-Parts: <count>` and `Stream-Snapshot-Digest: <digest of the whole snapshot>`. The body lists the part ids in order, each followed by a line feed, no id twice. `Content-Type` is the snapshot's.

A commit checks its key first, before it reads its body. A repeat of a published snapshot answers `204` with its digest, and a commit whose offset holds another snapshot, or that a later snapshot supersedes, answers `409` naming the latest, both even after the parts are gone. Otherwise Ursula copies the parts into one snapshot, checks its digest, and publishes it like any other snapshot, with the same answers. It answers `400` when a part is unknown, belongs to another stream or to an earlier incarnation of this one, or is listed twice, when the manifest does not match `Stream-Snapshot-Parts`, or when the digest differs.

Whether Ursula deletes the parts depends on the answer:

- After the publish's answer, when it is final for the commit's key (`204`, `400`, `404`, `409`, `410` or `412`), the parts are deleted, after the answer has gone out.
- After a `400` for a digest that differs, the parts are deleted too: the copy that found the mismatch used them up. Upload them again.
- After a `400` that copies nothing (an unknown part, another stream's part, a part listed twice, a malformed or oversized manifest), the parts stay, so a corrected commit can use them.
- After a `503` or any other retryable answer, the parts stay. Repeat the same commit.

The orphan sweep reclaims a part that no commit used once it is older than its grace, a day by default, whether its stream still exists or not, so commit within a day of staging the first part. Without a cold backend, parts, commits and discards answer `501`.

### Staged parts

A stream holds at most 8,192 staged parts that no commit used, and at most 2 GiB of them. That is twice what one commit can use, so an abandoned upload and a full retry both fit. The parts of the stream's earlier incarnations count until they are deleted, so deleting and recreating a stream does not reset the bound. A part past either bound answers `429 Too Many Requests` before its body is read, with the error code `STAGED_PARTS_LIMIT`, the stream's `Stream-Incarnation` and the bound it hit: `Ursula-Max-Staged-Parts: 8192` or `Ursula-Max-Staged-Bytes: 2147483648`. The answer has no `Retry-After`, because a short wait does not free anything. A commit frees its parts once it has deleted them, a discard frees them at once, and the orphan sweep frees the parts it reclaims after its grace. Commit or discard the parts you staged before you stage another snapshot. A part counts its `Content-Length` while it uploads, and 32 MiB when it has none, so send `Content-Length` near the byte bound.

Discard a stream's staged parts with `DELETE /{bucket}/{stream}/snapshot/parts`. It deletes every staged part of the stream's current incarnation, and the parts of its earlier incarnations staged more than a minute before it, and answers `204` with `Stream-Incarnation`. It may carry `Stream-Incarnation` (`412` when it does not match), answers `404` for a stream that does not exist, `501` without a cold backend and `502` with `COLD_STORE_FAILED` when the cold backend fails to list or delete the parts, and is answered by the stream's leader like a write. A part whose upload ends during a discard may or may not survive it. While a commit of the stream runs, a discard answers `503` with `Retry-After` and the error code `SNAPSHOT_COMMIT_IN_PROGRESS`. Through `ursulagw` a discard is authorized as a snapshot publish.

Deleting a stream deletes its staged parts after the delete has answered, in a task the node owns: the parts of the incarnations the stream's leader knew of at any age, and the stream's other parts staged more than a minute before the delete. A recreated stream's next listing deletes the parts of its earlier incarnations staged more than a minute before it. These margins assume the nodes' clocks agree within a minute. When the delete of a commit's spent parts fails, they stay until a discard, a delete of the stream or the orphan sweep removes them.

The stream's leader keeps the count in memory. It lists the stream's parts at the stream's first part after it starts to lead or after the orphan sweep reclaimed some of them, after every commit and discard, and at a refused part when its last listing is over a minute old. A new leader does not see the parts that were still uploading to the old one when it took over, so the stream can hold more than the bound by those parts until a commit, a discard, a delete or the sweep removes them.

| Status | Meaning (part upload) |
| ------ | --------------------- |
| `201` | The part is staged. `Stream-Snapshot-Part` is its id. |
| `404` | Stream not found or expired. |
| `412` | `Stream-Incarnation` did not match. |
| `413` | The part is above `Ursula-Max-Request-Bytes`, which the response names. |
| `429` | The stream holds as many staged parts, or bytes of them, as it may. The response names the bound and the stream's `Stream-Incarnation`. |
| `501` | The node has no cold backend. |
| `502` | The cold backend failed while storing the part or listing the stream's parts. |

A stream deleted and created again while its commit copies is not published to. A commit that sent `Stream-Incarnation` then answers `412`. One that did not answers `400` for an unknown part, as a commit sent after the new create does.

A node copies at most two commits at once, and starts a copy only while a request of the full 32 MiB limit still fits in `server.http_inflight_body_size` beside it. Another commit answers `503` with `Retry-After` and the error code `SNAPSHOT_COMMITS_BUSY`. A copy is charged against the budget while it runs: 56 MiB at the default 256 MiB, 32 MiB on a node of 64 MiB, which reads fewer pieces ahead and so copies one commit at a time.

<Note>
The node owns a commit once it starts copying. A client that goes away, or a gateway that times out, cancels none of it: the copy, the publish and the deletion of the parts run to their end. A repeat while the commit runs, and any other commit of the same stream incarnation, answers `503` with `Retry-After` and the error code `SNAPSHOT_COMMIT_IN_PROGRESS`, and a repeat after it answers `204` from the key. A copy takes time in proportion to the snapshot's size and the number of parts. On S3, 256 MiB in eight 32 MiB parts took about 3 seconds. Through `ursulagw`, whose `--response-header-timeout` is 30 seconds by default, a commit of many small parts can outlast the timeout. Repeat it until it answers, or send larger parts.
</Note>

```bash Example
curl -X POST 'http://127.0.0.1:4437/demo/hello/snapshot/00000000000000000042/parts' \
  --data-binary @part-1.bin
# 201, Stream-Snapshot-Part: 0000000000000000186f2b3a1c0d9e00-0000000000000007.part
printf '%s\n%s\n' "$PART_1" "$PART_2" | curl -X PUT \
  'http://127.0.0.1:4437/demo/hello/snapshot/00000000000000000042' \
  -H 'Content-Type: application/octet-stream' \
  -H 'Stream-Snapshot-Parts: 2' \
  -H "Stream-Snapshot-Digest: $DIGEST" \
  --data-binary @-
```

## Advance retention

`PUT /{bucket}/{stream}/retention/{offset}` explicitly discards history before a published checkpoint. The boundary must be no newer than the visible checkpoint and, on a JSON stream, a message boundary (`400` otherwise, `503` when it cannot be checked). Retention only moves forward: a boundary at or below the current one succeeds, changes nothing and reports the current boundary, so a repeated request is safe. Otherwise retention is exact: the response's `Stream-Retained-Offset` is the requested offset.

After a successful `204`, reads before the retained offset return `410 Gone`. This separate step lets clients publish and verify a checkpoint before making history unreachable.

<Note>
Snapshots are immutable at a given offset. A byte-identical retry is idempotent; a different body at the same offset conflicts. Publishing does not advance retention.
</Note>
