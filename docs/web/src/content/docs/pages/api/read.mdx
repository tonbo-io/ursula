---
title: Read stream
api: "GET /{bucket}/{stream}"
---

<ParamField path="bucket" type="string" required>
 Bucket ID.
</ParamField>

<ParamField path="stream" type="string" required>
 Stream ID within the bucket.
</ParamField>

<ParamField query="offset" type="string">
 Starting offset: `-1` for the beginning, `now` for the current tail, or a `Stream-Next-Offset` value from an earlier response.
</ParamField>

<ParamField query="cursor" type="string">
 On a long-poll or SSE read, the `Stream-Cursor` value from the previous live response. It lets caches tell successive live requests apart. It is not a position and never replaces `offset`.
</ParamField>

<ParamField query="consistency" type="string">
 `local` (default) or `leader`, on catch-up reads only. `leader` makes the read linearizable: it includes every append acknowledged before the request, at the cost of one round trip from the group's leader to a majority of voters. Use it to read back your own acknowledged writes. Combining it with `live` answers `400`. See [Read path](/docs/specs/extensions#92-leader-consistency).
</ParamField>

<ParamField query="record" type="string">
 For a JSON stream with Record Coordinates, start at a complete record boundary. Supply a zero-based ordinal or `now` for the current record tail. Mutually exclusive with `offset` and `tail_records`.
</ParamField>

<ParamField query="tail_records" type="number">
 Start at the most recent retained records: `max(first_record, next_record - count)`. Mutually exclusive with `record` and `offset`.
</ParamField>

<ParamField query="max_records" type="number">
 Maximum number of complete records to return. Requires `record` or `tail_records`. May be combined with `max_bytes`; the response stops at whichever limit is reached first.
</ParamField>

<ParamField query="record_view" type="string">
 Set to `envelope` with a record-aware start to return one `{record, value}` object per NDJSON line.
</ParamField>

<ParamField query="live" type="string">
 Live mode: `sse` for Server-Sent Events, `long-poll` for long-polling. Omit for catch-up read.
</ParamField>

<ParamField query="max_bytes" type="number">
 On an offset read, the maximum bytes to read in one response or SSE data batch. Every response is capped at 8 MiB; a larger value is clamped, and a value that is not a decimal integer is ignored. A shortened response has no `Stream-Up-To-Date`; continue from `Stream-Next-Offset`. For UTF-8 SSE data, Ursula may shorten the emitted batch so `Stream-Next-Offset` lands on a valid text boundary.

 With `record` or `tail_records`, a positive integer that bounds complete records instead: the response holds the longest run of whole records whose stored size (each message plus its LF) is at most `max_bytes`, and always at least one record when one exists, even if it alone is larger. It never ends inside a record.
</ParamField>

## Read modes

<Tabs>
 <Tab title="Catch-up">
 No `live` parameter. Returns all available data from the given offset immediately.

    ```bash
    curl 'http://127.0.0.1:4437/demo/hello?offset=-1'
    ```
 </Tab>
 <Tab title="Long-poll">
 `live=long-poll`. Returns immediately if data is available, otherwise holds the connection until new data arrives or `timeout_ms` elapses (default 1000, at most 60000).

    ```bash
    curl 'http://127.0.0.1:4437/demo/hello?offset=00000000000000000042&live=long-poll'
    ```
 </Tab>
 <Tab title="SSE">
 `live=sse`. Opens a persistent Server-Sent Events connection. The server pushes data events as new entries are appended. It sends no heartbeats, so a proxy with an idle timeout may close a quiet connection; reconnect from the last control event's `streamNextOffset`.

    ```bash
    curl 'http://127.0.0.1:4437/demo/hello?offset=-1&live=sse'
    ```
 </Tab>
</Tabs>

## Response

| Status | Meaning |
| ------ | ------------------------------------------------------------- |
| `200` | Data returned. A catch-up read at the tail answers `200` with an empty body and `Stream-Up-To-Date: true`. |
| `204` | Long-poll only: `timeout_ms` passed without new data. |
| `304` | `If-None-Match` matched the response's `ETag`. |
| `307` | In a cluster, this node could not serve the read as the stream's group leader (a long-poll or SSE read on a follower, or a `consistency=leader` read on a node that lost leadership). `Location` is the same request on the leader. |
| `400` | Invalid offset, live mode or `consistency`, or `consistency=leader` with `live`. |
| `404` | Stream not found or expired. |
| `410` | Requested offset has been trimmed. `Stream-Next-Offset` is the earliest offset still readable. |
| `503` | The group has no known leader, the leader could not confirm its leadership in time (`consistency=leader` and live reads), or this node holds too many live readers. Retry after `Retry-After`. |

Response headers include `Stream-Next-Offset`, `ETag`, `Stream-Up-To-Date`, `Stream-Closed`, and `Content-Type`. Long-poll responses for an open stream also carry `Stream-Cursor`.

Record-aware responses also advertise `json-record-coordinates-v1` in `Stream-Extensions` and include `Stream-Record-First`, `Stream-Record-Start`, and `Stream-Record-Next`. Continue with `record=<Stream-Record-Next>`. A record below `Stream-Record-First` returns `410`, and a record beyond the current tail returns `400`.

Releases before record-aware `max_bytes` reject it with `400`.

Streams written with `Content-Type: application/json` are returned as newline-delimited JSON with response `Content-Type: application/x-ndjson`, one stored message per line, exactly as written minus insignificant whitespace ([JSON message text](/docs/specs/extensions#json-message-text)). On an offset read, `max_bytes` applies to the encoded byte stream, so a response can end mid-line. Resume from `Stream-Next-Offset` and buffer any incomplete trailing line before parsing. `HEAD` reports the configured stream content type, while read responses report the wire representation.

## SSE event format

In SSE mode, the server sends:

- **Data events** (`event: data`): stream payload in the `data` field. The response `Stream-Data-Content-Type` header identifies the data payload type (`application/x-ndjson` for JSON streams, the original content type for other streams). SSE `data:` lines are transport lines, not guaranteed message boundaries. JSON clients should buffer until newline before parsing records. For binary streams, data is base64-encoded (controlled by the `Stream-Sse-Data-Encoding` header).
- **Control events** (`event: control`): JSON metadata including the current offset and stream state.

Ursula sends no heartbeat comments and does not end idle SSE connections.

<RequestExample>
```bash Catch-up
curl 'http://127.0.0.1:4437/demo/hello?offset=-1'
```

```bash Long-poll
curl 'http://127.0.0.1:4437/demo/hello?offset=00000000000000000042&live=long-poll'
```

```bash SSE tail
curl 'http://127.0.0.1:4437/demo/hello?offset=-1&live=sse'
```

```bash Read complete JSON records
curl -i 'http://127.0.0.1:4437/demo/hello?record=42&max_records=100'
```

```bash Read complete JSON records, at most 16 MiB
curl -i 'http://127.0.0.1:4437/demo/hello?record=42&max_bytes=16777216'
```

```bash Read the latest JSON records with ordinals
curl 'http://127.0.0.1:4437/demo/hello?tail_records=100&record_view=envelope'
```

```bash Tail future JSON records over SSE
curl -N 'http://127.0.0.1:4437/demo/hello?record=now&record_view=envelope&live=sse'
```
</RequestExample>
