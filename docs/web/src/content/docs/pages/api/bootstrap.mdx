---
title: Bootstrap
api: "GET /{bucket}/{stream}/bootstrap"
---

Returns the stream's latest snapshot (if any) plus the retained updates after the snapshot offset, packed as a `multipart/mixed` response. When some of those updates are only in cold storage, or they exceed 8 MiB, the response is an honest partial: it stops at a message boundary and the client reads the rest with ordinary reads. This is the recommended way to initialize a client that needs the complete current state of a stream.

<ParamField path="bucket" type="string" required>
 Bucket ID.
</ParamField>

<ParamField path="stream" type="string" required>
 Stream ID within the bucket.
</ParamField>

Bootstrap does not accept `?live=sse`. Combining the multipart body with an SSE event stream is rejected with `400`. To go live after bootstrap, finish the multipart response, then open a separate `GET /{bucket}/{stream}?offset=<Stream-Next-Offset>&live=sse`.

## Response

| Status | Meaning |
| ------ | --------------------------------------------- |
| `200` | Bootstrap response with snapshot and updates. |
| `400` | Invalid query parameters (including `live=sse`). |
| `404` | Stream not found or expired. |
| `410` | Requested offset has been trimmed. |

Response headers include:

| Header | Description |
| ------------------------ | ---------------------------------------------------------------- |
| `Content-Type` | `multipart/mixed; boundary=...` |
| `Stream-Next-Offset` | The offset after the last included update, or the snapshot point when the response has no update parts. Continue reading from here. |
| `Stream-Snapshot-Offset` | The snapshot offset, or `-1` if no snapshot exists. |
| `Stream-Up-To-Date` | `true` when the response reaches the stream's tail. Absent on a partial response. |
| `Stream-Closed` | Present and `true` if the stream is closed and the response reaches its tail. |
| `Stream-Record-First`, `Stream-Record-Next` | On a JSON stream with Record Coordinates: the stream's first retained record and record tail (not the end of this response). |
| `Cache-Control` | `no-store`. |

## Complete and partial responses

Let `S` be the snapshot offset, or the first retained offset when there is no snapshot. Ursula returns one of two forms:

- **Complete.** Every retained message in `[S, tail)`, one per part, with `Stream-Next-Offset` at the tail and `Stream-Up-To-Date: true`.
- **Partial.** The messages in `[S, P)` for some message boundary `P` below the tail, with `Stream-Next-Offset: P` and no `Stream-Up-To-Date`. When messages after `S` have already moved to cold storage, `P = S` and the response holds only the snapshot part. When the updates exceed 8 MiB, `P` is the last boundary within 8 MiB, and the response always holds at least one message.

Neither form skips or merges messages. After a partial response, read from `Stream-Next-Offset` with ordinary catch-up reads until `Stream-Up-To-Date: true`, and apply those updates before treating the state as current. Bootstrap never reads cold storage itself.

## Response body

The body is a `multipart/mixed` message:

<Steps>
 <Step title="Snapshot part">
 The first part is the snapshot blob (or an empty part if no snapshot exists).
 </Step>
 <Step title="Update parts">
 Subsequent parts are update messages starting at the snapshot point, exactly one message per part. For JSON streams, each part is one JSON record with the stream's content type.
 </Step>
</Steps>

<RequestExample>
```bash Example
curl 'http://127.0.0.1:4437/demo/hello/bootstrap'
```
</RequestExample>

<Tip>
After bootstrapping, catch up from `Stream-Next-Offset` if the response was partial, then switch to [SSE reads](/docs/api/read) with `live=sse` from the latest `Stream-Next-Offset` to receive real-time updates.
</Tip>
