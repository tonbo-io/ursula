---
title: Troubleshooting
---

Start at `/__ursula/metrics`. Most operational symptoms have a clear signal in the JSON snapshot.

## Diagnostic surface

```bash
curl http://NODE:4437/__ursula/metrics | jq .
```

Useful jq selectors:

| What you need | jq filter |
| ------------- | --------- |
| Per-group leader / term | `.raft_groups[] | {id, leader_id, current_term, last_applied}` |
| Hot bytes per group | `.raft_groups[] | {id, hot_bytes_total}` |
| Cold backpressure events | `.cold_backpressure_events_total` |
| Per-core mailbox depth | `.cores[] | {core_id, mailbox_pending}` |
| Live-read watcher counts | `.cores[] | {core_id, live_read_watchers_active}` |
| HTTP error counters | `.http.responses_by_status` |
| WAL disk pressure | `{available: .wal_available_bytes, minimum: .wal_min_available_bytes, pressure: .wal_disk_pressure}` |
| WAL reclaim/restart | `{physical: .wal_physical_bytes, segments: .wal_segments, reclaims: .wal_reclaims, lagging: .wal_lagging_groups, recovered_bytes: .wal_recovery_bytes, recovery_ns: .wal_recovery_ns}` |
| WAL opening and recovery gates | `{opening: .wal_recovery, gates: .recovery_gates}` |

`GET /__ursula/ready` is the process readiness probe: it returns `503` while
the WAL disk-pressure guard is active, while a group's recovery gate is closed on this
node, and after a Raft protocol mismatch with a peer
(`"reason": "format_epoch_mismatch"`). Ursula does **not** expose `/healthz`, `/readyz`,
Prometheus `/metrics`, or `/cluster/status`; use the JSON snapshot for detailed
diagnosis and `ursulactl wait-ready` for cluster-wide Raft readiness.

## Startup failures

### WAL topology mismatch or missing topology

`topology.bin` binds a WAL root to `runtime.core_count` and `raft.group_count`.
For a mismatch, restore the stored counts reported in the error. A missing
record on an existing WAL or a corrupt record also refuses startup. Do not
replace it with the current configuration. See [WAL routing
configuration](/docs/operations#wal-routing-configuration) for the upgrade and
replica-rebuild limitations.

### `raft.wal.path is required when raft.peers is set`

Every node of a static cluster keeps its Raft WAL in `raft.wal.path`. Set it to a directory on a persistent volume. Only a single node without `raft.peers` may omit it, and then its WAL lives in a temporary directory that is removed on clean shutdown.

### `raft.node_id must be non-zero`

Static Raft mode requires a unique `raft.node_id` in the config file or a `--node-id` override.

### `raft.peers` must include this node id

The local `raft.node_id` must appear in `[[raft.peers]]`. The peer list always includes self.

### `storage.cold.s3.bucket is required when cold backend is 's3'`

Set `storage.cold.s3.bucket`, or set `storage.cold.backend = "none"` if you don't want cold storage.

### Port already in use

`server.listen` is taken. Public HTTP and inter-node gRPC share the same port unless `server.cluster_listen` is configured separately.

### `raft WAL directory … holds data without a format marker`

The data directory was written by Ursula 0.5.x or earlier (format epoch 1). This release reads format epoch 3 only and has no in-place upgrade. Start on an empty `raft.wal.path` and a new object-storage prefix, or run the release that wrote it.

### `raft WAL directory … is format epoch N`

The directory's `FORMAT_EPOCH` marker names another epoch. This release reads format epoch 3 only. Run the release that wrote it, or start on an empty directory.

### `object storage s3://… is not empty and has no URSULA_FORMAT_EPOCH marker`

The cold root (or, with cold storage off, the S3 snapshot namespace) holds objects from Ursula 0.5.x or from another application. Point `storage.cold.root` (Helm: `s3.prefix` or `coldStorage.prefix`), or `storage.snapshot.s3_prefix` when only snapshots use S3, at an empty prefix used only by this cluster.

### `object storage s3://… is format epoch N`

The prefix's `URSULA_FORMAT_EPOCH` marker names another epoch. Use a new prefix and never reuse one across epochs.

### `journal … uses Ursula WAL version N`

A Raft WAL journal of another format epoch: version 1 is Ursula 0.5.x, version 2 is 0.6. This release reads format epoch 3 only. The directory marker normally refuses the directory first, and the journal check is the backstop. Start on an empty `raft.wal.path`.

### `peer N (…) refused Raft protocol 3`

A configured peer runs a release of another format epoch (Ursula 0.6 speaks protocol 2, 0.5.x protocol 1). A node cannot join a cluster of another format epoch. Install this release as a new cluster.

### `/__ursula/ready` answers `503` with `format_epoch_mismatch`

The node exchanged a Raft RPC with a peer on another format epoch: a peer that was unreachable during the startup probe, or a node of another release that has this node in its peer list. The node stays not ready until it restarts. Remove the mismatched node from the peer lists and restart.

### `/__ursula/ready` answers `503` with `recovery_gate_closed`

The node's logs may be missing entries it acknowledged: it started after a host
crash or power loss under `raft.wal.fsync = "never"`, after a journal I/O error,
or without its run state file, or with an emptied WAL directory. Each
gated group waits until it has applied a fresh barrier from the group's leader,
and its leader rebuilds the replica meanwhile. `recovery_gates` in
`/__ursula/metrics` lists the gated groups. This normally clears in seconds
once a leader is reachable. See
[Recovering after a host crash](/docs/operations#recovering-after-a-host-crash).

### `/__ursula/ready` answers `503` with `recovery_stalled`

A gated group on this node has seen no leader barrier and applied nothing for
`30s`. A majority of the group's voters are probably gated, so the group has no
leader and refuses writes. The groups are listed under
`recovery_stalled_groups`. The group recovers only when an operator accepts the
loss of writes acknowledged after the last `fsync`, with
`POST /__ursula/raft/{group}/recovery/accept-unsynced-loss` on the gated
replicas with the longest logs. The request body names the replica's
`last_log_index` and `current_term` from `/__ursula/metrics`. See
[Recovering after a host crash](/docs/operations#recovering-after-a-host-crash).

### `accept-unsynced-loss` answers `409 Conflict`

Nothing changed. The body says why. Either the replica's recovery gate is not
stalled, so it may still open through a leader's barrier without losing
anything, or the replica no longer holds the `last_log_index` and
`current_term` the request names. Wait for `recovery_stalled`, read
`/__ursula/metrics` on the replica again, and decide again with what it shows.

### I/O error on `raft.wal.path`

The directory must be writable and owned by exactly one Ursula process. Each
core journal holds an advisory `journal.lock` containing the owner PID. Do
not remove it while that process is alive; stop the conflicting process or fix
the volume mount. A stale lock file is harmless because ownership is enforced
by the OS lock, not the file's existence.

## Backup and restore

### `backup manifest format_version N` or `target cluster speaks backup format N`

The backup or the cluster is of another format epoch. This release reads and writes backup format 3 only, so a backup of another epoch cannot be restored, and a cluster of another epoch cannot be backed up or restored into.

### `… cold objects this backup references are missing from the target cluster's cold store`

The backup references cold objects that the target's `storage.cold.root` does not hold. `restore` stopped before the first import, so the target is still empty. Copy the source cluster's cold objects into the target's root (see [Copying cold objects](/docs/operations#copying-cold-objects)) and run `restore` again. The error names the first missing keys. A key under `cold-index/` is an index page, so everything that page lists is unchecked until the page is there.

## Bootstrap and cluster join

### A fresh cluster never elects leaders

`/__ursula/metrics` on each node should show non-zero `leader_id` and a stable `current_term`. If groups stay leaderless:

- First start must include `raft.init_membership_per_group = true` (or `raft.init_membership = true`) on every voting node.
- Every peer URL must be reachable from every node.

### Replacing or restarting a node leaves it leaderless

Restart with the **same** `raft.node_id` and peer list. A fresh `raft.wal.path` means rehydrating from peers, which can be slow on cold-storage-only history (see [Rejoining a wiped node](/docs/operations#rejoining-a-wiped-node)).

## Write path

### `503` with `Retry-After` on append

Inspect the JSON error. `WalDiskPressure` means the WAL filesystem is below
`raft.wal.min_available_size` (or its free-space stat failed); the node also
becomes unready and attempts to yield its leaders. Free space or expand the
volume. Admission resumes only at `raft.wal.resume_available_size`, preventing
probe flapping.

Other errors indicate cold-write backpressure for that group. Either the hot
ring exceeds `storage.cold.max_hot_size_per_group` (cold flush isn't keeping
up), or the cold backend is slow or erroring out.

Raise the per-group ceiling, lower `storage.cold.flush_interval`, raise `storage.cold.flush_max_concurrency`, or fix the cold backend.

### `409 Conflict` with `producer-expected-seq` / `producer-received-seq`

Out-of-order producer headers. Response tells you what was expected:

- `producer-expected-seq: N` is the next allowed sequence
- `producer-received-seq: M` is what the client sent

Common causes:

- Producer restart without bumping `Producer-Epoch`. Bump every restart.
- Two writers share the same `Producer-Id`. Use distinct IDs.
- A retry skipped a sequence number. Producer sequences must be contiguous within an epoch.

### `409 Conflict` from `Stream-Seq`

The supplied `Stream-Seq` is not bytewise greater than the last value accepted on this stream: another writer committed first, or the values are not fixed-width (`"10"` sorts before `"9"`). The response's `Stream-Next-Offset` is the tail. Read what you missed, re-derive the value and retry. See [Conditional writes](/docs/concepts/conditional-writes).

### `404 Not Found` on `POST /{bucket}/{stream}`

The stream hasn't been created. Create with `PUT /{bucket}/{stream}` first. There is no implicit creation on POST.

### `400 Bad Request` on JSON appends

JSON streams are validated on the server. Malformed JSON, invalid UTF-8, messages nested deeper than 127 levels, and empty arrays without `allow_empty_array` are rejected. Send valid JSON or switch to `application/octet-stream`.

## Read path

### No `Stream-Up-To-Date` on a read

The response is partial: cut by `max_bytes` or the 8 MiB cap, or served by a follower, which never sends it with data. Read on from `Stream-Next-Offset`. Not an error.

### SSE drops after 30-60 s idle

A proxy or load balancer is closing idle TCP. Raise its idle timeout or enable TCP keepalive on the proxy-to-Ursula leg. Ursula doesn't emit SSE keepalive comments.

### SSE on a binary stream returns base64 text

Expected. SSE wire format is text-only, so binary stream data events carry raw base64 text and the `Stream-Sse-Data-Encoding: base64` header signals it. See [binary SSE](/docs/concepts/binary-sse).

### Reads stall for hundreds of ms for cold offsets

The first read of a cold offset triggers an S3 `GetObject` range read. It runs off the actor turn so it doesn't block other commands, but the request still pays S3 latency.

## Replication and consensus

### A group has no leader (`leader_id == 0`)

Either an election is in progress or quorum is lost for that group. Only streams hashed to that group are affected.

- Multiple nodes briefly claim leader: election is flapping. Check peer reachability and CPU pressure.
- No node claims leader: fewer than `n/2+1` voters are reachable. Restore reachability.

### One follower lags behind

State-machine apply runs on the follower's owner core. If CPU is pinned, `last_applied` trails. Check:

- Per-core mailbox depth (sustained queueing means saturation).
- Disk pressure on the WAL volume (`fsync` latency, in particular with `raft.wal.fsync = "always"`).
- A pathological hot stream forcing constant cold flushes (`hot_bytes_total` per group).

### Manually trigger a snapshot

These are admin-plane endpoints (`server.admin_listen`, loopback `:4438` by default), reached over a tunnel (see [ursulactl's operation providers](/docs/cli#the-admin-plane)). The examples assume a forward from local `4438` to the node's admin plane.

```bash
process_incarnation=$(curl --fail http://127.0.0.1:4438/__ursula/metrics | jq -er .process_incarnation)
curl --fail -H "x-ursula-process-incarnation: ${process_incarnation}" -X POST http://127.0.0.1:4438/__ursula/raft/{group_id}/snapshot
curl --fail -H "x-ursula-process-incarnation: ${process_incarnation}" -X POST http://127.0.0.1:4438/__ursula/raft/{group_id}/purge
```

Purge only after the snapshot replicates. Otherwise a slow follower may need log entries you just dropped.

## A Raft group stopped while applying a committed record

An application panic or internal application error stops only that local Raft
group. Other groups continue running. The failed group reports
`apply_failure` in `/__ursula/metrics`, including its term, log index, failure
kind, and message; its maintenance `running` flag is false and readiness fails.
Ordinary stream errors (for example, a missing stream) remain protocol responses.

The failed entry is still committed in the WAL. It is not acknowledged as
successfully applied, skipped, or included in a new snapshot. A deterministic
bug can stop the same group on every replica when each reaches that record.
Restarting the same buggy binary will encounter it again.

To recover without losing committed data:

1. Save metrics, error logs, the exact binary revision, and a consistent backup
   of the stopped node's WAL volume. Keep the original volume and configuration.
2. Fix the deterministic application bug and validate replay using a copy of
   that WAL. Confirm that the failed record applies and that earlier data remains
   readable. If the cause is an unavailable dependency rather than code, restore
   that dependency before replay.
3. Deploy the corrected binary and restart the stopped replica with its **original
   WAL directory and snapshot metadata**. Follow the normal maintenance procedure;
   a group whose quorum is stopped needs enough corrected replicas to restore its
   quorum. Do not clear recovery gates to bypass missing-log detection.
4. Check that `apply_failure` is absent, `last_applied.index` has passed the failed
   index, the group has a leader, and readiness succeeds. Verify reads of data
   written before the failure and submit a fresh write.

Do not truncate the WAL, delete the failed record, force a purge, or restore an
older backup over the existing volume. Ursula does not offer a local skip switch:
skipping a committed command independently on replicas would diverge their state.
The native regression `poison_apply_isolates_one_group_and_corrected_code_replays_the_intact_wal`
exercises the supported restart/replay procedure with a disk WAL, a deterministic
apply failure, and an unaffected group sharing the same core journal.

## Cold flush issues

### Writes succeed but data never reaches S3

- `storage.cold.backend` is `none`, or set to `memory` when you expected `s3`.
- IAM permissions missing. Required: `s3:GetObject`, `s3:PutObject`, `s3:ListBucket`, `s3:DeleteObject`.
- `storage.cold.s3.endpoint` unreachable.
- Cold flush worker stalled (`cold_backpressure_events_total` climbing).

If hot bytes grow unbounded, you'll eventually hit `storage.cold.max_hot_size_per_group` and writes start returning `503`. Fix the backend before that.

## Still stuck?

Open a [GitHub issue](https://github.com/tonbo-io/ursula/issues) with:

- `/__ursula/metrics` from every node (with timestamps)
- Config file and CLI overrides per node (redact credentials)
- Last ~200 log lines at `RUST_LOG=ursula_runtime=debug,ursula_raft=debug,ursula=info`
