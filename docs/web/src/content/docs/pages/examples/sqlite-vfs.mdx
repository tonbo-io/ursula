`sqlite-ursula-vfs` is a SQLite loadable extension that replicates a database file to an Ursula stream. Your application keeps using SQLite unchanged, for example `node:sqlite` or Pi Durable's official `SqliteStorage`: every commit is appended to the stream before it reaches the local file, and any host can rebuild the database from the stream. The extension lives in [`clients/sqlite-vfs`](https://github.com/tonbo-io/ursula/tree/main/clients/sqlite-vfs), and the TypeScript helpers in [`clients/sqlite-ursula`](https://github.com/tonbo-io/ursula/tree/main/clients/sqlite-ursula), published to npm as `@tonbo/sqlite-ursula` with the extension prebuilt.

It is experimental: the extension speaks plain HTTP without credentials, and its formats and API may change in a minor release. What it still needs for production use is tracked in [#468](https://github.com/tonbo-io/ursula/issues/468).

How it works:

- One database is one binary stream (`application/octet-stream`). A commit is one append carrying the transaction's final page images, zstd-compressed.
- The append happens at SQLite's commit point. `COMMIT` returns only after Ursula acknowledged it; if the append is rejected, SQLite rolls the transaction back and nothing of it stays local.
- Attaching a file claims the stream with a new producer epoch. Every earlier owner is fenced: its next commit fails.
- The owner publishes a [snapshot](/docs/concepts/snapshots) of the database whenever the log since the last one outgrows the database (8 MiB at least), reads it back, and then advances the stream's retention to the snapshot before it. A new host starts from the latest snapshot and replays only the tail.

## What the cluster needs

- Room for one transaction per append: up to 32 MiB of compressed page images.
- For databases whose snapshots exceed 1 MiB, a cold backend, so snapshot bodies are stored in the cold tier (up to 1 GiB). Without it, snapshots are kept inline, up to 32 MiB.
- Snapshots above 32 MiB must go straight to a node, or through a gateway whose `--max-request-body-bytes` is raised.

## Install and load

```bash
npm install @tonbo/sqlite-ursula
```

The package needs Node.js 22.19 or later. It ships the extension prebuilt for Linux x64 and arm64 with glibc 2.28 or later (Debian 11, Ubuntu 20.04, Amazon Linux 2023 and newer), Linux x64 with musl (Alpine), and macOS 11 or later on Apple silicon. npm installs only the build for your platform.

On other platforms, build the extension and point `SQLITE_URSULA_VFS` at it. The variable also overrides the prebuilt extension.

```bash
cd clients/sqlite-vfs
cargo build --release   # target/release/libsqlite_ursula_vfs.so (.dylib on macOS)
export SQLITE_URSULA_VFS=$PWD/target/release/libsqlite_ursula_vfs.so
```

The extension calls whatever SQLite loads it, here `node:sqlite`. Load it once per process: it registers the `ursula` VFS as SQLite's default. `attach` and `openUrsulaPiStorage` load it if you have not.

```ts
import { attach, loadUrsulaVfs, status } from "@tonbo/sqlite-ursula";
import { DatabaseSync } from "node:sqlite";

loadUrsulaVfs(); // the prebuilt extension, or the one SQLITE_URSULA_VFS names

// Catch the file up (from the latest snapshot if it is missing or behind), claim the stream,
// and attach. No connection to the file may be open yet.
attach("/data/app.db", "https://ursula.example.com/my-bucket/app-db");

const db = new DatabaseSync("/data/app.db");
db.exec("PRAGMA journal_mode=WAL");
db.exec("CREATE TABLE IF NOT EXISTS notes(id INTEGER PRIMARY KEY, body TEXT)");
db.prepare("INSERT INTO notes(body) VALUES (?)").run("replicated"); // returns after Ursula has it

console.log(status("/data/app.db"));
// { offset, epoch, poisoned, fenced, reason, snapshot, retained, local, installed }
```

From SQL, the same functions are `ursula_attach(path, url)`, `ursula_status(path)`, `ursula_stats(path)` and `ursula_set_token(token)`. They can be called from top-level SQL only, not from a trigger or a view. Offsets (`attach`'s result, and `offset`, `snapshot`, `retained`, `local` and `installed`) are the server's [opaque offset](/docs/concepts/offsets) strings: compare two of the same stream as strings, never as numbers. `"-1"` means none (no snapshot, no retention, a file rebuilt from nothing).

## TLS and credentials

`https://` stream URLs work with the certificate authorities bundled with the extension (Mozilla's). For a private CA, point `URSULA_VFS_CA_FILE` at a PEM bundle: the extension then trusts only the CAs in it.

Behind `ursula gateway` with access control (see [Security](/docs/security)), every request needs a bearer token. Name a file that holds it, and the extension reads it again whenever it changes (a Kubernetes projected token, or a file a sidecar refreshes):

```bash
export URSULA_VFS_TOKEN_FILE=/var/run/secrets/ursula/token
```

Or set it from the application. It takes precedence over the file until you set `null`:

```ts
import { setToken } from "@tonbo/sqlite-ursula";

setToken(accessToken);
```

The token is process-wide. A request whose token is refused (`401`) is sent again, with the token read again, within the retry budget (`URSULA_VFS_RETRY_MS`). A commit still refused then fails, and the file must be attached again, as after any failed commit. A `403` from the gateway's authorizer fails the request at once. Neither marks the owner fenced. The gateway answers `404` for a private bucket to a client without a token, so attach then reports the stream as missing.

`setToken` cannot rescue a commit that is already retrying. `node:sqlite` is synchronous, so the thread that runs the commit cannot call `setToken` until the commit returns. A commit whose set token has expired waits out the retry budget (30 s by default, and reads of the file in the process wait with it), then fails, and the file must be attached again. Call `setToken` with a fresh token before the current one expires, or use a token file, which is read again on every retry.

When the token file holds no token as it is read (empty, half-written, or missing while it is replaced), the extension keeps the last token it read from it, and logs `token_file_unreadable` once until the file holds a token again.

Over `http://` the token crosses the network in clear. Use `https://` for any endpoint on another host. The extension logs `token_in_clear` once when it sends a token over `http://` to a host that is not a loopback address.

## Health and alerts

`status(file)` (`ursula_status`) reports the owner's health along with its offsets:

- `commits`, `append_retries`: commits acknowledged since the attach, and append attempts beyond the first (unknown outcomes, `429`, `503`, a refused token).
- `log_bytes`, `snapshot_due_bytes`: the log since the latest snapshot, which a rebuild replays, and the size at which a snapshot is taken (the database's size, or `URSULA_VFS_SNAPSHOT_MIN_BYTES` if larger).
- `snapshot_age_ms`, `snapshot_failures`, `snapshot_error`: milliseconds since this owner last saw a snapshot published (`null` for none since the attach), and the snapshot attempts that failed in a row with the last reason.
- `attach_ms`: how long the attach took.

`instrument(file, meter)` reports the same as metrics on an OpenTelemetry `Meter`, which can be any object with `createHistogram`, `createCounter` and `createObservableGauge`. The package does not depend on OpenTelemetry. The metrics are `sqlite_ursula.commit.duration` and `sqlite_ursula.append.duration` (ms), `sqlite_ursula.append.retries`, `sqlite_ursula.stream.bytes`, and the gauges `sqlite_ursula.log.bytes`, `sqlite_ursula.snapshot.due_bytes`, `sqlite_ursula.snapshot.age`, `sqlite_ursula.snapshot.failures`, `sqlite_ursula.poisoned` and `sqlite_ursula.fenced`. It drains `drainStats` every 10 seconds, so do not drain the same file elsewhere. Call the function it returns to stop.

The extension logs one line per event on stderr, in logfmt: `sqlite-ursula-vfs level=warn event=poisoned file=... stream=... fenced=true reason="..."`. The events: `poisoned`, `append_retry` (a commit's append failed and is tried again, with the attempt, the time since the commit's first attempt and the reason), `append_gave_up` (the same for the last attempt, after which the commit fails), `snapshot_failed`, `open_refused`, `journal_refused`, `local_files_discarded`, `attach_retrying`, `attach_rebuilding`, `token_file_unreadable`, `token_in_clear`, `ca_file_unreadable`, `ca_file_without_certificates`.

Alerts worth setting:

- `poisoned` is 1: commits fail until the file is attached again. `reason` says why. Attach again once the cause is fixed.
- `fenced` is 1 without a planned handoff: another process claimed the stream. Find the second owner before attaching again.
- `log_bytes` stays above a few times `snapshot_due_bytes`, or `snapshot_failures` keeps growing: snapshots are not being published, for example a body over the gateway's `--max-request-body-bytes` or a long reader pinning WAL frames. Every rebuild then replays the whole log.
- The p99 of `sqlite_ursula.commit.duration` rises: look at the Ursula cluster first. A commit waits for its append.

## Pi Durable

`openUrsulaPiStorage` attaches the file and opens it with Pi's own node driver:

```ts
import { openUrsulaPiStorage, UrsulaReplicationError } from "@tonbo/sqlite-ursula";

const storage = await openUrsulaPiStorage("/data/harness-1.db", "https://ursula.example.com/pi/harness-1");
// hand `storage` to the Pi harness; storage.close(ctx) on shutdown
```

A commit the stream does not accept surfaces as `UrsulaReplicationError`; `fenced: true` means another host took the stream over, the stream was deleted and recreated (opening it again then rebuilds the file from the new stream; see Rules), or another writer appended to it with a higher `Stream-Seq`. The storage is then read-only for this process: open it again to take the stream back.

## Rules

- WAL mode only, 4 KiB pages (SQLite's default). `locking_mode=EXCLUSIVE` is not supported.
- One process owns a database file at a time (a lock file next to it enforces this on the host). Use as many connections inside that process as you like.
- Treat the local file as a cache: do not copy it elsewhere and attach it to another stream. A commit is durable once Ursula acknowledges it; commits do not fsync the local files (only the db file, once per WAL wrap), so `PRAGMA synchronous` does not matter.
- After a reboot, a power loss, or on another host, attach discards the local files and rebuilds them from the latest snapshot and the stream's tail (a crashed process on the same boot resumes from its local files). A volume restored from a disk snapshot without a reboot is checked: attach uses it only if its WAL still holds what the sidecar `<db>-ursula` records, and rebuilds otherwise. Keep the file on a local disk, not a network filesystem, and do not copy it with `cp` or `rsync` while the process runs. Delete the file to force a rebuild.
- A commit whose append gets no answer is retried with the same producer sequence for up to 30 s (`URSULA_VFS_RETRY_MS`), then fails, and the file must be attached again.
- A file that has been attached (it has a sidecar `<db>-ursula`) opens only after an attach of it succeeds in the process: in a new process before its attach, or after an attach that failed (the server is unreachable, for example), opening it fails (SQLite reports "unable to open database file"; the log, and `ursula_status` after a failed attach, name the reason), so no commit can bypass the stream.
- A stream deleted and recreated at the same path is a new stream: attach never resumes the local file on it, and rebuilds it from the new stream, whatever its length. When the stream of a file that holds data is missing (deleted by mistake, expired, or not carried over by a fresh install), attach refuses and keeps the file, which may be the only copy left. Delete the file to start over from an empty stream, or attach a new file under another stream URL. Neither the file nor a copy of it attaches under another URL. To salvage its data, copy the file and its `-wal` to a new name before deleting anything. The copy has no sidecar, so it opens as a plain SQLite file: read its rows from there into a newly attached database. An owner of the deleted stream is normally fenced at its next commit, but stop every owner before deleting a stream you will recreate: a snapshot it is publishing, or an attach racing the recreate, can still put its data into the new stream (see the design doc).
- Within a minor (0.7.x), extension versions take over each other's streams, so upgrade owners one at a time: the new owner's attach fences the old one. Across minors, follow the release notes. A minor that changes the extension's `Producer-Id` cannot fence owners of the other version, so both would commit and could corrupt the database: stop every owner of a stream before attaching it with the new version (and the reverse on a downgrade). A frame or snapshot of another minor's format stops attach with an error that names it.
- An owner idle for 7 days loses its producer state on the server; its next commit takes the stream back only if nobody else wrote meanwhile.
- Every commit carries a `Stream-Seq` above all earlier ones. Do not append to the stream yourself: a write with a higher `Stream-Seq` fences the owner at its next commit, and one without breaks every rebuild that replays it, until the owner publishes a snapshot past it.
- `URSULA_VFS_SNAPSHOT_MIN_BYTES` sets the smallest log between snapshots (default 8 MiB).
