The first tool to reach for is [`ursulactl`](/docs/cli). It covers the raft-aware verbs operators run most often: drain, status, readiness gates. This page covers everything **around** it: the metrics shape ursulactl reads, the admin endpoints it (and your custom tooling) can call, and the operational policies ursulactl does not encode (backups, log levels). Deployment and process lifecycle belong to the platform, [Helm and OpenTofu](/docs/deploy-cluster).

## Tooling map

| Surface | When to reach for it |
|---------|---------------------|
| [`ursulactl`](/docs/cli) | Day-2 cluster ops over HTTP: drain, restart, status, wait-ready. |
| `/__ursula/metrics` and the `/__ursula/raft/...` admin endpoints | Custom tooling. ursulactl uses these underneath. The surface is small and stable enough to script directly. |

There is no Prometheus scrape and no general-purpose orchestrator yet.

## Metrics

```bash
curl http://127.0.0.1:4437/__ursula/metrics | jq .
```

The JSON snapshot covers per-core mailbox depth, append/read counters, latency
histograms, per-group leader and `last_applied`, hot/cold bytes, cold-flush
backlog, WAL physical/reclaim/recovery work, WAL disk-pressure admission, HTTP
status counters, live-read watchers, and cold-write admission state. Start here
when triaging slowness, lag, or `503`s. `GET /__ursula/ready` provides the
process-level readiness signal; `ursulactl status` is a friendlier read of the
leadership-related fields across the whole cluster.

## Admin endpoints

These are the primitives `ursulactl` and any custom operator tooling builds on. They live on the **admin plane** (`server.admin_listen`, loopback `127.0.0.1:4438` by default), not the public client plane. Nodes expose no cluster-mutation surface on the network. Reach them over a tunnel to the admin port (see [ursulactl's operation providers](/docs/cli#the-admin-plane)). The examples below assume a forward from local `4438` to the node's admin plane. Each call is local to one node. To act on every group, loop over the IDs in metrics.

```bash
# Force a cold flush for one stream (skip the timer)
curl -X POST http://127.0.0.1:4438/__ursula/flush-cold/demo/hello

# Trigger a Raft snapshot for one group
curl -X POST http://127.0.0.1:4438/__ursula/raft/42/snapshot

# Purge log entries below the last snapshot index for one group
curl -X POST http://127.0.0.1:4438/__ursula/raft/42/purge

# Add a learner (non-voting replica) to one group without blocking on catch-up
curl -X POST "http://127.0.0.1:4438/__ursula/raft/42/learners/4?addr=http://node-4:4437&blocking=false"

# Hand leadership of one group to another voter (used by `ursulactl drain`)
curl -X POST http://127.0.0.1:4438/__ursula/raft/42/leader/transfer/2

# Replace the voter set of one group (call on the group's current leader)
curl -X POST "http://127.0.0.1:4438/__ursula/raft/42/membership?voters=1,2,3"

# Put this node into maintenance drain / lift it again
curl -X POST   http://127.0.0.1:4438/__ursula/leadership-shed/maintenance
curl -X DELETE http://127.0.0.1:4438/__ursula/leadership-shed/maintenance

```

The leader-transfer endpoint refuses with `409 Conflict` if the receiving node isn't the current leader and `400 Bad Request` if the target isn't a voter. This is why `ursulactl` is the safer way to chain these calls: it consults metrics first.

On a memory-WAL cluster the group leader keeps every group at its configured voters: if the membership endpoint drops a configured voter, the leader adds it back as a learner and promotes it again once it has caught up (see [Restarting a memory-WAL node](#restarting-a-memory-wal-node)). Membership changes there are for repair, not for shrinking a group.

The membership endpoint has the same leader-only contract: it answers `409 Conflict` (with the current leader's id in the body) when the receiving node does not lead the group, and `400 Bad Request` without a non-empty `voters` query parameter. On success it returns the log index at which the new voter set was committed. It replaces the whole voter set in one call, so include every node that should remain a voter.

### Maintenance drain

`POST /__ursula/leadership-shed/maintenance` marks the node as draining: it stops campaigning and accepting transfers, and the background leadership balancer migrates its current leaderships to eligible peers one transfer per tick until the mark is lifted with `DELETE`. Both verbs return the node's leadership-shed state so tooling can confirm the transition took effect:

```json
{
  "bits": 1,
  "state": "maintenance-drain",
  "should_accept_transfer": false,
  "should_campaign": false,
  "should_shed_current_leaders": true
}
```

`ursulactl drain` wraps exactly this pair: mark first so the node stops re-acquiring groups, then transfer leaderships away explicitly instead of waiting for the balancer. The mark stays set until `ursulactl undrain` clears it. If a rollout ever dies mid-way, a node can be left refusing leadership. Run `ursulactl undrain` (or `DELETE` the mark directly) to recover. Peers read each other's shed state (`GET /__ursula/leadership-shed` on the cluster-plane listener) when deciding which nodes are eligible to pick up leaderships, so a drained node stops attracting groups cluster-wide, not just locally.

### Rejoining a wiped node

Rebuild a wiped voter through committed membership: remove it from each affected voter set, attach it as a blocking learner with its current address, and promote it only after snapshot and log catch-up. Use `ursulactl repair-restarted-voter` for the cluster-wide, resumable sequence. A process-local log-reversion trigger is not a durable recovery contract; the admin API uses it only to adopt a survivor after a majority of a memory-WAL group restarted (below). A memory-WAL node restarted alone is rebuilt automatically from 0.6.2.

### Restarting a memory-WAL node

Every restart of a node on `raft.wal.backend = "memory"`, planned or not, wipes it: it comes back with an empty Raft log. Production clusters must use the disk WAL; the memory WAL is for development, benchmarks and chaos (`raft.wal.allow_volatile_multi_peer`). From 0.6.2 a restarted node is rebuilt automatically when it is the only one of its groups to lose its log, and a group that loses the log on a majority of its voters, or on all of them, stops instead of losing acknowledged writes (a restart of every voter is detected only with object storage).

**A minority restarts (one node of three).** Nothing to do. For each group on the restarted node:

- **It does not initialize the group again.** A per-group membership initializer (`raft.init_membership_per_group = true`, the chart default) runs `Initialize` only when every other configured voter answers that it holds nothing for the group either and no leader is seen; a fresh install still bootstraps this way. One voter holding entries or following a leader means the group exists, and the node waits to be replicated to. It waits for every voter, not a quorum, so a fresh install with a voter that never comes up stays uninitialized (it logs "waits for every voter before initializing").
- **It does not vote until it has caught up.** Until the node holds the log that its leader had committed when it first heard from that leader, it refuses every vote for a candidate whose log is not empty and, once it has seen committed entries, every candidate. It can never help elect a leader that lacks entries committed with its lost copy.
- **The leader rebuilds it.** The leader sees the node answer that it lacks entries it had acknowledged, and runs the same sequence as `ursulactl repair-restarted-voter`: commit a voter set without the node, add it back as a learner, wait until it has replicated the commit index, promote it. Each step is read off the current membership, so a leader change, another restart of the node, or `repair-restarted-voter` running at the same time all converge. Leadership handoffs (the balancer, the commit-stall watchdog) skip the node until then.

`ursulactl verify-cluster` shows the node unready until every group has promoted it. The chart's graceful-rollout hook still runs `repair-restarted-voter` after a prepared restart; it finds nothing left to do. During a rolling upgrade from 0.6.1, a group whose leader still runs 0.6.1 is not rebuilt automatically; the hook rebuilds it, and the 0.6.2 node refuses to vote meanwhile.

**A majority restarts at once (two nodes of three).** The group stops accepting writes and waits for an operator. The empty nodes refuse every candidate, and a surviving leader never removes a voter because the removal could not commit, so no leader with an incomplete log is ever elected and no acknowledged write is silently lost. Writes answer `503` with `Retry-After` while no leader exists; a surviving node that still believes it leads accepts writes it cannot commit, so they time out.

To recover from a majority restart, pick the survivor whose log you keep: on each affected group, the voter with the highest `last_log_index` in `GET /__ursula/metrics`. Acknowledged writes that only the lost nodes held are gone; adopting the survivor accepts that. Then run, on every node of the group (through each node's admin listener, as below):

```bash
# group 42, survivor node 1
curl -X POST http://127.0.0.1:4438/__ursula/raft/42/rejoin/adopt-survivor/1
```

On an empty node this lets it vote for the survivor (and only the survivor) while it is behind (`"action": "vote_released"`). On the survivor, if it still leads, it lets it replicate the emptied nodes from the start (`"followers_reset"`); if it does not lead (`"survivor_not_leader"`), it wins the next election once the others released their vote. The group then heals as after a minority restart. This is the only use of OpenRaft's one-shot log-reversion reset; it is process-local, so repeat the call if the survivor restarts or loses leadership before the emptied nodes caught up.

**Every node restarts at once.** Every voter of every group comes back empty, which looks exactly like a fresh install to the bootstrap probe. Object storage tells them apart: each memory-WAL group keeps an "initialized" marker, `URSULA_GROUP_INITIALIZED/group-{id}`, next to the format-epoch marker (at the cold-storage root, or under the snapshot prefix when only snapshots use S3).

- A group leader writes the marker before it proposes the group's first write, and proposes no write until the marker is stored (`503` with `Retry-After` meanwhile, for example while object storage is unreachable). A process checks this once per group, so an outage later does not stop writes. No write is ever acknowledged without the marker.
- A replica whose applied state already holds writes (a group created by 0.6.1, which writes no marker) writes the marker too, so a cluster upgraded from 0.6.1 is protected once every pod runs 0.6.2, with no new write. 0.6.1 ignores the marker, so a downgrade is safe; it just loses the protection.
- When every voter of a group reports an empty log, the group's initializer reads the marker. No marker: the group never acknowledged a write, and it initializes as on a fresh install. This covers a crash of every node during the first bootstrap: no operator is needed. Marker present: the group held writes that no node has any more. It does not initialize: it has no leader and refuses writes (`503`), and the initializer logs `lost its log on every voter after it held writes` with the group id and lists the group under `memory_wal_full_restart_groups` in `GET /__ursula/ready` (readiness itself stays `200`, so the node keeps serving its other groups). Marker unreadable (object storage unreachable): it does not initialize, and retries until it can read the marker.

The writes are gone; only the operator can accept that. On the node that lists the group (the group's initializer: with per-group initializers, the voter at position `group id mod voter count`, counting from 0, in the group's sorted voter list), run, through its admin listener:

```bash
# group 42: initialize it again, empty, accepting the loss of its writes
curl -X POST 'http://127.0.0.1:4438/__ursula/raft/42/rejoin/reinitialize?accept_data_loss=true'
```

It answers `{"action": "reinitialize_accepted"}`, and the group initializes on the next probe. Without `accept_data_loss=true` it answers `400`; on a node where the group has not stopped, `409`. Cold objects the group wrote before the restart stay in object storage, unreferenced. To start such a cluster over instead, install it on a new object-storage prefix (as for any fresh install).

Without object storage (memory cold store and inline snapshots) nothing survives a restart of every node, so it cannot be detected: the groups initialize again, empty, and every acknowledged write is lost.

`POST /__ursula/cluster-probe` also exists on the client plane, but it is machinery rather than an operator surface: nodes send each other heartbeat-sized bodies through it to verify cluster-plane egress, and it bypasses ingress admission.

## Memory without retention

Per-stream replicated state, on every replica, is at most about 32 KiB plus bounded producer state, beyond the unflushed payload itself, without retention. It grows neither with the number of messages nor with the length of the cold history. The bounds that make this hold are always on: a 1,024-receipt producer receipt window per stream with 7-day idle-producer expiry and a 4,096-producer cap, unique stream incarnations with incarnation-scoped cold objects, external payload locators committed first and indexed after, and a compact hot window with no per-message bookkeeping, so cold admission and the flush thresholds charge hot payload only. Snapshot bodies of at least `runtime.external_payload_min_size` go to the cold tier when a cold backend is configured (up to 1 GiB). Retention stays available as a storage-cost tool, but it is not the way to bound memory.

The per-group gauges under `group_state_gauges` in `/__ursula/metrics` show what each group holds.

## Usage export

`GET /__ursula/usage` returns committed counters and current gauges from local replicated state, aggregated by bucket across this node's Raft groups:

```json
{
  "version": 1,
  "write_unit_bytes": 10240,
  "buckets": {
    "tenant-a": {
      "committed_append_bytes": 24576,
      "committed_records": 3,
      "committed_write_units": 4,
      "retained_bytes": 24576,
      "stream_count": 1
    }
  }
}
```

The raw byte and record counters are pricing-neutral facts. `committed_write_units` is a convenience derived meter: every committed, non-deduplicated create or append contributes at least one unit and rounds its canonical payload up independently by `write_unit_bytes`. Consumers must validate both `version` and `write_unit_bytes` before interpreting it; the unit is data in the contract, not encoded into the counter name. The same unit is persisted in Raft snapshots, and a build refuses to restore a snapshot carrying a different unit. Changing it therefore requires a new contract version and an explicit state migration, never a configuration edit. Ursula does not attach currency, a price, or an account owner.

Counters are monotonic and survive snapshots, stream deletion, and bucket purge. `retained_bytes` and `stream_count` are current-state gauges and may decrease. A node serves local applied state, so replicated consumers should poll every voter and use their own completeness policy rather than treating one response as a cluster-wide linearizable read.

## Tenant offboarding (bucket purge)

`DELETE /__ursula/purge/{bucket}` erases one tenant's complete bucket domain: every stream in every Raft group, the bucket, cold chunks and indexes, external payloads, and any uncommitted object-store staging orphan below `{bucket}/`. The replicated purge also installs a permanent bucket-erasure fence in every group. It retains only the bucket's aggregate usage counters, because deleting a counter before an asynchronous meter observes it would erase committed billable work. Purge is served only on the admin listener (`server.admin_listen`, loopback `127.0.0.1:4438` by default); the client listener answers `404`. On Kubernetes the chart keeps the admin listener on pod loopback, so reach it through `kubectl port-forward pod/<voter-pod> 4438:4438` or `kubectl exec`; any one voter accepts the request for the whole cluster.

The response is a completion report an operator can attest to:

```bash
curl -X DELETE http://127.0.0.1:4438/__ursula/purge/tenant-a
# {"bucket":"tenant-a","removed_streams":12,"groups_with_streams":[0,3,5],"cold_gc_entries_reclaimed":12,"cold_gc_pending_entries":0,"cold_gc_complete":true,"cold_gc_error":null,"bucket_prefix_absent":true}
```

Semantics:

- **Retry on `503`.** A Raft group whose leader is unknown or changing answers `503` with `Retry-After`, never a redirect to a peer. Because purge is idempotent, retry the same request.
- **Idempotent and resumable.** Re-purging an erased bucket returns the same report shape with zero removals. A purge interrupted mid-way converges on re-run: the permanent fence and stream removal are replicated commands per group, while cold reclamation and the complete bucket-prefix erasure are repeatable object-store operations.
- **Permanently fenced.** Commands linearized after purge cannot create the bucket or append to its streams. The fence survives Raft snapshots and restore; data-plane access continues to conceal the erased namespace as `404 Not Found` instead of recreating it.
- **Isolated.** Other buckets' streams, offsets, checksums, snapshots, and object-store prefixes are untouched. Every cold object, shared packs included, lives under its own bucket's `{bucket}/` prefix.
- **Accounting residue.** The retained entry contains only aggregate counters and zero-valued content gauges, not stream data. Ursula does not currently provide an acknowledgement protocol for erasing it after an external meter persists the final delta. Use opaque bucket IDs if retaining the identifier itself would violate an erasure requirement.
- **Physical absence proof.** `cold_gc_entries_reclaimed` is diagnostic only. After a second replicated purge proves every group's bucket-specific GC queue is empty, Ursula recursively deletes the complete `{bucket}/` erasure domain and lists the authoritative object store to prove it contains no files. Only `cold_gc_complete=true`, `cold_gc_pending_entries=0`, `bucket_prefix_absent=true`, and no error constitute the proof. If object storage is unavailable or still lists a file, the response remains incomplete and a later idempotent request retries the proof.
- **Backups.** A purged tenant may persist inside backups taken before the purge until those backups age out; restore replays whatever the manifest contains. Deleting old backup sets is part of completing an offboarding with erasure obligations.

## Cleaning S3

Cold data lives under the `storage.cold.root` prefix. Benchmark and test runs should use a date-stamped root so cleanup is one prefix delete with standard S3 tooling:

```bash
aws s3 rm "s3://my-ursula-bucket/ursula-test-20260518T000000Z" --recursive
```

There is no automatic retention policy. Application checkpoints and explicit stream-retention advances control which cold objects become eligible for GC. After a retention advance, each group's leader deletes the stream's cold objects that lie wholly below the retained offset (chunks and offloaded external payloads, in whole 64 MiB cold-index pages, so up to one page just below the retained offset can remain until retention moves past it) once a 5-minute grace has passed, so reads planned before the advance still complete; its cold-index cursor visits 16 streams per group per minute, so on groups with many streams collection can lag further. The grace restarts after a leader change. Retention is a storage-cost tool only: replica memory does not depend on it (see [Memory without retention](#memory-without-retention)).

## Backup and disaster recovery

`ursulactl` provides a verifiable whole-cluster backup and restore workflow:

```bash
# Create: one MessagePack snapshot object per raft group + manifest.json,
# into a local directory or s3://bucket/prefix.
ursulactl backup-create --config cluster.yaml --location s3://backups/ursula/2026-07-25

# Verify: manifest completeness, byte sizes, BLAKE3 checksums, and deep
# state-machine validation of every snapshot. Touches no cluster.
ursulactl backup-verify --location s3://backups/ursula/2026-07-25

# Restore: into a FRESH, EMPTY cluster with the same raft group count.
ursulactl restore --config new-cluster.yaml --location s3://backups/ursula/2026-07-25
```

The recovery contract:

- **Consistency boundary.** Each group export is the deterministic state-machine snapshot the raft snapshot path persists: internally consistent per group while writes continue. Cross-group consistency is not promised; the boundary is per stream. Acknowledged writes in the exporting replica's applied state are included whether or not they were cold-flushed, so **RPO is bounded by export time**, not by the cold-flush interval. `backup-create` asks every node and keeps the reply with the highest group commit index.
- **Fresh identity on restore.** Restore replays each snapshot as one replicated write on the target cluster, which keeps its own raft membership and log identity — nothing from the source cluster's raft metadata is reused. Groups that already hold buckets refuse the import with `409`; group-count mismatches fail closed before the first import. Group commit indexes and per-stream append counters restart under the new identity; stream bytes, offsets, close/TTL state, published snapshots, retention floors, and producer dedup states are preserved exactly.
- **Cold objects are part of the backup set.** Snapshots reference cold-tier chunks by object key; point the restored cluster at the same (or a copied) cold-store namespace. `backup-verify` validates snapshots but does not dereference cold objects.
- **Format compatibility.** The backup format is the format epoch (`format_version` 2 in the manifest and in `/__ursula/backup/info`). `ursulactl` refuses a manifest or a target cluster of another version before the first import, and a server refuses to import a group without format epoch 2 (`400`). Backups of Ursula 0.5.x cannot be restored into 0.6; see [Upgrading to 0.6](#upgrading-to-06).
- **RTO** is dominated by transferring and importing the group snapshots; each import is a single replicated write per group.

The recovery drill — write, snapshot, retain, close; back up; destroy the cluster; restore; verify checksums, offsets, and boundaries; continue appending — runs in CI (`backup_restore_drill_preserves_streams_and_allows_continued_appends`).

What you can additionally rely on:

- **Quorum durability.** Acknowledged writes survive as long as a majority of voters survives. Three voters across AZs tolerate any single-AZ outage.
- **Cold-tier durability.** Once flushed to S3, a chunk inherits S3-grade durability. The unflushed window is bounded by the flush interval (seconds by default).
- **Format epoch 2, no migration.** Everything Ursula 0.6 persists or sends
  between nodes carries format epoch 2: the Raft WAL, snapshots, the
  object-storage prefix, backups and the Raft gRPC protocol. A 0.6 node refuses
  data and peers written by Ursula 0.5.x (format epoch 1) and does not migrate
  them. See [Upgrading to 0.6](#upgrading-to-06).

Node-level loss: replace the host with the same `node_id` and cluster config, and it rehydrates from peers. Use `ursulactl wait-ready` afterwards to confirm the replacement is voting and caught up before declaring the recovery done. Total-cluster loss: restore the latest verified backup into a fresh cluster as above.

## Upgrading to 0.6

**0.6.0 is a breaking release.** It changes the storage format (format epoch 2) and removes several protocol features (listed in the release notes). It refuses to start on data written by 0.5.x (Raft WAL directories, object-storage prefixes, snapshots and backups) and will not join a cluster with 0.5.x nodes. There is no in-place upgrade, no automatic migration and no rollback.

- **If you run 0.5.x with data you need to keep, do not upgrade yet.** Stay on 0.5.1 and [open an issue](https://github.com/tonbo-io/ursula/issues) so we can work out a migration path with you.
- **New deployments install on fresh storage:** empty PVCs and a never-used object-storage prefix.
- **`helm upgrade` from 0.5.x stops at the first pod.** Recover with `helm rollback`.

The removed protocol features, and every behaviour change, are listed in the [0.6.0 release notes](/docs/release-notes#removed).

To install 0.6:

1. **Install fresh.** Install with a new `s3.prefix` and empty PVCs. With cold storage off and S3 snapshots, also use a new `snapshotStore.prefix`. With the event-time indexer, use a new or emptied `indexer.s3.prefix` and register the indexes again; the registration and query formats changed ([release notes](/docs/release-notes#event-time-indexer-experimental)).
2. **Reset SQLite VFS clients.** Stop every owner of a stream before upgrading the extension, then delete `<db>`, `<db>-wal` and `<db>-ursula` before attaching, or attach under a new stream URL.
3. **Never reuse a prefix** that an earlier release, or a failed upgrade attempt, wrote to.

`helm upgrade` from 0.5.x stalls at the first new pod, with the default `RollingUpdate` strategy and also with `OnDelete` plus the graceful rollout: the new pod exits at startup or reports not ready, so no second voter is replaced. Recover with `helm rollback`. The refused pod wrote nothing, so the old pods are unaffected.

How a 0.6 node refuses old data, and what it prints, is listed under [Startup failures](/docs/troubleshooting#startup-failures). Every startup refusal happens before the node writes anything:

- **Raft WAL directory.** `{raft.wal.path}/raft-log/FORMAT_EPOCH` records the epoch. A directory that holds data without the marker, or a marker of another epoch, is refused. The marker is written after every check passes.
- **Object storage.** `URSULA_FORMAT_EPOCH` sits at `storage.cold.root` when the cold backend is S3, otherwise at the S3 snapshot namespace (`storage.snapshot.s3_prefix`) when snapshots live on S3. A namespace that holds objects without the marker is refused, so it must be used only by this cluster. With a memory cold store and inline snapshots there is no object-storage check.
- **Peers.** Before it writes the markers, a node with configured peers asks each one, in parallel (2 seconds to connect plus 2 seconds for the answer, about 4 seconds at most), whether it speaks Raft protocol 2. A peer that refuses ends startup; an unreachable peer is skipped, because a fresh cluster starts its pods in parallel.
- **Readiness.** Any later Raft protocol mismatch, inbound or outbound, is logged at error level and makes `/__ursula/ready` answer `503` with `"reason": "format_epoch_mismatch"` until the node restarts.
- **Backups.** Backups use format version 2. `ursulactl backup-restore` and `backup-create` refuse a cluster that reports another version, and a server refuses to import a group without format epoch 2 (`400`).

Bucket IDs `snapshots` and any ID starting with `__` are reserved (`400`): `snapshots` is the default raft-snapshot namespace in the object store.

## Logs

`RUST_LOG=ursula=info,ursula_runtime=info,ursula_raft=info` is the baseline. Bump to `debug` for one crate when chasing a subsystem:

```bash
RUST_LOG=ursula_raft=debug ./target/release/ursula server ...
```

`debug` is verbose under sustained load, so redirect to a file.
