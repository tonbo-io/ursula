title: ursulactl
---

`ursulactl` manages the **logical** state of a running cluster over Ursula's admin and metrics HTTP APIs: which node leads which Raft groups, and whether a node is caught up. It executes nothing on hosts. Physical lifecycle belongs to whatever owns the process: Helm and the StatefulSet controller on Kubernetes, systemd on hosts, OpenTofu for the infrastructure underneath. The verbs encode the safety properties an operator otherwise has to remember manually:

- before a node goes down, transfer every Raft group it leads to a healthy successor (`drain`)
- after it comes back, refuse to move on until `last_applied_index` has caught up to peers' `committed_index` (`wait`)
- abort rather than corner a group with no leader

A safe rolling restart wraps the platform's restart in these verbs, one node at a time. On Kubernetes:

```bash
ursulactl drain --config manifest.json --node 3
kubectl delete pod ursula-2        # the platform restarts the pod
ursulactl wait --config manifest.json --node 3
ursulactl undrain --config manifest.json --node 3
ursulactl verify-cluster --config manifest.json
```

On bare metal the restart in the middle is `systemctl restart ursula` on the host. The drain planning and readiness logic is exercised under [deterministic simulation](/docs/architecture/overview).

<Warning>
The naive procedure of "restart followers, then leader" does **not** wait for `applied_index` to catch up between steps. A restarted voter that lost entries, for example after a host crash under `raft.wal.fsync = "never"` or with a replaced disk, stays out of elections until its group leader has rebuilt it. Always drain before restart and wait for catch-up before moving to the next voter.
</Warning>

## Verbs

| Verb | Effect |
|------|--------|
| `drain --node N` | Mark the node draining and transfer away every leadership it holds. The mark persists (the node attracts no leaderships) until `undrain`. `--dry-run` prints the transfer plan |
| `undrain --node N` | Clear the drain mark so the node may hold leaderships again |
| `wait --node N` | Block until the node is a voter in every group and within `--lag-tolerance` of peers. Progress-gated: a node that keeps advancing is never timed out |
| `pin-incarnations` | Save observed process identities in a manifest for subsequent commands; legacy opt-in stays uncertified |
| `status` | Per-node group counts and leadership distribution |
| `wait-ready` | Block until every node reports the expected group count and every group has a leader |
| `verify-cluster` | Require every configured voter to be present and caught up in two consecutive samples before the next rollout step |
| `verify-quorum` | Confirm every configured group with a fresh ReadIndex round and require every replica to apply its fixed prefix under the same leader term |
| `verify-survivors` | Confirm fresh prefixes on two observed survivors while preserving the three-voter configuration; does not certify full redundancy or physical fencing |
| `backup-create` | Export every Raft group into a backup at a local directory or `s3://bucket/prefix` |
| `backup-verify` | Check a backup's manifest, sizes, checksums and every group snapshot without contacting a cluster |
| `restore` | Restore a verified backup into a fresh, empty cluster with the same group count, once the cluster confirms it holds every cold object the backup references |

Mutating verbs exit `0` on success and `2` on an abort (drain timeout, no safe transfer target, catch-up stall). Anything else is a configuration or transport error with a single-line, machine-greppable message.

## Process identity across commands

Each CLI invocation pins the first observed server instance. A process change makes subsequent observations fail, and mutations retain the original `x-ursula-process-incarnation` header. To preserve the same plan across invocations:

```bash
ursulactl pin-incarnations --config cluster.json > pinned-cluster.json
ursulactl drain --config pinned-cluster.json --node 3
```

The saved nodes carry `expected_process_incarnation`. After an intentional process
replacement, `pin-incarnations --replace-node 3` binds only that replacement;
every survivor must still match its saved identity. Missing identities fail
closed. `verify-quorum` reports process identities separately from participation.

Meta Raft serializes maintenance operations and pins participant process epochs.
Use `operation` for replica movement, lost-volume rebuild, and decommission.
Ordinary restarts preserving the PVC claim a fresh process epoch directly.

## The admin plane

Nodes carry **no cluster-mutation surface on the network**. The mutating operator endpoints (raft snapshot/purge/membership/learners/leader-transfer, maintenance drain, cold-flush trigger, bucket purge) plus metrics and usage are served on a separate **admin plane** bound to `server.admin_listen`, which defaults to loopback (`127.0.0.1:4438`). The public client plane (`:4437`) serves only stream traffic and read-only metrics and usage.

Metrics use an explicit `metrics_url` when configured, then `http_url`, then `admin_url`. Set `metrics_url` to a Pod-bound admin tunnel to inspect a replacement before cluster DNS becomes reachable. Mutating verbs always use `admin_url`; learner attachment and Raft handoff retain the advertised `http_url`.

ursulactl is a plain HTTP client and opens no tunnels itself. When the admin plane is not directly reachable, bring your own forward and point the manifest's `admin_url` at it. On Kubernetes, `kubectl port-forward` reaches the loopback-bound plane inside each pod:

```bash
kubectl port-forward pod/ursula-0 5441:4438 &
kubectl port-forward pod/ursula-1 5442:4438 &
kubectl port-forward pod/ursula-2 5443:4438 &
```

```toml
[[nodes]]
id = 1
admin_url = "http://127.0.0.1:5441"

[[nodes]]
id = 2
admin_url = "http://127.0.0.1:5442"

[[nodes]]
id = 3
admin_url = "http://127.0.0.1:5443"
```

On bare metal the same shape works with `ssh -N -L 5441:127.0.0.1:4438 admin@node1` per node.

## When to use ursulactl vs. the other surfaces

| Task | Tool |
|------|------|
| Day-2 logical operations: drain, observe, gate on readiness | **`ursulactl`** |
| Deployment, restarts, upgrades, topology | [Helm and OpenTofu](/docs/deploy-cluster) (systemd on bare metal) |
| Custom operator tooling | The admin-plane HTTP endpoints, reached over your own tunnel |

## Install

Build from the workspace alongside the server:

```bash
cargo build --release -p ursula-ctl --bin ursulactl
```

The binary lands at `target/release/ursulactl`. Drop it on your control machine. It does not need to run on the Ursula hosts themselves.

## Manifest format

Every verb accepts `--config <path>`. The manifest is **TOML, JSON, or YAML** (chosen by file extension, sniffed when read from stdin with `-`) and lists the cluster's nodes.

Prefer generating the manifest from whatever already knows the topology instead of writing it by hand. On Kubernetes the Helm chart renders one into its ConfigMap, and the URLs in it are in-cluster DNS, so pipe it to ursulactl running where those names resolve (the server image contains ursulactl):

```bash
kubectl get configmap ursula -o jsonpath='{.data.cluster-manifest\.json}' \
  | ursulactl status --config -
```

For infrastructure provisioned by OpenTofu, emit the manifest as a stack output or generated file (the same pattern as `deploy/eks`'s `generated-values.yaml`) rather than teaching ursulactl to read state files. `tofu output -json <name> | ursulactl status --config -` composes the same way.

Per-node fields, all optional except `id`:

- `admin_port` (default `4438`) or an explicit `admin_url`: the admin plane to reach, directly or through your forward.
- `host`: address shown in reports. Falls back to the admin URL's host.
- `http_url`: advertised client/Raft URL used for learner attachment and survivor handoff, and for metrics when no explicit `metrics_url` is set.
- `metrics_url`: optional metrics endpoint, for example the same tunnel as `admin_url`; it overrides metrics access without changing the peer address persisted in membership.

## Restarting a voter that lost its log

A voter that shut down cleanly comes back with every entry it acknowledged and only catches up on what it missed. A voter that lost entries (a host crash under `raft.wal.fsync = "never"`, a journal I/O error, a wiped or replaced disk) needs no ursulactl verb either: it stays behind its recovery gate, and each group leader rebuilds it by itself, removing the voter, adding it back as a learner and promoting it after catch-up (see [Rejoining a wiped node](/docs/operations#rejoining-a-wiped-node)). Keep the node drained and run `wait` until every group has promoted it. A group whose majority lost entries at once waits for an operator instead (see [Recovering after a host crash](/docs/operations#recovering-after-a-host-crash)).

The rebuild of a voter that lost its disk installs snapshots for every group and can take 10+ minutes. `wait` is progress-gated, so no timeout tuning is needed: a rebuild that keeps advancing is never timed out, and `--stall-timeout-secs` (default 90) only aborts a node that stops making progress.

## `status`

Per-node summary of Raft group count and leadership distribution, sourced from every node's `/__ursula/metrics`. Nodes whose metrics fail are reported with `metrics unavailable — …` rather than aborting the report, because `status` is meant to surface partial cluster health.

```bash
ursulactl status --config cluster.json
```

Sample output:

```
node 1 (10.0.0.1): groups=4 leaders={1: 2, 2: 2}
node 2 (10.0.0.2): groups=4 leaders={1: 2, 2: 2}
node 3 (10.0.0.3): groups=4 leaders={1: 2, 2: 2}
```

`leaders={…}` is the count of groups each node is leading from this reporter's perspective. Healthy clusters report the same distribution from every node.

## `wait-ready`

Block until every node reports `--expected-groups` Raft groups, each with a leader. Useful in CI / scripts after a deploy or a config change.

```bash
ursulactl wait-ready --config cluster.json --expected-groups 4
```

Exits non-zero with a one-line reason if the timeout passes (`cluster not ready after 120s: node 3 has 1 group(s) without a leader`).

## Underlying HTTP surface

For custom tooling, every verb maps onto a small set of HTTP endpoints on each node:

| Verb | Endpoint |
|------|----------|
| `status`, `wait-ready`, `wait` | `GET /__ursula/metrics` |
| `drain` / `undrain` (maintenance guard) | `POST /__ursula/leadership-shed/maintenance`, `DELETE` to clear |
| `drain` (transfer step) | `POST /__ursula/raft/{raft_group_id}/leader/transfer/{node_id}` |
| `backup-create` | `GET /__ursula/backup/info`, `GET /__ursula/backup/group/{raft_group_id}` |
| `restore` | `GET /__ursula/backup/info`, `POST /__ursula/backup/group/{raft_group_id}/cold-check`, `POST /__ursula/backup/group/{raft_group_id}/import` |

The transfer endpoint returns a typed rejection: `409 Conflict` for a changed leader or a recovering target, `400` for an invalid target, `404` for an unregistered group, and `500` for a stopped Raft. Drain re-observes and re-plans the two `409` cases; other errors stop the operation.

## Backup and restore

`backup-create`, `backup-verify` and `restore` implement the backup workflow in [Backup and disaster recovery](/docs/operations#backup-and-disaster-recovery). A backup location is a local directory or `s3://bucket/prefix`.

```bash
ursulactl backup-create --config cluster.json --location s3://backups/ursula/2026-10-07
ursulactl backup-verify --location s3://backups/ursula/2026-10-07
ursulactl restore --config new-cluster.json --location s3://backups/ursula/2026-10-07
```

- `backup-create` writes one MessagePack snapshot per Raft group and `manifest.json`. It asks every node for each group and keeps the answer with the highest commit index. `--created-unix-ms` overrides the manifest timestamp.
- `backup-verify` checks that the manifest lists every group once, and each object's size, BLAKE3 checksum and snapshot. It reads only the backup.
- `restore` verifies the backup, refuses a target whose backup format or group count differs, and then asks the target to check every group's cold references against its cold store. Only when nothing is missing does it import the groups, one replicated write each. A target group that already holds data refuses the import. Restore into a fresh, empty cluster.

`backup-create` and `restore` take `--http-timeout-secs` (default `30`). The cold check looks up every object a group references, 32 at a time, in one request per group, so a group with tens of thousands of cold objects needs a longer timeout. An `s3://` location uses the AWS SDK credential chain and `AWS_REGION`. For MinIO or another S3-compatible store, also set `AWS_ENDPOINT_URL`.

The backup format is the format epoch, 3. `ursulactl` refuses a backup or a cluster of another format epoch.

Each command exits `0` on success and non-zero with an error that names the failed check. A refused `restore` imports nothing.

## `verify-quorum`

This source provides a bounded observation for recovery measurements and maintenance tooling. Supply the deployed group count explicitly; the example below uses 256 groups:

```bash
ursulactl verify-quorum --config cluster.json --expected-groups 256 --timeout-secs 120
```

The command requires each configured voter exactly once, every configured group on every voter, complete uniform membership, no learners, and eligible local participation reports. It confirms each group's leader through a new outbound ReadIndex probe, then waits for all replicas to apply the captured prefix under that leader's term. Continuous writes can advance without moving this target. One absolute deadline covers metrics requests, RPCs and waits. The JSON output includes the observation start/end times, each group's leader/term/prefix and every replica's applied index.

The prefix is confirmed through the incarnation-bound admin route
`GET /__ursula/raft/{group}/quorum`. The CLI uses shared admin protocol types
and has no dependency on `ursula-raft`. Quorum proof and self-election requests
require process identity; servers without the admin protocol are unsupported.

A successful observation is not a maintenance reservation, a continuously refreshed health claim or physical fencing permission. Independent maintenance workflows still need to serialize disruptions and bind replacement to the actual Pod/process/host incarnation.

## `verify-survivors`

After one voter becomes unavailable, this source can separately observe the two survivors. Keep all three voters in the manifest and explicitly exclude exactly one known node:

```bash
ursulactl verify-survivors --config cluster.json --excluded-node-id 3 --expected-groups 256 --timeout-secs 120
```

Every group must still have the complete uniform three-voter membership, no learners and open participation gates on both observed replicas. Both survivors must agree on a reachable leader and apply each newly confirmed fixed prefix. The command rejects a second missing replica, an unknown exclusion or a changed topology; it never shrinks the configured membership to fit observations. Missing safety fields fail closed.

The output is scoped as `surviving_quorum`, records the configured and observed voter sets, and always reports `full_redundancy_restored=false`. Excluding a voter from observation does not prove its old process or host is stopped. Hard fencing and an exclusive maintenance reservation remain prerequisites for physical replacement, and the complete `verify-quorum` check is required before any subsequent disruption.

## `operation`

Submit typed maintenance intent to the meta-Raft authority through a pinned admin endpoint:

```bash
ursulactl operation --config cluster.json --node-id 1 --request intent.json
```

The request file uses the shared `OperationRequest` schema. `Begin` selects
`MoveReplicas`, `RebuildReplica`, or `DecommissionNode`; subsequent requests
carry the returned operation token. The server collects quorum/apply evidence
from the committed peer inventory. Kubernetes only performs the requested
physical lifecycle step after the relevant retirement response.

An ordinary restart preserving its PVC needs no rebuild operation. Drain and
restart one voter at a time, then require maintenance readiness before the next
restart. The former ConfigMap reservation and provider-specific startup commands
have been removed. See `docs/architecture/meta-control-plane.md` for operation
sequencing, failure recovery, and migration from a meta-disabled deployment.
