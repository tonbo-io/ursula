## Abstract

This document defines extensions to the [Durable Streams Protocol](/docs/specs/durable-stream). It adds bucket namespacing, optional path affinity, snapshot and bootstrap semantics, multipart bootstrap delivery, mutable stream attributes, Ursula-specific append batching for high-throughput small-event writes, stable record coordinates for JSON streams, a JSON message text rule, and keyed streams: a writer-declared keyed record format with a keyed-state read resource.

The snapshot and bootstrap design in sections 2 and 3 was proposed by [Loro](https://loro.dev/); Ursula adopts that design.

All base protocol semantics remain in effect. Where this document is silent, the base protocol governs.

## Terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174].

## Extension Capability Advertisement

`Stream-Extensions` is a response header for advertising protocol extensions that are active for the target stream. Its value is a comma-separated list of extension tokens registered by the specifications that define them. A server MUST advertise only tokens whose extension semantics apply to the target stream; server-wide support for an extension is not sufficient. An extension specification defines its token and the responses on which an active implementation MUST advertise it.

Clients MUST ignore unrecognized extension tokens. A client that depends on an extension MUST verify its token before relying on extension-specific request parameters, response headers, or body semantics.

This document registers the following extension tokens:

| Token | Defined in | Active for |
|---|---|---|
| `path-affinity-v1` | Section 1.7 | streams addressed through the affinity form |
| `group-append-transaction-v1` | Section 1.8 | `$transaction` responses |
| `json-record-coordinates-v1` | Section 6 | `application/json` streams, including keyed streams |
| `keyed-batch-v1` | Section 9.1 | keyed streams |
| `keyed-state-v1` | Section 9.2 | keyed streams on which the server serves the keyed-state resource |

[JSON Message Text](#json-message-text) has no token: it applies to every `application/json` stream.

## JSON Message Text

This section defines the "normalized message" that the base protocol's JSON mode refers to. It is a storage rule, not an optional extension, and has no extension token. A server MUST apply it to every stream whose content type is `application/json` (with or without parameters, including keyed streams, Section 9).

It applies to every JSON write: the body of a creating `PUT`, the body of `POST`, each Append Batch frame (Section 4), and each `$transaction` operation whose content type is JSON (Section 1.8). It applies to every read representation: the default NDJSON view, the record envelope view (Section 6.8), SSE, and bootstrap parts (Section 3).

1. The server MUST validate each request body (each frame or operation payload, for Append Batch and `$transaction`) as JSON text per [RFC8259]. `\uXXXX` escapes that encode unpaired surrogates are valid.
2. After top-level array flattening, the server MUST store each message as the original text with insignificant whitespace removed, followed by one LF (U+000A). Insignificant whitespace is U+0020, U+0009, U+000A and U+000D outside string literals. The server MUST NOT reorder object members, drop or merge duplicate member names, or rewrite number or string literal text.
3. The nesting depth of a scalar is 0. The depth of an array or object is 1 plus the maximum depth of its elements or member values; an empty array or object has depth 1. A message whose depth exceeds 127 MUST be rejected with `400 Bad Request`. Depth is measured per message, after flattening, so a top-level array body may be one level deeper than its deepest message.
4. A body with invalid JSON or invalid UTF-8 MUST be rejected with `400 Bad Request`, and no message from that request is committed.
5. Every read representation MUST carry the stored message text unchanged. Where a representation embeds the message in a larger JSON document, such as the envelope `value` member, the embedded text MUST be the stored text.
6. Offsets, ETags and record coordinates (Section 6) refer to the stored text.

Messages stored before a server adopted this rule are not rewritten. Clients MUST NOT assume that numbers survive storage as any particular binary floating-point value: a literal such as `1.50e3` or `1e400` is stored and returned as written.

> **Compatibility note (informative).** Earlier Ursula releases re-serialized JSON messages: they sorted object members, kept only one of several duplicate members, rewrote numbers through a binary double, and rejected lone-surrogate escapes and numbers outside the double range. This rule removes these behaviors for new writes. The depth limit is unchanged for a bare message; a message inside an array body gains one level.

## 1. Buckets

Every stream belongs to a bucket. The stream URL takes the form `{base_url}/{bucket_id}/{stream_id}`.

### 1.1. Identifier Constraints

- `bucket_id`: MUST match `^[a-z0-9_-]{4,64}$`. Globally unique within the service.
- `stream_id`: Any UTF-8 string. MUST NOT exceed 122 bytes. MUST NOT contain `/`, `\0`, or `..`. On the bucketed `/` surface, the combined `{bucket_id}/{stream_id}` key MUST also not exceed 122 bytes.
- The literal local stream ID `streams` is reserved for the bucket listing endpoint `/{bucket_id}/streams`.

### 1.2. Create Bucket

```
PUT /{bucket_id}
```

Buckets MUST be created explicitly. `PUT /{bucket_id}/{stream_id}` MUST NOT implicitly create a bucket.

**Response Codes:**

- `201 Created`: Bucket created successfully.
- `400 Bad Request`: `bucket_id` is invalid.
- `409 Conflict`: Bucket already exists.

### 1.3. Get Bucket Metadata

```
GET /{bucket_id}
```

**Response Codes:**

- `200 OK`: Bucket exists. Returns a JSON object with at least `bucket_id` (string) and `streams` (integer, count of streams in the bucket).
- `400 Bad Request`: `bucket_id` is invalid.
- `404 Not Found`: Bucket does not exist.

### 1.4. List Bucket Streams

```
GET /{bucket_id}/streams?prefix={prefix}&after={cursor}&limit={n}
```

- `prefix` filters bucket-local stream IDs by prefix. When omitted, all bucket-local stream IDs are eligible.
- `after` is an exclusive cursor over bucket-local stream IDs.
- `limit` defaults to `1000` and must be in `1..=1000`.

The response body is:

```json
{
  "bucket_id": "agents",
  "prefix": "user-",
  "stream_count": 1,
  "streams": [
    {
      "stream_id": "user-1",
      "status": "Open",
      "content_type": "text/plain",
      "tail_offset": 42,
      "created_at_ms": 1735689600000,
      "last_write_at_ms": 1735689601000
    }
  ],
  "next_cursor": "user-1",
  "has_more": true
}
```

`streams` is sorted lexicographically by `stream_id`.

- `stream_id` is the bucket-local path of the stream: what follows `/{bucket_id}/` in its URL. For a stream addressed through the affinity form (Section 1.7) it is `{affinity_key}/{stream_id}`, so `prefix` and `after` also apply to that path.
- `prefix` echoes the request's prefix, and is the empty string when the request has none.
- `stream_count` is the number of entries in `streams` on this page, not the number of streams in the bucket.
- `has_more` is `true` when more matching streams sort after the last entry. `next_cursor` is then that entry's `stream_id`, to be passed as `after`; otherwise it is `null`.
- `status` is `Open` or `Closed`. `tail_offset` is the stream's tail as an integer byte offset. Streams whose TTL or expiry time has passed are not listed.

Each entry MUST include `stream_id`, `status`, `content_type`, `tail_offset` and `created_at_ms`. `last_write_at_ms` is OPTIONAL: a server that does not track the time of the last write MUST omit it rather than report a substitute value, and clients MUST tolerate its absence.

> **Note (informative).** Ursula omits `last_write_at_ms`. It assembles a page from every Raft group's local replica on the node that serves the request, so a stream created a moment earlier may be missing from a page served by a follower.

**Response Codes:**

- `200 OK`: Matching streams returned.
- `400 Bad Request`: `bucket_id` or query parameters are invalid.
- `404 Not Found`: Bucket does not exist.

### 1.5. Delete Bucket

```
DELETE /{bucket_id}
```

A bucket MUST be empty (zero streams) before deletion.

**Response Codes:**

- `204 No Content`: Bucket deleted.
- `400 Bad Request`: `bucket_id` is invalid.
- `404 Not Found`: Bucket does not exist.
- `409 Conflict`: Bucket is not empty.

### 1.6. Stream Operations

All stream operations defined in the base protocol apply under `{base_url}/{bucket_id}/{stream_id}`. When the bucket does not exist, the server MUST return `404 Not Found`.

### 1.7. Path Affinity

Path affinity is an optional routing extension for applications that need several independent streams to share one Ursula Raft group. Its extension token is `path-affinity-v1`.

The affinity form of a stream URL is:

```
{base_url}/{bucket_id}/{affinity_key}/{stream_id}
```

For example, `/workflow/run-42/journal` and `/workflow/run-42/queue` have the same affinity key and therefore route to the same Raft group. The ordinary two-segment form, such as `/workflow/run-42-journal`, has no affinity key and continues to hash the complete bucket and stream identity so unrelated streams are distributed across groups.

- `affinity_key` follows the same UTF-8 and path-safety constraints as `stream_id`.
- The complete `{bucket_id}/{affinity_key}/{stream_id}` identity MUST NOT exceed 122 bytes.
- Within one bucket, streams with the same `affinity_key` MUST route to the same Raft group.
- Streams with different affinity keys MAY still share a Raft group. Clients MUST NOT infer isolation, group IDs, or physical placement from different keys.
- Path affinity changes placement only. It does not by itself make separate HTTP operations atomic.
- `$transaction`, `append-batch`, `attrs`, `bootstrap`, `keyed-state`, `retention`, and `snapshot` are reserved local stream IDs under an affinity path because those names identify affinity-level operations or stream subresources on the two-segment form.

Responses for a stream addressed through the affinity form MUST advertise `path-affinity-v1` in `Stream-Extensions`. Responses for ordinary two-segment stream URLs MUST NOT advertise it merely because the server supports the extension.

### 1.8. Group-local Append Transaction

The `group-append-transaction-v1` extension atomically appends to existing streams that share one path affinity key:

```
POST /{bucket_id}/{affinity_key}/$transaction
Content-Type: application/json

{
  "operations": [
    {
      "stream": "journal",
      "content_type": "application/json",
      "payload_base64": "eyJ0eXBlIjoic3RlcF9jb21taXR0ZWQifQo=",
      "record_match": 44
    },
    {
      "stream": "queue",
      "content_type": "application/json",
      "payload_base64": "eyJ0eXBlIjoiYWNrIn0K",
      "record_match": 9
    }
  ]
}
```

The server MUST commit every operation in one Raft entry or commit none of them. A failed content-type check, producer check, sequence check, record precondition, quota check, closed-stream check, or missing-stream check MUST leave every targeted stream unchanged. The endpoint does not create streams, accept empty append payloads, or coordinate across affinity keys. The first version permits at most 64 operations and a 32 MiB request body.

Each operation accepts `stream`, `content_type`, `payload_base64`, and the optional fields `close_after`, `stream_seq`, `producer`, and `record_match`. `producer` uses the same `producer_id`, `producer_epoch`, and `producer_seq` fields as the producer extension. Payload bytes use standard padded base64 so the transaction envelope can carry arbitrary stream content without JSON reinterpretation.

An operation's `content_type` is normalized exactly as a `Content-Type` request header is before it is compared with the target stream's content type: the value is split at `;`, each part is trimmed of surrounding whitespace, empty parts are dropped, each part is ASCII-lowercased, and the parts are joined with `; `. A `content_type` of `Application/JSON` therefore matches an `application/json` stream. The decoded payload of an operation that targets a JSON stream is then subject to [JSON Message Text](#json-message-text), and, for a keyed stream, to Section 9.1.

The response is `200 OK` with a JSON array of append acknowledgements in request order. Any operation failure returns the normal Durable Streams error status for that failure, such as `412 Precondition Failed`, and no operation is visible. Responses MUST advertise both `path-affinity-v1` and `group-append-transaction-v1` in `Stream-Extensions`.

## 2. Snapshots

A snapshot is a materialized representation of a stream's content from offset `-1` (inclusive) to `snapshot_offset` (exclusive). Snapshots enable clients to skip full replay and resume from a compacted state.

### 2.1. Offset Conventions

- Offsets are opaque tokens as defined in the base protocol. Clients MUST use server-returned `Stream-Next-Offset` values.

Servers that expose snapshots and `/bootstrap` as message sequences MUST use one consistent retained-message boundary model across ordinary reads, snapshot-offset validation, and bootstrap responses. This extension does not require any particular binary framing format.

### 2.2. Publish Snapshot

```
PUT {stream_url}/snapshot/{snapshot_offset}
```

Creates a snapshot at the specified offset. The snapshot represents the materialized result of folding all updates in the range `[-1, snapshot_offset)`.

**Request Headers:**

- `Content-Type`: The content type of the snapshot blob. Servers MUST store this value and return it on subsequent reads. Defaults to `application/octet-stream`.
- `Stream-Snapshot-Match`: Optional digest of the currently visible snapshot. If supplied and it does not match, the server MUST reject the publish with `409 Conflict`.

**Response Codes:**

- `204 No Content`: Snapshot published successfully.
- `400 Bad Request`: `snapshot_offset` is invalid or not aligned to a committed message boundary.
- `404 Not Found`: Stream does not exist.
- `409 Conflict`: `snapshot_offset` exceeds the current tail, or the server cannot produce a consistent view at that offset.
- `410 Gone`: `snapshot_offset` is older than the current earliest retained offset.
- `413 Payload Too Large`: Snapshot exceeds the server's size limit.

> **Note (informative).** Ursula keeps snapshot bodies of up to 32 MiB in replicated state. With a cold backend and feature level 5, it stores bodies of at least its external-payload threshold (1 MiB by default) as cold-tier objects instead and accepts up to 1 GiB; only the reference is replicated, and the digest is the same as for an inline body.

**Idempotency:**

The server MUST return `Stream-Snapshot-Digest` for a successful publish. Repeating a publish at the same offset with the same content type and body MUST succeed and return the same digest. Publishing different content at an already-published offset MUST return `409 Conflict`.

**Retention Effect:**

Publishing a snapshot MUST NOT change the earliest retained offset. Retention is a separate, explicit operation:

```
PUT {stream_url}/retention/{retained_offset}
```

The server MUST reject a retention boundary that is not aligned to committed data, moves backward, or is newer than the latest published snapshot. After success, offsets less than `retained_offset` MUST return `410 Gone`. A server MAY retain less than requested, at a committed boundary at or below `retained_offset` (Ursula keeps exact boundaries for older history only once per MiB of log); the success response's `Stream-Retained-Offset` (and, for record-aware streams, `Stream-Record-First`) then reports the effective boundary, and offsets below it MUST return `410 Gone`.

For record-aware JSON streams, servers also expose:

```
PUT {stream_url}/snapshot?record={record}
PUT {stream_url}/retention?record={record}
```

The server resolves the stable record ordinal to the canonical byte boundary before applying the operation.

Publishing a new snapshot replaces the previously visible snapshot immediately. The superseded snapshot MAY be garbage-collected asynchronously after the new snapshot becomes visible. Clients MUST NOT depend on older snapshots remaining readable after overwrite.

**Concurrency:**

Snapshot creation MUST NOT block concurrent appends. The snapshot's consistency boundary is `snapshot_offset`. Updates at or beyond that offset MUST NOT be folded into the snapshot.

### 2.3. Read Latest Snapshot

```
GET {stream_url}/snapshot
```

Returns a redirect to the latest visible snapshot resource, if one exists.

**Response:**

- `307 Temporary Redirect` when a latest snapshot exists. The `Location` header points to `{stream_url}/snapshot/{snapshot_offset}`.
- `404 Not Found` when no snapshot exists.

### 2.4. Snapshot Metadata on HEAD

```
HEAD {stream_url}
```

Servers SHOULD include `Stream-Snapshot-Offset` when a latest visible snapshot exists for the stream.

**Response Headers:**

- `Stream-Snapshot-Offset`: The latest visible snapshot offset.
- `Stream-Snapshot-Digest`: A digest of the latest visible snapshot's content type and body.

**Semantics:**

- Absence of `Stream-Snapshot-Offset` means the stream has no visible snapshot.
- When present, the value MUST refer to the same latest visible snapshot that `GET {stream_url}/snapshot` would resolve to.

### 2.5. Read Snapshot

```
GET {stream_url}/snapshot/{snapshot_offset}
```

Returns the snapshot blob at the specified offset.

**Response Headers:**

- `Content-Type`: The content type stored at publish time.
- `Stream-Snapshot-Offset`: The snapshot offset.
- `Stream-Snapshot-Digest`: The snapshot digest returned at publish time.
- `Stream-Next-Offset`: The next offset after the snapshot.
- `Stream-Up-To-Date`: Boolean indicating whether the stream has updates beyond the snapshot.

**Response Codes:**

- `200 OK`: Snapshot exists.
- `404 Not Found`: Snapshot does not exist or has been garbage-collected.

### 2.6. Delete Snapshot

```
DELETE {stream_url}/snapshot/{snapshot_offset}
```

Deletes the snapshot identified by `snapshot_offset`, subject to bootstrap safety rules.

**Response Codes:**

- `404 Not Found`: Snapshot does not exist or has been superseded.
- `409 Conflict`: `snapshot_offset` refers to the latest visible snapshot and cannot be deleted because `/bootstrap` would become incomplete.

Implementations that expose only one visible snapshot MAY make superseded snapshots unreachable immediately after overwrite. In that case, deleting an older offset will return `404 Not Found`.

## 3. Bootstrap

Bootstrap provides single-request initialization: a snapshot (if any) plus retained updates after the snapshot point, returned as a single ordered response that preserves per-message content types. A server returns either every retained update after the snapshot point, or a contiguous prefix of them and an honest continuation offset from which the client reads the rest through ordinary reads (Section 3.3).

### 3.1. Request

```
GET {stream_url}/bootstrap
```

**Query Parameters:**

- `/bootstrap` is a one-shot initialization endpoint. It does not define any query parameters of its own.
- Servers SHOULD reject any `live` query parameter on `/bootstrap` with `400 Bad Request`.

### 3.2. Response

**Response Headers:**

- `Content-Type: multipart/mixed; boundary=<token>`
- `Stream-Snapshot-Offset`: The snapshot offset, or `-1` if no snapshot exists.
- `Stream-Next-Offset`: The offset immediately after the last returned update message. When the response contains no update parts, it is the snapshot point (defined below).
- `Stream-Up-To-Date: true`: Present when `Stream-Next-Offset` equals the stream's tail offset at the time the response was produced. Otherwise the server MUST either omit the header, as for ordinary reads in the base protocol, or send `false`. Clients MUST treat an absent header as `false`.

The **snapshot point** `S` is the visible snapshot's offset when a snapshot exists, and otherwise the offset of the earliest retained message.

**Completeness:**

A server MUST return one of the following:

- **Complete:** one update part for every retained message in `[S, tail)`, with `Stream-Next-Offset` equal to the tail and `Stream-Up-To-Date: true`.
- **Partial:** one update part for every retained message in `[S, P)` for some boundary `P` with `S ≤ P < tail`, with `Stream-Next-Offset: P` and no `Stream-Up-To-Date: true`. `P` MAY equal `S`, in which case the response contains the snapshot part and no update parts.

In both cases the update parts MUST be the retained messages starting exactly at `S`, contiguous and in stream order: a server MUST NOT skip any message between `S` and `Stream-Next-Offset`, MUST NOT duplicate a message, and MUST NOT place more than one message in a part. `Stream-Next-Offset` MUST be a committed message boundary that ordinary reads accept, and MUST NOT be below `S`.

A server MAY choose the partial form for any reason, for example because some messages after `S` are held only in a storage tier that does not keep per-message boundaries in memory. Serving `/bootstrap` never requires a server to read such a tier. A client MUST NOT treat a partial response as an error.

> **Note (informative).** Ursula returns the complete form when every message in `[S, tail)` is above the stream's cold frontier, and otherwise the partial form with `P = S` (the snapshot part only). It never reads cold storage for update parts while serving `/bootstrap` (a snapshot body stored in the cold tier is streamed from it as the first part), and it omits `Stream-Up-To-Date` from a partial response. It also caps the update parts of one response at 8 MiB: when the updates exceed the cap it returns the partial form with `P` at the last message boundary that keeps the parts within the cap, and always includes at least one message, even when that message alone exceeds the cap.

**Response Body:**

The body is an RFC 2046 `multipart/mixed` entity. Each MIME part is one logical bootstrap message. The multipart boundary, not any outer binary framing, defines the bootstrap message boundaries.

1. **First part**: Snapshot message. If a snapshot exists, the part body MUST be the raw snapshot bytes and the part `Content-Type` MUST equal the snapshot blob's stored content type.
2. **Subsequent parts**: Zero or more retained updates starting at the snapshot point, one update message per part, as required by the completeness rules above. Each part body MUST be exactly one retained update message, and the part `Content-Type` MUST be the content type of that update. For streams with a fixed stream-level content type, all update parts will normally share that value.

If no snapshot exists, the server MUST still emit an empty first part, `Stream-Snapshot-Offset` MUST be `-1`, and that empty part's `Content-Type` MUST be `application/octet-stream`. Update parts, if any, then begin at the earliest retained offset.

Servers MUST NOT wrap the entire bootstrap response in an outer binary framing container. Each update part contains exactly one retained update message from the stream. Implementations MUST preserve the same retained-message boundaries they use for ordinary reads and snapshot-offset validation, and they MUST NOT reinterpret or reframe binary payloads when constructing bootstrap parts.

**Example:**

```http
HTTP/1.1 200 OK
Content-Type: multipart/mixed; boundary=rr-bootstrap-9f1c2e7a
Stream-Snapshot-Offset: 0000000000000012
Stream-Next-Offset: 0000000000000026
Stream-Up-To-Date: true
Cache-Control: no-store

--rr-bootstrap-9f1c2e7a
Content-Type: application/octet-stream

<snapshot-bytes>
--rr-bootstrap-9f1c2e7a
Content-Type: application/json

{"op":"set","path":["title"],"value":"hello"}
--rr-bootstrap-9f1c2e7a
Content-Type: application/json

{"op":"insert","path":["body",0],"value":"world"}
--rr-bootstrap-9f1c2e7a--
```

A partial response that returns only the snapshot. The client continues with `GET {stream_url}?offset=0000000000000012`:

```http
HTTP/1.1 200 OK
Content-Type: multipart/mixed; boundary=rr-bootstrap-4b7d01c3
Stream-Snapshot-Offset: 0000000000000012
Stream-Next-Offset: 0000000000000012
Cache-Control: no-store

--rr-bootstrap-4b7d01c3
Content-Type: application/octet-stream

<snapshot-bytes>
--rr-bootstrap-4b7d01c3--
```

**Response Codes:**

- `200 OK`: Bootstrap data returned.
- `404 Not Found`: Stream does not exist.

### 3.3. Follow-Up Live Reads

Bootstrap is one-shot only:

- `/bootstrap` returns an ordered initialization payload once.
- `/bootstrap` does not support `live=sse` or `live=long-poll`.
- After applying the bootstrap response, clients MUST continue tailing through the ordinary stream read APIs using the returned `Stream-Next-Offset`.
- When the response does not carry `Stream-Up-To-Date: true`, the ordinary catch-up reads from `Stream-Next-Offset` return the remaining updates; clients MUST apply them before treating their state as current.
- Clients SHOULD prefer `GET {stream_url}?offset=<offset>&live=sse` and fall back to `GET {stream_url}?offset=<offset>&live=long-poll` when SSE is unavailable.

### 3.4. Compatibility

- Regular `GET {stream_url}?offset=...` MUST NOT return snapshot bytes. Snapshots are only delivered through `/bootstrap`.
- When a server returns `410 Gone` for a read (because retention has advanced), clients SHOULD call `/bootstrap` to rebuild state, then continue tailing from the returned `Stream-Next-Offset` through the ordinary read APIs.
- If a server has begun returning `410 Gone` for a stream (i.e., earliest retained offset > `-1`), the server MUST ensure `/bootstrap` is available and can provide a snapshot covering that earliest retained offset.
- Clients MUST parse `/bootstrap` as an ordered message sequence. Message boundaries come from MIME parts.

## 4. Append Batch

Append Batch is an Ursula-specific implementation extension. It is not part of the base Durable Streams Protocol and clients MUST NOT assume it exists on other Durable Streams servers.

The extension reduces HTTP request overhead for workloads that append many small independent records. It is a transport batching mechanism only: each frame in the request is committed as an independent logical append with its own acknowledgement. Servers MUST NOT concatenate the frames into one stream record.

### 4.1. Request

Bucketed Ursula route:

```
POST /{bucket_id}/{stream_id}/append-batch
```

The request `Content-Type` applies to every frame and MUST match the stream's configured content type.

The request body is a sequence of binary frames:

```
uint32_be payload_len
payload bytes
uint32_be payload_len
payload bytes
...
```

`payload_len` is a 32-bit unsigned integer encoded in network byte order. It is the number of payload bytes that immediately follow. Zero-length frames are invalid.

Ursula currently accepts at most 512 frames per public append-batch request and a 32 MiB total body. Servers MAY reject larger batches with `413 Payload Too Large`.

### 4.2. Unsupported Per-Append Controls

The current Ursula append-batch endpoint does not support controls that require per-frame headers:

- `Stream-Closed`
- `Producer-Id`, `Producer-Epoch`, `Producer-Seq`
- `Stream-Record-Match`
- `Stream-Seq`

Clients that need producer fencing, idempotent producer sequence checks, stream preconditions, or atomic stream close MUST use the standard `POST {stream_url}` append operation.

### 4.3. Response

On a syntactically valid batch request, the response is `200 OK` with a JSON array. The array order matches the request frame order. Each element acknowledges one logical append:

```json
[
  { "status": 204, "stream_next_offset": 3 },
  { "status": 204, "stream_next_offset": 6 }
]
```

Acknowledgement fields:

- `status`: HTTP status code for the frame-level logical append.
- `stream_next_offset`: Present when the frame append succeeds or when an error can report the stream tail.
- `stream_closed`: Present and `true` if the append observes a closed stream.
- `error_code`: Present for failed frame-level appends.
- `error`: Human-readable failure detail for failed frame-level appends.

Malformed framing, missing `Content-Type`, unsupported headers, or an oversized request MAY fail the entire HTTP request with `400 Bad Request` or `413 Payload Too Large`.

Frame-level failures are reported inside the JSON array. A successful outer `200 OK` does not mean every frame committed. Clients MUST inspect every acknowledgement.

### 4.4. Ordering and Compatibility

Frames are submitted in request order and response acknowledgements preserve that order. For a single stream, successful frames advance the same stream offsets that standard `POST {stream_url}` would have produced.

All standard stream read APIs remain unchanged. Data appended through Append Batch is read through ordinary `GET`, long-poll, SSE, snapshot, and bootstrap paths using the same offsets and content type rules as standard appends.

## 5. Stream Attributes

Stream Attributes are an Ursula-specific metadata extension for mutable, application-owned stream attributes. They are separate from the base protocol's stream metadata returned by `HEAD {stream_url}`.

Attributes are not part of the append-only byte stream. Updating attributes MUST NOT change stream offsets, `ETag`, content type, closed state, snapshots, bootstrap payloads, or ordinary read results.

### 5.1. Attribute Object

The attribute document is a JSON object with the following optional fields:

```json
{
  "title": "Support session",
  "metadata": {
    "purpose": "customer-support",
    "environment_id": "env_019e2590d33f711fabf42f2857cecd8a",
    "agent": {
      "id": "agent_019e390add9f7bac9b6cc806db46fcbd",
      "version": 2
    }
  }
}
```

Fields:

- `title`: Optional string. Interpreted by the application.
- `metadata`: Optional JSON object for arbitrary application metadata.

Ursula does not define first-class semantics for application concepts such as agents or environments. If an application wants to associate such information with a stream, it SHOULD store that information inside `metadata`.

Unknown top-level fields are ignored: servers MUST accept attribute objects containing unrecognized top-level fields and MUST NOT store them. Clients that need additional fields MUST place them inside `metadata`.

The encoded attribute object MUST NOT exceed 16 KiB. Servers MUST reject larger attribute documents with `400 Bad Request`. Attributes are replicated with stream state, so the limit keeps log entries and snapshots small.

An empty attribute object (`{}`) is equivalent to no attributes.

### 5.2. Create Stream With Attributes

Attributes MAY be supplied when creating a stream:

```http
PUT {stream_url}
Stream-Attrs: {"title":"Support session","metadata":{"purpose":"customer-support"}}
```

`Stream-Attrs` is an optional request header whose value is the JSON attribute object.

When a stream already exists, the create request is idempotent only if the existing stream attributes match the supplied attributes after empty-object normalization. A mismatch MUST return `409 Conflict`, the same as other create-configuration mismatches.

### 5.3. Read Attributes

```http
GET {stream_url}/attrs
```

**Response:**

- `200 OK`: Returns the current attribute object as `application/json`.
- `404 Not Found`: The stream does not exist or has expired.

When no attributes are set, the response body is `{}`.

### 5.4. Replace Attributes

```http
PUT {stream_url}/attrs
Content-Type: application/json

{"title":"Renamed session","metadata":{"purpose":"debugging"}}
```

The request body replaces the complete attribute object. Partial merge semantics are not defined by this extension.

**Response Codes:**

- `204 No Content`: Attributes were replaced, or the submitted object already matched the stored attributes.
- `400 Bad Request`: The request is missing `Content-Type`, the content type is not `application/json`, the body is not a valid attribute JSON object, or the attribute object exceeds the size limit.
- `404 Not Found`: The stream does not exist or has expired.

Submitting `{}` clears the stream attributes. Attributes MAY be updated after a stream is closed because stream closure only forbids further appends.

## 6. JSON Record Coordinates

The JSON Record Coordinates extension adds a stable logical message coordinate to streams configured with `Content-Type: application/json`. It is a pure superset of the base protocol: offsets remain the canonical exact-resume cursor, ordinary offset reads remain byte-oriented, and clients that do not understand record coordinates continue to operate unchanged.

This extension registers the token `json-record-coordinates-v1`. It is active only for an `application/json` stream for which the server maintains the record model defined below. Responses to `HEAD` and stream operations targeting such a stream MUST advertise this token in `Stream-Extensions`. A server MUST NOT advertise this token for a stream on which the extension is inactive, including a stream with a non-JSON content type.

Record-aware clients MUST verify this token before relying on record query parameters or response headers and MUST reject a record-aware response that omits it.

### 6.1. Record Model

Each logical JSON message has a zero-based unsigned integer record ordinal. Ordinals are assigned consecutively in committed stream order and are scoped to one stream.

For one stream:

- `F` is the first retained record ordinal.
- `N` is the next record ordinal and record tail.
- Retained records occupy `[F, N)`.
- `O(r)` is the canonical Durable Streams offset at the first byte of record `r`.

A new empty stream has `F = N = 0`. An ordinal MUST NOT be reused or changed after it becomes externally visible. Retention MAY advance `F`, but MUST NOT renumber surviving records.

Record ordinals are independent from offsets, `Stream-Seq`, idempotent-producer sequence numbers, and sequence fields inside application JSON values. Clients MAY perform arithmetic on ordinals, but MUST continue to treat offsets as opaque tokens.

The JSON-mode normalization rules in the base protocol, made precise by [JSON Message Text](#json-message-text), define the records:

- A non-array JSON value creates one record.
- A top-level JSON array creates one record per array element after exactly one level of flattening.
- An empty array creates no records on `PUT` and remains invalid on `POST`.

An implementation MUST preserve each normalized message boundary and its ordinal across hot storage, WAL, cold flush, compaction, snapshot, restart, and retention. Coalescing physical storage objects MUST NOT coalesce the logical record coordinate space.

### 6.2. Client Event Time

This extension does not assign a server timestamp to records. Applications that need event time SHOULD include one client-supplied timestamp in each JSON value, for example a `captured_at` field in a telemetry event.

Client event times MAY be out of order and MUST NOT change committed record order, ordinals, canonical bytes, or offsets. Their HTTP metadata representation and any secondary index over them are outside this extension.

### 6.3. Create and Append Acknowledgements

When `PUT` creates a JSON stream with initial messages, or `POST` appends one or more JSON messages, successful responses MUST include:

- `Stream-Record-Start`: Inclusive ordinal of the first record created by this operation.
- `Stream-Record-Next`: Exclusive ordinal after the last record created by this operation.

For an operation that creates no records, `Stream-Record-Start` and `Stream-Record-Next` MUST both equal the current record tail.

All messages from one JSON request body MUST commit atomically and receive one contiguous ordinal range, or the operation MUST fail without making any ordinal visible. Concurrent appenders MUST receive disjoint ranges in committed stream order.

When an idempotent-producer retry is deduplicated, the server MUST return the original `Stream-Record-Start` and `Stream-Record-Next` values for a sequence whose receipt it retains: every sequence in the stream's receipt window, and always each producer's newest sequence. A server MAY bound the receipt window; Ursula keeps 1,024 receipt items per stream beyond each producer's newest receipt. A duplicate whose receipt the window evicted MUST still be deduplicated, never appended again, and is answered `204 No Content` with `Producer-Seq` and without `Stream-Next-Offset`, `Stream-Record-Start` or `Stream-Record-Next`. A server MUST NOT return a recomputed range.

For example, if the current record tail is `42`:

```http
POST {stream_url}
Content-Type: application/json

[
  {"type":"navigation_started"},
  {"type":"network_response","status":500}
]
```

The successful response includes:

```http
Stream-Extensions: json-record-coordinates-v1
Stream-Record-Start: 42
Stream-Record-Next: 44
Stream-Next-Offset: <opaque-offset>
```

### 6.4. Conditional Append by Record Tail

A writer MAY require the current record tail to match an expected value:

```http
Stream-Record-Match: 42
```

The server MUST accept the append only when the current `N` equals the supplied unsigned integer. A mismatch MUST return `412 Precondition Failed` with the current `Stream-Record-Next` and `Stream-Next-Offset`. This precondition composes with, but does not replace, `Stream-Seq` or idempotent-producer headers.

### 6.5. Record Metadata on HEAD

For a JSON stream implementing this extension, `HEAD {stream_url}` MUST include:

- `Stream-Record-First`: First retained record ordinal `F`.
- `Stream-Record-Next`: Next record ordinal `N`.

### 6.6. Record-Aware Read Parameters

A record-aware read selects its starting position with exactly one of:

- `record=<ordinal>`: Start at the specified record boundary.
- `record=now`: Start at the current record tail.
- `tail_records=<count>`: Start at `max(F, N - count)`.

These parameters are mutually exclusive with each other and with `offset`. `tail_records` MUST be a non-negative integer.

The following rules apply:

- `record < F` MUST return `410 Gone` with `Stream-Record-First` and `Stream-Record-Next`.
- `record = N` is a valid up-to-date empty read.
- `record > N` MUST return `400 Bad Request` with `Stream-Record-Next`.
- `tail_records=0` is equivalent to `record=now`.

Record-aware reads MAY also specify `max_records=<positive-integer>`. `max_records` limits the number of complete records returned. `max_records` without a record-aware start parameter MUST return `400 Bad Request`.

Record-aware reads MAY also specify `max_bytes=<positive-integer>`. On a record-aware read, `max_bytes` bounds complete records rather than bytes of a partial range:

- The response contains the longest run of complete records from the resolved start whose total size is at most `max_bytes`, and always at least one record when a record exists at the start, even if that record alone exceeds `max_bytes`.
- Size counts the stored message bytes (see [JSON Message Text](#json-message-text)), including each record's terminating LF, whatever representation the response uses. Envelope framing (Section 6.8) does not count.
- `max_bytes` MAY be combined with `max_records`; both limits apply, and the response stops at whichever is reached first.
- `Stream-Record-Next` and `Stream-Next-Offset` give the continuation after the last returned record. All other response headers are unchanged.
- A record-aware response never ends inside a record because of `max_bytes`.

Offset reads keep the base protocol's `max_bytes` semantics, including responses that end inside a JSON record.

A server that advertises `keyed-state-v1` (Section 9.2) for a stream MUST support `max_bytes` on that stream's record-aware reads. Other servers that implement this extension SHOULD support it; a client that has not verified support by that token MUST be prepared for an older server to reject the parameter with `400 Bad Request`.

### 6.7. Record-Aligned Read Responses

A successful record-aware catch-up or long-poll response MUST:

- begin at a complete record boundary;
- contain only complete normalized JSON messages;
- return `Content-Type: application/x-ndjson` by default;
- return at most `max_records` messages when supplied;
- include `Stream-Record-First`, `Stream-Record-Start`, `Stream-Record-Next`, and `Stream-Next-Offset`.

`Stream-Record-Start` is the resolved starting ordinal. `Stream-Record-Next` is the continuation ordinal after the last complete returned record. `Stream-Next-Offset` MUST identify the same logical boundary as `Stream-Record-Next`.

An empty successful response MUST set `Stream-Record-Start` and `Stream-Record-Next` to the resolved starting ordinal.

Example:

```http
HTTP/1.1 200 OK
Content-Type: application/x-ndjson
Stream-Extensions: json-record-coordinates-v1
Stream-Record-First: 0
Stream-Record-Start: 42
Stream-Record-Next: 44
Stream-Next-Offset: <opaque-offset>

{"type":"navigation_started"}
{"type":"network_response","status":500}
```

Ordinary `GET {stream_url}?offset=...` behavior is unchanged and MAY still end in the middle of a JSON record as defined by the base protocol.

### 6.8. Optional Record Envelope View

A record-aware client MAY request `record_view=envelope`. This parameter MUST be combined with a record-aware start parameter.

The response MUST use:

```http
Content-Type: application/vnd.durable-stream-records+ndjson
```

Each response line MUST be a JSON object containing:

- `record`: Record ordinal.
- `value`: The stored message text, embedded verbatim as defined by [JSON Message Text](#json-message-text). Servers MUST NOT re-serialize it, so member order, duplicate members, number and string literal text, and unpaired-surrogate escapes are preserved.

Example:

```json
{"record":42,"value":{"captured_at":"2026-07-18T10:29:59.900Z","type":"navigation_started"}}
{"record":43,"value":{"captured_at":"2026-07-18T10:30:00.100Z","type":"network_response","status":500}}
```

The envelope is an alternate read representation only. It MUST NOT change canonical stream bytes, offsets, record ordinals, ETags for the canonical representation, snapshots, bootstrap data, or ordinary reads.

### 6.9. Live Reads and SSE

Record start parameters compose with `live=long-poll` and `live=sse`.

SSE control events for record-aware reads MUST add:

```json
{
  "streamNextOffset": "<opaque-offset>",
  "streamFirstRecord": 0,
  "streamNextRecord": 44,
  "upToDate": true
}
```

For the default JSON view, SSE data events retain the base protocol's JSON-mode representation and MAY contain multiple newline-delimited messages. Control-event record coordinates MUST refer to the boundary after every complete message represented before that control event.

With `record_view=envelope`, each SSE `event: data` MUST contain exactly one envelope object and the response MUST include `Stream-Data-Content-Type: application/vnd.durable-stream-record+json`.

A reconnecting client MAY use either the last `streamNextRecord` or `streamNextOffset`. Offset-based reconnection remains the base-protocol path.

### 6.10. Retention, Snapshots, and Bootstrap

Retention MUST advance `F` only at a record boundary. A trimmed ordinal MUST return `410 Gone`; surviving records keep their original ordinals. When retention lands below its target (Section 2.2), `F` is the ordinal of the effective boundary; a retention or snapshot target at an intra-record offset MUST return `400 Bad Request`.

When a snapshot advances the earliest retained offset, that offset MUST map to one record boundary. Snapshot publication at an intra-record offset MUST return `400 Bad Request`. Snapshot and bootstrap responses SHOULD include `Stream-Record-First` and `Stream-Record-Next` when the underlying stream implements this extension. Bootstrap update parts MUST preserve one logical JSON message per update part.

Implementations MAY reclaim ordinal index entries only after the corresponding records fall before `F` and are no longer required by a visible snapshot or bootstrap response.

### 6.11. Append Batch Integration

For JSON streams implementing this extension, each successful Append Batch frame receives its own contiguous record range. Frame acknowledgements defined in Section 4.3 MUST additionally include:

- `stream_record_start`;
- `stream_record_next`.

One outer Append Batch request remains transport batching, not an atomic multi-frame transaction. A failed frame assigns no visible record ordinal; successful later frames continue from the last committed record tail.

### 6.12. Compatibility and Non-Goals

A base Durable Streams client continues to append JSON values or arrays, read by offset, and receive canonical NDJSON. It MAY ignore all `Stream-Record-*` and `Stream-Extensions` headers.

This extension does not define:

- schema validation or schema evolution;
- indexes over arbitrary JSON fields;
- SQL, Arrow, Parquet, or DataFusion integration;
- consumer groups;
- per-record arbitrary byte headers;
- authentication or authorization;
- a bidirectional append-session transport;
- record framing for arbitrary binary content types.

### 6.13. Correctness Requirements

Implementations MUST preserve these invariants:

1. Every successfully appended normalized JSON message receives exactly one ordinal.
2. Ordinals are contiguous in committed stream order and are never reused.
3. One atomic append receives one contiguous ordinal range or no range.
4. A deduplicated append returns its original ordinal range, or no range once its receipt left the receipt window.
5. `O(r)` always identifies the first canonical byte of record `r`.
6. Offset reads and record reads expose the same canonical JSON sequence.
7. Record-aware reads never return partial records.
8. Flush, compaction, snapshot, restart, and retention never change a surviving record's ordinal.
9. `N - F` equals the number of retained logical messages.
10. Base-protocol clients observe no semantic change.

Conformance tests SHOULD cover JSON array flattening, concurrent append ordering, idempotent retry, record-tail preconditions, partial offset reads, record-aligned reads, byte-bounded record reads, retention, snapshot/bootstrap boundaries, cold flush, restart, and live-read reconnection.

## 9. Keyed Streams

A keyed stream is a JSON stream whose messages are writer-declared batches of key-value mutations. The server validates each batch's grammar at append time, never runs application logic, and exposes the folded key-value state through a read resource. The log remains the source of truth: keyed state is a deterministic function of the stream's records and MAY be rebuilt from them at any time.

Keyed streams are an Ursula-specific extension. They register two tokens: `keyed-batch-v1` for the record format (Section 9.1) and `keyed-state-v1` for the read resource (Section 9.2).

### 9.1. Record Format and Fold

#### 9.1.1. Activation

A stream is a keyed stream if and only if its normalized content type equals exactly:

```
application/json; profile=keyed-batch-v1
```

Normalization is the rule of Section 1.8: split at `;`, trim each part, drop empty parts, ASCII-lowercase each part, and join with `; `. `Application/JSON;Profile=keyed-batch-v1` therefore activates the extension; a quoted `profile="keyed-batch-v1"` or any additional parameter does not. The content type is fixed at stream creation, so a stream cannot become keyed, or stop being keyed, after it is created.

> **Note (informative).** `application/json` defines no parameters [RFC8259], and a `profile` value is a URI in [RFC6906]. Using `profile=keyed-batch-v1` on `application/json` therefore deviates from [RFC6838] Section 4.3 and [RFC6906]. The deviation is deliberate: generic clients that select JSON mode by the `application/json` media type keep doing so on keyed streams, and a reader that does not understand the extension can still read a keyed log as ordinary JSON.

A keyed stream is an `application/json` stream for every other purpose. A server that implements keyed streams:

- MUST apply [JSON Message Text](#json-message-text) to every keyed stream;
- MUST implement JSON Record Coordinates (Section 6) on every keyed stream, so record ordinals, `Stream-Record-Match` and record-aware reads are available.

Every write that targets a keyed stream (the creating `PUT` body, `POST`, each Append Batch frame, and each `$transaction` operation) MUST carry a content type that normalizes to exactly the stream's content type. A mismatch MUST be rejected with `409 Conflict`, as for any other content-type mismatch.

#### 9.1.2. Grammar

After JSON Message Text flattening, every message written with the activation content type MUST match this grammar:

```
message = JSON object with exactly one member whose name, after unescaping, is "ops";
          other members: any JSON value, ignored by the fold and stored verbatim;
          the names of the message's own members MUST NOT contain escapes that
          encode unpaired surrogates (names inside values are unrestricted)
ops     = JSON array of zero or more op
op      = ["p", key, value]        ; put
        / ["d", key]               ; point delete
        / ["x", key, key]          ; range delete [start, end); start < end
key     = JSON string whose characters are exactly the canonical unpadded
          base64url encoding ([RFC4648] Section 5) of 1..4096 octets:
          no "=" padding, zero pad bits, and no backslash escapes
value   = any JSON value
```

- Op codes (`"p"`, `"d"`, `"x"`) and the member name `ops` are compared after JSON unescaping, so `"p"` is the op code `p` and a member named `"ops"` is the `ops` member. An object with two members that both unescape to `ops` does not match.
- Keys are checked on the raw characters between the quotes. A key that contains any backslash escape does not match, even if it unescapes to a canonical encoding.
- In a range delete, `start < end` compares the decoded octet strings in unsigned lexicographic order.
- A put of the literal `null` makes the key visible with value `null`. It is not a delete.
- An `ops` array MAY be empty. There is no limit on the number of ops in one message.

#### 9.1.3. Validation

The server MUST validate a write against Section 9.1.2 whenever the write's normalized content type equals the activation content type, before it looks up the target stream.

- The server MUST validate every message of a request before committing any of them. If any message fails, the server MUST respond `422 Unprocessable Content` and commit nothing from the request. For Append Batch this fails the whole request rather than one frame, as JSON syntax errors already do.
- The plain-text response body SHOULD read `invalid keyed batch at message <i>: <reason>`, where `<i>` is the zero-based message index after flattening. For Append Batch the body SHOULD read `invalid keyed batch at frame <f> message <i>: <reason>`.
- JSON syntax, UTF-8 and depth errors remain `400 Bad Request` under JSON Message Text.
- Precedence is `400` (JSON text), then `422` (grammar), then the apply-time statuses (`404`, `409`, `412`, and so on). An ungrammatical request sent with the activation content type to an absent or non-keyed stream is therefore answered `422`.

#### 9.1.4. Fold

Let `state(D)` be the key-value state after records `0 … D−1`. It is computed by applying the records in ordinal order, and the ops within each record in array order:

- A put `["p", k, v]` in record `r` sets `k → (r, v)`.
- A point delete `["d", k]` removes `k`.
- A range delete `["x", s, e]` removes every key `k` with `s ≤ k < e` in unsigned octet order.

A key is visible in `state(D)` when the last op that applies to it is a put. Its `record` is the ordinal of the record containing that put, and its value is that put's value text as stored under JSON Message Text. `state(0)` is empty.

The server MUST NOT derive keys or values that no op declares. Members of a message other than `ops` MUST be stored verbatim and MUST NOT affect the fold.

#### 9.1.5. Advertisement

Responses to `HEAD`, to the creating `PUT`, to appends (including Append Batch and `$transaction` responses that include a keyed stream), and to record-aware reads of a keyed stream MUST advertise `keyed-batch-v1` in `Stream-Extensions`, together with `json-record-coordinates-v1`. Responses for other streams MUST NOT advertise `keyed-batch-v1`.

A client that writes keyed batches SHOULD verify `keyed-batch-v1` on the create or `HEAD` response before its first append. A server that does not advertise it would store such messages under ordinary JSON rules without validating them.

#### 9.1.6. Limits

- Keys are 1..4096 octets after decoding.
- Message depth follows [JSON Message Text](#json-message-text): at most 127.
- The request body is bounded by the server's request limit. Ursula accepts at most 32 MiB and answers `413 Payload Too Large` above it.
- There is no limit on the number of ops per message.

#### 9.1.7. Snapshots, Retention, and Bootstrap

Snapshots, retention and `/bootstrap` keep their generic semantics on keyed streams; there are no keyed-specific rules.

Retention removes the records keyed state is built from. A server that maintains keyed state incrementally needs the record before its published frontier, and a rebuild needs every record from `0`. Once the first retained record ordinal `F` (Section 6.1) passes what the server needs, keyed state can no longer advance or be rebuilt, and the keyed-state resource answers `500 Internal Server Error` for any `min_through_record` above the state it holds (Section 9.2.6). Writers that rely on keyed state SHOULD NOT advance retention on keyed streams.

`/bootstrap` returns the batch log, not keyed state. Clients SHOULD read state through the keyed-state resource.

#### 9.1.8. Format Evolution

A change to the grammar or fold ships as a new profile and token, such as `keyed-batch-v2`, for new streams. A server that has advertised `keyed-batch-v1` MUST keep validating and folding `keyed-batch-v1` streams for as long as it serves them. Application-level schema versions belong inside the application's own keys and values.

#### 9.1.9. Example

```http
POST {stream_url}
Content-Type: application/json; profile=keyed-batch-v1
Stream-Record-Match: 103

{"o":17,"ops":[["p","AW5leHRfaWQA",130],["d","QQIAAAAAAAAAgA"],["x","VAAAAAAAAAAEAAAAAAAAAAA","VAAAAAAAAAAEAAAAAAAAAGc"]]}
```

The successful response includes:

```http
Stream-Extensions: json-record-coordinates-v1, keyed-batch-v1
Stream-Record-Start: 103
Stream-Record-Next: 104
Stream-Next-Offset: <opaque-offset>
```

The member `o` is ignored by the fold and stored verbatim.

### 9.2. Keyed-State Resource

The keyed-state resource serves `state(D)` (Section 9.1.4) of a keyed stream for some published `D`. Its extension token is `keyed-state-v1`.

#### 9.2.1. Request

```
GET {stream_url}/keyed-state?key={k}
GET {stream_url}/keyed-state?[start={k} | after={k}][&end={k}][&limit={n}]
```

Both forms accept `&min_through_record={r}` and `&timeout_ms={t}`. The resource exists for both the two-segment and the affinity form of a stream URL; `keyed-state` is a reserved local stream ID under an affinity path (Section 1.7).

Only `GET` is defined. Every other method, including `HEAD`, MUST be answered `405 Method Not Allowed` with `Allow: GET`. A server that does not serve keyed state for any stream MAY instead answer `404 Not Found` to every method.

Parameters:

- Every key parameter `k` is the canonical unpadded base64url encoding of 1..4096 octets, as in Section 9.1.2.
- `key=k` is a point read of one key. It MUST NOT be combined with `start`, `after`, `end` or `limit`.
- The range is `[lo, hi)` in unsigned octet order. `lo` is `start` (inclusive) or `after` (exclusive); the two are mutually exclusive, and the default is before the first key. `hi` is `end` (exclusive), and the default is after the last key. If `lo ≥ hi`, nothing is selected.
- `limit` is the maximum number of rows, an integer in `1..1000`. The default is `100`.
- `min_through_record=r` is a non-negative integer: the response MUST reflect `state(D)` with `D ≥ r` (Section 9.2.4).
- `timeout_ms=t` bounds the wait for `min_through_record`. The default is `1000`. An unparseable value means the default, and a parsed value is clamped to `1..60000`. It is ignored without `min_through_record`.
- A repeated parameter, a forbidden combination, an invalid key, an out-of-range `limit`, or an unparseable `min_through_record` MUST be rejected with `400 Bad Request`.
- Unrecognized parameters are ignored, as on the other read surfaces.

Request targets can be long: two 4096-octet keys produce a request target of about 11 KB. Deployments SHOULD accept request lines of at least 12 KiB on this resource.

#### 9.2.2. Response Body

On `200 OK` the body has the media type:

```
application/vnd.durable-stream-keyed-rows+ndjson
```

It contains one line per visible key in the selected range, in ascending unsigned octet order of the decoded keys. Each line is a JSON object with exactly the members `key`, `record` and `value`, in that order:

```json
{"key":"AW5leHRfaWQA","record":103,"value":130}
{"key":"AW93bmVyAA","record":42,"value":{"epoch":42,"nonce":"c0ffee00112233445566778899aabbcc"}}
```

- `key` is the key in canonical base64url.
- `record` is the ordinal of the record containing the last put applied to the key in `state(D)`. It is a function of `state(D)` alone, so internal compaction or a rebuild never changes it.
- `value` is the put's value text exactly as stored under [JSON Message Text](#json-message-text), embedded verbatim.

An empty selection, including a point read of a key that is not visible, is a `200 OK` with an empty body.

#### 9.2.3. Response Headers

- `Stream-Keyed-Through: D` MUST be present on every `200` and `204`. `D` is exclusive: the response reflects every record below `D` and none at or above it.
- `Cache-Control: no-store` MUST be present on every `200` and `204`.
- `Stream-Keyed-After: k` names the last returned key. It MUST be present when the server stopped before the end of the selected range, because of `limit` or the response budget, and MAY be present otherwise. Its absence means the range is exhausted. A client continues with `after=k` and the same `end`.
- `Stream-Extensions` MUST include `keyed-state-v1` on every response of this resource for a keyed stream, except `404`.

The response budget is 4 MiB of uncompressed body. The server MUST NOT add a row that would take the body past the budget, except that the first row of a response is always returned whole.

#### 9.2.4. Consistency

- Every `200` and `204` MUST reflect exactly one `state(D)`, with `D` at most the stream's record tail `N`. Rows of one response never mix states.
- For one stream incarnation, once a response has carried `Stream-Keyed-Through: D`, no later `200` or `204` carries a smaller `D`, unless the stream's log itself was rewound by an operator restore; `D` then restarts from the state rebuilt from the restored log.
- A deleted and recreated stream at the same URL is a new incarnation. Its keyed state MUST NOT be served from the old incarnation's state.
- With `min_through_record=r`, the server MUST respond with `D ≥ r`, waiting up to `timeout_ms` for keyed state to reach `r`. If `D < r` when the timeout elapses, it MUST respond `204 No Content` with `Stream-Keyed-Through: D`. Without `min_through_record`, any published `D` MAY be returned.
- A keyed stream for which no keyed state has been built yet is served as `state(0)`.
- Pagination is keyset-monotone: a client paging with `after` sees no key twice, but each page MAY reflect a different `D`, so rows changed between pages MAY be missed. A client that needs one consistent view across pages passes the highest `D` it has seen as `min_through_record` and reconciles by `D`.

A writer achieves read-your-writes for its record `s` by passing `min_through_record=s+1`.

#### 9.2.5. Waiting and Coalescing

The server MAY coalesce concurrent requests that wait on the same stream, and MAY space successive publications of keyed state by a minimum interval. Correctness MUST NOT depend on either. A request whose `min_through_record` is above the published `D` causes the server to make progress toward it; keyed state of a stream that nobody reads need not be maintained.

#### 9.2.6. Errors

- `400 Bad Request` for invalid parameters (Section 9.2.1).
- `404 Not Found` when the stream does not exist, is not a keyed stream, or the server does not serve keyed state for it.
- `400 Bad Request` with `Stream-Record-Next: N` when `min_through_record` exceeds the stream's record tail `N`.
- `500 Internal Server Error` with a plain-text reason naming a record ordinal when a permanent condition prevents producing `state(D)` for any `D ≥ r`: a source record that cannot be applied, an irreparable continuity break, or source records below the first retained ordinal (Section 9.1.7).
- `503 Service Unavailable` with `Retry-After` when the resource is temporarily unavailable, including transient failures to read the source log and keyed state that is ahead of its source log (`D > N`) while it is re-validated or rebuilt.

Precedence is the parameter `400`, then `404`, then the beyond-tail `400`, then `5xx`, then `204`. A `503` MAY precede `404` when the server cannot determine whether the stream exists.

#### 9.2.7. Advertisement

Responses to the creating `PUT` and to `HEAD {stream_url}` of a keyed stream MUST advertise `keyed-state-v1` when the server serves this resource for that stream, and MUST NOT advertise it otherwise. A server that advertises `keyed-state-v1` for a stream MUST also support `max_bytes` on that stream's record-aware reads (Section 6.6).

#### 9.2.8. Example

```http
GET {stream_url}/keyed-state?start=AQ&end=Ag&limit=2&min_through_record=104&timeout_ms=5000
```

```http
HTTP/1.1 200 OK
Content-Type: application/vnd.durable-stream-keyed-rows+ndjson
Stream-Extensions: keyed-state-v1
Stream-Keyed-Through: 104
Stream-Keyed-After: AW93bmVyAA
Cache-Control: no-store

{"key":"AW5leHRfaWQA","record":103,"value":130}
{"key":"AW93bmVyAA","record":42,"value":{"epoch":42,"nonce":"c0ffee00112233445566778899aabbcc"}}
```

The client continues with `after=AW93bmVyAA&end=Ag`.

### 9.3. Correctness Requirements

Implementations MUST preserve these invariants. Each is testable against a reference fold over the stream's records.

1. A message is committed to a keyed stream only if it matches Section 9.1.2. Every committed record of a keyed stream is grammatical.
2. A request with any ungrammatical message commits nothing and is answered `422`; a request with invalid JSON text is answered `400`; grammar validation precedes every apply-time status.
3. Stored record bytes equal the writer's text with insignificant whitespace removed, and every read surface (offset reads, record reads, envelope, SSE, bootstrap, and keyed-state `value`) returns those bytes.
4. Every `200` and `204` from the keyed-state resource reflects exactly one `state(D)` with `D ≤ N`, and its rows equal the reference fold `state(D)` restricted to the selected range, in ascending unsigned octet order.
5. A row's `record` is the ordinal of the record holding the key's last applied put in `state(D)`, and is unchanged by any internal compaction or rebuild.
6. A response to `min_through_record=r` either has `D ≥ r` or is `204` with `Stream-Keyed-Through` below `r`.
7. For one incarnation, served `D` never decreases, except after an operator restore of the log.
8. Keyed state is served only for the incarnation it was built from, and only while it is consistent with the source log's records below `D`.
9. A response stops before the end of the selected range only with `Stream-Keyed-After` naming its last row; paging with `after` until `Stream-Keyed-After` is absent visits every key of the range at most once.
10. No response exceeds `limit` rows, and no response exceeds the 4 MiB budget unless it contains exactly one row.
11. `HEAD` and every method other than `GET` on the resource return `405` with `Allow: GET`, unless the server serves keyed state for no stream (Section 9.2.1).
12. A keyed stream with no built state is served as `state(0)`.
13. Non-keyed streams are unaffected: they never advertise `keyed-batch-v1` or `keyed-state-v1`, and a `GET` of their keyed-state resource answers `404`.

Conformance tests SHOULD cover: escaped and duplicate `ops` members; unpaired-surrogate escapes in top-level member names (rejected) and in member names inside values (accepted); non-canonical keys (`AB`, `AA==`, `+/`, the empty string) and escaped keys; range deletes with `start ≥ end`; depth 127, 128 and 129, bare and inside an array body; `1e400`; `lo ≥ hi`; repeated parameters; `HEAD` and other methods; out-of-range and unparseable `timeout_ms`; wait timeouts; keyed state ahead of the source log; an invalid batch sent to a non-keyed or absent stream; `max_bytes` with `max_records` and with `record_view=envelope`; a stream with no built state; and deleting and recreating the same stream URL within one millisecond.

### 9.4. Tuple Layer (Informative)

The server treats keys as opaque octet strings. This appendix describes the order-preserving tuple encoding that Pi Durable's owner uses to build keys, so that prefix and range reads over the keyed-state resource return rows in a useful order. Other applications MAY use any encoding.

| Component | Encoding | Order |
|---|---|---|
| tag | 1 octet family tag | — |
| `u64(x)` | 8 octets, big-endian | ascending |
| `u64desc(x)` | 8 octets, big-endian, of `2^64−1−x` | descending |
| `u8(e)` | 1 octet enumeration value | — |
| `str(s)`, short form | WTF-8 of the JavaScript string (valid surrogate pairs become 4-octet UTF-8; a lone surrogate becomes `ED A0..BF xx`), with each `00` octet escaped as `00 FF`, followed by a `00` terminator. Used when the result is at most 1024 octets. | groups by string |
| `str(s)`, long form | `FE` followed by `SHA-256(WTF-8(s))`: 33 octets | exact match only |
| `strinc(p)` | strip trailing `FF` octets, then increment the last octet | prefix successor |

- A key is the concatenation of its components, encoded with base64url for the wire.
- `TextEncoder` is unsuitable for `str` because it replaces lone surrogates with U+FFFD, which would merge distinct strings.
- The short and long forms never collide: a short form never starts with `FE`, because its first octet is `00` or a WTF-8 lead octet at most `F4`.
- The code is not prefix-free. A short form is a prefix of the short forms of its NUL-extensions: `str("k")` = `6B 00` is a prefix of `str("k\u0000z")` = `6B 00 FF 7A 00`. A range `[p, strinc(p))` that ends in a `str()` component therefore also returns rows for every string that extends the target with U+0000. Readers that scan such a prefix need to compare the full string, which the application stores in the value or in a row the key points to, and skip mismatches.
- Long forms appear only where the application needs exact matches, never in positions that are scanned by prefix for ordering.
- The range of all keys with prefix `p` is `start=p&end=strinc(p)`.

Vectors:

| Tuple | Key (base64url) |
|---|---|
| tag `0x33`, `str("\ud800")`, `u64(5)` | `M-2ggAAAAAAAAAAABQ` |
| tag `0x33`, `str("\ud801")`, `u64(5)` | `M-2ggQAAAAAAAAAABQ` |
| tag `0x42`, `u64(1)`, `str("R" × 2000)` (long form) | `QgAAAAAAAAAB_qlzUi6syczOrf_AEPEPP8d5ztBpK79Sfr0W73LnIc4y` |
| tag `0x01`, `str("owner")` | `AW93bmVyAA` |

The first two vectors show that lone surrogates stay distinct.
