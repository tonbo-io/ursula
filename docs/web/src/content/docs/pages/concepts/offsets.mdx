An offset is a position inside a stream. Clients use offsets to read from a specific point or resume where they left off.

## Format

Offsets are opaque tokens. Ursula returns them as 20-character strings, for example `"00000000000000000042"`, but their content carries no meaning for clients. Take each offset from a server response and pass it back unchanged. To tell which of two offsets of the same stream comes first, compare them lexicographically. Don't parse offsets or compute new ones from them.

Two special values are accepted on read requests:

- `offset=-1`: start from the very beginning of retained data (the earliest still-available offset).
- `offset=now`: start from the stream's current tail. Useful for "only new data" subscriptions.

## Response headers

After every read or append, the server returns two related headers:

- **`Stream-Next-Offset`**: always present. The offset to pass back on the next request.
- **`Stream-Cursor`**: set on live (long-poll, SSE) responses. A counter for caches, not a position: echo it as `?cursor=` on the next live request. Each response's cursor is past the one the request sent, so successive long-poll URLs differ and a cache can't serve the same empty response in a loop.

Resume from `Stream-Next-Offset` (in SSE, the latest control event's `streamNextOffset`) in every read mode. `Stream-Cursor` carries no stream identity, so it doesn't reveal that a stream was recreated; see [Recreated streams](#recreated-streams).

## Stability across snapshots

Offsets are stable across snapshot publishes. Publishing a snapshot at an offset doesn't renumber later offsets or delete earlier data. A separate retention advance trims the data before its offset. A read at a trimmed offset returns `410 Gone`, and its `Stream-Next-Offset` header is the earliest offset still readable, which `HEAD` also reports as `Stream-Retained-Offset`.

## Recreated streams

An offset doesn't identify which stream it came from. If a stream is deleted and recreated at the same URL, an offset saved from the old stream may be accepted by the new one and return the new stream's data. `HEAD` returns a `Stream-Incarnation` token that changes when a stream is deleted and recreated. A client that keeps offsets across a possible recreate should store the incarnation with them and compare it for equality before resuming.
