## 0.6.1

A patch release on format epoch 2: no storage, snapshot or Raft protocol change. Upgrade from 0.6.0 with an ordinary rolling restart.

### Fixed

- **A memory-WAL voter restarted empty no longer passes readiness.** On restart it rejoins as a voter with an empty log for the groups it bootstraps, and an idle leader never backfills it. `ursulactl` counted such a voter ready whenever the peers' commit index was within `--lag-tolerance`, so `repair-restarted-voter` skipped those groups and a rollout continued with two real copies. A voter that has applied nothing while its peers have committed entries is now never ready, and `repair-restarted-voter` rebuilds it through the learner catch-up path; `classify-amnesiac` counts such groups as missing for amnesiac recovery, so an empty voter outside `--lag-tolerance` is now recoverable instead of refused.
- **The leadership balancer hands a group only to a caught-up peer.** It used to hand leadership to a voter that had not replicated the leader's log; the transfer then left the leader muted while the target could not win, and the next restart fence timed out with "leader … is stale". The balancer now waits until the leader's replication metrics show the target matched its last log entry.
- **The restart fence waits out an in-flight leadership transfer.** The restart fence (`prepare-restart`, `prepare-amnesiac-restart`, `repair-restarted-voter`) now waits 1.5 s (the Raft minimum election timeout) after fencing the surviving voters before it checks leadership, so a transfer accepted just before the fence settles first.

## 0.6.0

**0.6.0 is a breaking release.** It changes the storage format (format epoch 2) and removes several protocol features (listed in the release notes). It refuses to start on data written by 0.5.x (Raft WAL directories, object-storage prefixes, snapshots and backups) and will not join a cluster with 0.5.x nodes. There is no in-place upgrade, no automatic migration and no rollback.

- **If you run 0.5.x with data you need to keep, do not upgrade yet.** Stay on 0.5.1 and [open an issue](https://github.com/tonbo-io/ursula/issues) so we can work out a migration path with you.
- **New deployments install on fresh storage:** empty PVCs and a never-used object-storage prefix.
- **`helm upgrade` from 0.5.x stops at the first pod.** Recover with `helm rollback`.

This release changes the storage format to epoch 2, removes the protocol features listed under [Removed](#removed), stores JSON messages exactly as written, and stops per-stream replicated memory from growing with message count or cold history, without retention (see [Memory without retention](/docs/operations#memory-without-retention)).

### Installing 0.6.0

See [Upgrading to 0.6](/docs/operations#upgrading-to-06).

1. **Install fresh.** Install with a new `s3.prefix` and empty PVCs (with cold storage off and S3 snapshots, also a new `snapshotStore.prefix`). With the event-time indexer, use a new or emptied `indexer.s3.prefix` and register the indexes again ([Event-time indexer](#event-time-indexer-experimental)).
2. **Never reuse a prefix** that an earlier release, or a failed upgrade attempt, wrote to.
3. **`helm upgrade` from 0.5.x stops at the first pod.** The new pod exits at startup or reports not ready (`/__ursula/ready` answers `503` with `format_epoch_mismatch`), so no second voter is replaced and the refused pod writes nothing. Recover with `helm rollback`.
4. **SQLite VFS.** Stop every owner of a stream before upgrading the extension, then delete `<db>`, `<db>-wal` and `<db>-ursula` or attach under a new stream URL ([SQLite VFS](#sqlite-vfs)).

### Always on

Every group runs one behaviour from its first command; there are no feature levels to raise. Always on: bounded producer receipts (1,024 receipt items per stream plus each producer's newest; older duplicates are answered `204` without ranges), 7-day idle-producer expiry, the 4,096-producer cap, unique incarnations, external locators committed before indexing, the compact hot window (no per-message bookkeeping), and cold-tier snapshot bodies up to 1 GiB.

### Observable changes for JSON streams

Every `application/json` stream now follows [JSON message text](/docs/specs/extensions#json-message-text): Ursula validates the body and stores each message as the writer's text with insignificant whitespace removed, followed by one LF. Compared with earlier releases, which re-serialized every message:

| Input | Before | Now |
| --- | --- | --- |
| `{"b":1,"a":2}` | `{"a":2,"b":1}` (members sorted) | `{"b":1,"a":2}` (writer's order) |
| `{"a":1,"a":2}` | one `a` kept | both members kept |
| `1.50e3` | `1500.0` | `1.50e3` |
| `1e400` | `400 Bad Request` | stored as written |
| `"\ud800"` (unpaired surrogate escape) | `400 Bad Request` | stored as written |
| `[{"a":[…127 levels…]}]` | depth counted including the outer array | depth counted per message: a message inside an array body may be as deep as a bare one (127) |

- Every read surface returns the stored text: NDJSON reads, SSE and bootstrap parts.
- Offsets, ETags and byte counts refer to the stored text, so a message's size can differ from what the previous release would have stored for the same input.
- Clients that parse records must accept unpaired surrogate escapes and numbers outside the double range. Ursula's event-time indexer does.

### New

- **`Stream-Incarnation` as a request precondition.** Every request that addresses a stream may carry `Stream-Incarnation`; the server compares it with the stream's incarnation atomically with the request (a write when it is applied) and answers `412 Precondition Failed` (a refused write applies nothing) when the stream was deleted and recreated, including by TTL expiry and a later create. A `PUT` with it for a missing stream answers `412` and creates nothing; a `404`, `410` or `416` stays as it is; a long-poll or SSE read with it ends when its stream is recreated. Without the header nothing changes. A read refused by the precondition returns no data but, like any request that reaches a stream, may still renew the sliding TTL of the stream now at that path. Every successful stream response except a `DELETE` now carries `Stream-Incarnation`, not only `HEAD`. The SQLite VFS sends it on every request after attach, so an owner of a deleted stream can no longer reach the stream recreated at its path, and the event-time indexer sends it on reads. See [Stream incarnation](/docs/specs/extensions#24-snapshot-metadata-on-head-and-stream-incarnation).
- **Metrics.** `/__ursula/metrics` adds `group_state_gauges` (per-group state sizes).
- **External payload locators.** External appends commit their locator in replicated state first and the leader indexes it afterwards, so `runtime.external_payload_min_size` may be lowered.
- **Compact hot window.** Replicated state keeps nothing per message, and cold admission and flush thresholds charge hot payload only.
- **Snapshot bodies in the cold tier.** With a cold backend, snapshot bodies of at least `runtime.external_payload_min_size` are streamed into the cold tier instead of replicated state, and bodies of up to 1 GiB are accepted (32 MiB inline). Snapshot reads and `/bootstrap` stream them back and send `Content-Length`. Superseded bodies are deleted five minutes after the publish that replaced them.

### Changed

- **Bootstrap is an honest partial.** `/bootstrap` never reads cold storage and never skips a byte. When updates after the snapshot are already cold, it returns the snapshot part alone with `Stream-Next-Offset` at the snapshot point and no `Stream-Up-To-Date`; when updates exceed 8 MiB, a JSON stream stops at the last message boundary within the cap and any other stream answers the snapshot part alone. Clients continue from `Stream-Next-Offset` with ordinary reads, as the specification already required. On a JSON stream each update part holds exactly one message, split on LF, so a JSON array append now appears as one part per element.
- **Producer receipts are bounded.** Each stream keeps exact receipts for 1,024 items plus each producer's newest one. An older duplicate is still deduplicated, but answered `204` without range headers. A producer idle on a stream for 7 days is forgotten and must restart at sequence `0` or bump its epoch. See [Exactly-once writes](/docs/concepts/exactly-once-writes).
- **`Producer-Id` and `Stream-Seq` are capped at 256 bytes** on every write path, with `400` above it.
- **Unique incarnations.** A stream's `created_at_ms` strictly increases within a Raft group, so a stream deleted and recreated at the same path is always a distinguishable incarnation, and stream GC only removes the deleted incarnation's objects.
- **Snapshots** are written in a compact MessagePack envelope that earlier releases cannot read.
- **Producer cap.** A stream holds at most 4,096 producers; a new producer evicts producers idle for at least an hour, and when none is, the write answers `429` with a body starting `producer_limit`.
- **Reads are capped at 8 MiB.** A larger `max_bytes` is clamped. A capped offset read may end inside a message, on a JSON stream too: an offset read without `max_bytes`, or with `max_bytes` above 8 MiB, no longer ends at a message boundary. Continue from `Stream-Next-Offset`.
- **Binary bootstrap returns one part.** On a stream that is not `application/json`, `/bootstrap` returns the hot updates after the snapshot as one part, which may contain several messages; a part boundary is not a message boundary. When those updates exceed 8 MiB, or an external append among them is not hot, the response is the snapshot part alone.
- **Non-JSON snapshot and retention offsets need no message alignment.** Any offset between the retained offset and the tail is accepted; an offset inside a message used to answer `400` or `204` depending on whether it had been flushed.
- **JSON snapshot and retention offsets must follow an LF, and the check fails closed.** On an `application/json` stream, `PUT …/snapshot/{offset}` and `PUT …/retention/{offset}` answer `400` for an offset inside a message, whether its bytes are hot or already flushed (an offset below the flushed point used to be accepted), and `503` when the server cannot read the byte before the offset to check it (it used to skip the check). Retention is exact: it no longer lands below its target. Snapshot publishes and retention advances no longer cost a linearizable `HEAD` on every stream; a flushed JSON boundary costs one leader read.
- **Hot tails are flushed after `storage.cold.flush_max_hot_age`** (default 5 minutes, `0` disables), even when the group is below its flush threshold.
- **Defaults.** `storage.cold.compaction_enabled` now defaults to `true`, and `storage.snapshot.backend` defaults to `auto` (S3 when the cold backend is S3, inline otherwise). Raft snapshots are taken by log bytes against a node-wide `raft.snapshot_log_budget` (default 1 GiB) with a `raft.snapshot_backstop_logs` entry backstop.
- **Format epoch 2.** The Raft WAL directory and the object-storage prefix carry a format-epoch marker, every snapshot starts with a format-epoch frame, snapshot pointers are MessagePack only, the WAL journal header, the Raft gRPC protocol (now also on forwarded reads and writes), S3 snapshot references and backups are version 2, and `ursulactl` checks the target cluster's backup format before the first import. A node checks its WAL directory, its object-storage prefix and its peers before it writes anything, and `/__ursula/ready` answers `503` with `format_epoch_mismatch` after any later Raft protocol mismatch.
- **Reserved bucket IDs.** `snapshots` (the default raft-snapshot namespace in the object store) and IDs starting with `__` answer `400`.
- **`PUT /{bucket}` validates the bucket ID.** It answers `400` for an ID that does not match `[a-z0-9_-]{4,64}` and `201` otherwise, and still changes no state: buckets are implicit namespaces. See [Buckets](/docs/concepts/buckets).
- **Helm chart defaults.** The chart now renders `coldStorage.compaction.enabled: true` and `snapshotStore.backend: auto` (previously `false` and `inline`), so a release with cold storage gets compaction and S3 snapshots unless its values set the old ones.
- **TTL renewal is monotonic.** A read or write never moves a stream's expiry earlier. Before, a request stamped by a node whose clock lagged the node that last renewed the stream could shorten the stream's life by that lag.
- **`consistency=leader` reads are linearizable.** Before it answers a `consistency=leader` read, `HEAD`, `/bootstrap`, a snapshot read or a long-poll/SSE registration, the leader confirms with a majority of voters that it still leads (Raft ReadIndex) and waits until it has applied everything committed up to that point. Each such request costs one round trip to the voters, shared by concurrent requests to the same Raft group. On the leader, the confirmation runs before the request reaches the group, so appends and other reads to that group do not queue behind it. `offset=now` without `consistency=leader` takes no confirmation and may resolve to a lagging tail right after a leader change. A long-poll or SSE read takes its `offset=now` position, existence, content type and incarnation from its registration, and its first read is served only by the leader that registered it. A long-poll also answers `416` at registration for an offset beyond the tail (an SSE session reports it as an `error` event from its first read), ends when the stream it registered against is recreated even without `Stream-Incarnation`, and on timeout answers `204` at the requested offset. A leader cut off from the majority, or one that cannot confirm in time, answers `503` with `Retry-After` instead of serving state that may miss appends a newer leader acknowledged. Before, a deposed leader could serve these reads stale, and a follower dropped `consistency=leader` when it forwarded the read.
- **SQLite VFS: opaque offsets.** `ursula_attach`, `ursula_status`, `ursula_stats` and `@tonbo-io/sqlite-ursula` (`attach`, `status`, `drainStats`) return stream offsets as the server's strings (`"-1"` for none) instead of numbers; compare them as strings. The extension never computes an offset: it verifies its claim by reading from the tail it caught up to, and every commit carries a `Stream-Seq`, so a foreign append with a higher one fences the owner. The sidecar (`<db>-ursula`, format 2) and the snapshot body (`USS2`) changed: the first attach after the upgrade rebuilds the local file, and a stream whose latest snapshot is an older body (`USS1`) cannot be attached: attach under a new stream URL (deleting the local files is not enough).
- **Bucket purge is admin-plane only.** `DELETE /__ursula/purge/{bucket}` is served only on the admin listener (`server.admin_listen`, loopback by default); the client listener answers `404`. A Raft group whose leader is unknown or changing answers `503` with `Retry-After` instead of redirecting (`307`) to a peer's client URL; purge is idempotent, so retry it. `/__ursula/usage` stays on both listeners. See [bucket purge](/docs/operations#tenant-offboarding-bucket-purge).

### SQLite VFS

- **Trusted network only.** The extension speaks plain HTTP to Ursula, with no TLS and no credentials. Run it, and the Ursula or `ursulagw` endpoint it talks to, on a network you trust.
- **The local file is a cache.** A commit is durable once Ursula acknowledges it; the extension no longer fsyncs the WAL or the sidecar on every commit. After every reboot (a new kernel boot id), and whenever the local files cannot be verified, attach rebuilds the database from its latest snapshot plus the tail since it. In the 0.6 benchmarks a fresh host took 16 to 27 s to attach a 1 GB database, so a fleet-wide rolling reboot is a burst of snapshot reads, and a stream whose snapshots cannot be published replays from the last one it has. See the [SQLite VFS design](https://github.com/tonbo-io/ursula/blob/main/docs/architecture/sqlite-vfs.md).
- **Owners are bound to a stream incarnation.** The extension's `Producer-Id` is `sqlite-ursula-vfs/<Stream-Incarnation>` and every request after attach carries `Stream-Incarnation`, so an owner of a deleted stream is fenced instead of writing into the stream recreated at its path. Versions with the old `Producer-Id` and this one do not fence each other: stop every owner of a stream before upgrading (or downgrading) the extension.

### Event-time indexer (experimental)

- **API break.** Query and status return `(offset, len)` locators with opaque `next` and `through` tokens instead of record ordinals. The 0.5.1 query parameters `after_captured_at_ms`, `after_record` and `through_record` answer `400`, and unknown registration fields answer `422`. Registration takes `extract` (JSON pointers, with fallbacks and units) and `start`; the legacy `timestamp_field` is still accepted. Re-register every index under a new or emptied `indexer.s3.prefix`.
- **NDJSON sources** (`application/x-ndjson`) are indexed, and nested or unit-ful timestamps (OTLP JSON) are supported. Messages without a usable event time are skipped and counted instead of blocking the index.
- **Chart values.** `indexer.workers.segmentBytes` replaces `readBatchRecords` and `segmentRecords`.
- **Polling cost.** Every indexer pod sends a `HEAD` (always confirmed by a ReadIndex) for every registration on every poll (`indexer.ingest.pollIntervalMs`, default 250 ms), and each one costs the stream's leader a ReadIndex round trip to its voters, even when the stream is idle. Keep registrations few, or raise the poll interval.

### Removed

- **Feature levels.** `/__ursula/feature-level` has no route any more (the admin listener answers `404`), the `409` with `feature_not_enabled` is gone, the per-group `feature_level` gauge is gone from `/__ursula/metrics`, and `ursulactl cluster feature-level` and `cluster enable-feature` are gone.
- **Keyed streams and `clients/pi-durable-ursula`.** `profile=keyed-batch-v1` is an inert media-type parameter, `{stream}/keyed-state` answers `404`, and `[keyed_state]`, `server.keyed_state_upstream` and the indexer's keyed mode are gone. Pi Durable runs on `clients/sqlite-vfs` and `clients/sqlite-ursula`.
- **Data-plane bucket quotas.** `PUT /__ursula/quota/{bucket}` is gone from both listeners, and creates and appends no longer answer `429` for a bucket's stream count or retained bytes. The per-group limits were a backstop worth `limit x group_count` cluster-wide. Nothing in Ursula replaces them: the gateway's `--quota-policy` limits request rate, live reads and body size only ([Security](/docs/security)). Cap a tenant's streams or bytes in your own control plane, using `/__ursula/usage`. The `429` with a `producer_limit` body is unchanged.
- **Bucket lifecycle rules in the extensions specification.** Explicit bucket creation, bucket metadata, stream listing and bucket delete (Sections 1.2 to 1.5) were never implemented and are withdrawn; see [Buckets](/docs/specs/extensions#1-buckets). Removing a bucket stays an operator action ([bucket purge](/docs/operations#tenant-offboarding-bucket-purge)), which permanently fences the bucket ID: later stream creates in it answer `404`.
- **Stream attributes.** `GET` and `PUT /{bucket}/{stream}/attrs` are gone, a `Stream-Attrs` header on create is ignored, and create idempotency no longer compares attributes. Keep application metadata about a stream in your own store.
- **Snapshot delete, the latest-snapshot redirect and `Stream-Snapshot-Match`.** `DELETE /{bucket}/{stream}/snapshot/{offset}`, which never succeeded, and `GET /{bucket}/{stream}/snapshot`, which redirected (`307`) to the latest snapshot, now answer `405` from a node (an access-controlled `ursulagw` answers `404` for the `DELETE`, as for any unrecognized route). To read the latest snapshot, take `Stream-Snapshot-Offset` from `HEAD` and `GET /{bucket}/{stream}/snapshot/{offset}`. A snapshot publish carrying `Stream-Snapshot-Match` answers `400` rather than publishing unconditionally.
- **Append Batch and `Prefer: return=minimal`.** `POST /{bucket}/{stream}/append-batch` and its affinity form are gone, and `Prefer: return=minimal` is ignored. To send several messages in one request to a JSON stream, `POST` a JSON array: it is committed atomically under one producer sequence. `/__ursula/metrics` no longer reports the 18 `raft_write_many_*` series.
- **Path affinity and `$transaction`.** Three-segment stream paths (`/{bucket}/{affinity}/{stream}` and their subresources), `POST /{bucket}/{affinity}/$transaction`, the admin route `/__ursula/flush-cold/{bucket}/{affinity}/{stream}` and the `path-affinity-v1` and `group-append-transaction-v1` extension tokens are gone; such paths answer `404`. Streams created under the three-segment form are not carried over. Address every stream as `/{bucket}/{stream}`; there is no atomic append across streams, but a JSON array `POST` is atomic within one stream. A stream ID may no longer start with `$` (`400`); that prefix is reserved for future bucket-level subresources. `$transaction`, `append-batch`, `attrs`, `bootstrap`, `retention` and `snapshot` stay reserved as stream subresource names.
- **JSON record coordinates.** Record ordinals and everything built on them are gone: the read parameters `record=` (including `record=now`), `tail_records`, `max_records` and `record_view` (with the `application/vnd.durable-stream-records+ndjson` envelope and its SSE form) now answer `400` on catch-up, long-poll and SSE reads; `Stream-Record-Match` on an append answers `400`; the `Stream-Record-First`, `Stream-Record-Start` and `Stream-Record-Next` headers, the record fields of SSE control events and the `Stream-Extensions` header are no longer sent; `PUT …/snapshot?record=` and `PUT …/retention?record=` are gone (`405` and `404` from a node; an access-controlled `ursulagw` answers `404` for both); and `record_coordinate_corruptions` and the record gauges (`record_marks`, `dense_record_entries`, `hot_records`, `hot_real_bytes`) left `/__ursula/metrics`. Resume from the opaque offsets in `Stream-Next-Offset` and SSE `streamNextOffset`; append conditionally with `Stream-Seq` ([conditional writes](/docs/concepts/conditional-writes)). JSON messages are still validated, stored one per line, and counted in usage `committed_records`.
- **Compatibility-only configuration keys.** `raft.snapshot_pressure_unpurged_logs` (chart value `raft.snapshotPressureUnpurgedLogs`) and `storage.snapshot.drive_flush_concurrency` had no effect and are gone. A config file that still sets either now fails at startup; the Helm chart ignores `raft.snapshotPressureUnpurgedLogs` if a values file still sets it.
- **Bucket purge's legacy-pack pass.** Purge no longer rewrites slices of packs written before buckets were erasure domains, and its response no longer carries `legacy_shared_chunks_pending`: every pack of this release lives under its bucket's prefix.
- **`Stream-Integrity-*` headers.** `HEAD` no longer returns the seven undocumented `Stream-Integrity-*` headers. They exposed a per-stream setsum tally that snapshots carried forward without recomputing it from stored bytes, so it could not detect cold-tier or read-path corruption, and it cost a SHA3-256 pass over every inline-appended byte on every replica. `HEAD` still returns `Stream-Cold-Hot-Start-Offset`.

### Fixed

- `/bootstrap` silently dropped bytes after a checkpoint that retention had not followed.
- The `/bootstrap` multipart boundary was a hash of the response's shape, so a writer could predict it and forge part breaks inside an update. Each response now uses a fresh 128-bit random boundary.
- After a stream with small hot bytes received an append of 1 MiB or more and then flushed, the large append could become unreadable and snapshots holding the stream could not be restored.
- Cold-index pages could keep entries of rejected large appends and later serve wrong bytes; existing pages are clipped and repaired.
- Stream GC after a delete and recreate could delete objects of the new incarnation.
- Staged external payloads were deleted after ambiguous failures, even when the append might have committed.
- Several node-local structures grew without bound: the cold-index page cache's LRU, cold-read readahead readers, per-stream append counts and the TTL index.

### Documentation

- **Read path and `HEAD` are specified.** The [Read path](/docs/specs/extensions#9-read-path) section of the extensions specification now defines `consistency=leader`, the 8 MiB read cap with `max_bytes`, JSON stream reads and binary SSE, next to `timeout_ms`. [Snapshot metadata on `HEAD`](/docs/specs/extensions#24-snapshot-metadata-on-head-and-stream-incarnation) adds `Stream-Retained-Offset` and requires `Stream-Snapshot-Offset` and `Stream-Snapshot-Digest` whenever a snapshot exists. [`HEAD`](/docs/api/head-stream) also lists `Stream-Cold-Hot-Start-Offset`, as a diagnostic header that may change in any release. The `HEAD`, read, bootstrap and snapshot-read pages list the `307` and `503` answers of leader-confirmed requests.
- **`Stream-Seq` is documented as the compare-and-set it is.** [Conditional writes](/docs/concepts/conditional-writes) describes the per-stream, bytewise check, the prefix-count pattern for several writers, and publishing committed facts with producer headers. Ursula adds no `If-Match` tail precondition.
- **Corrected statements.** A creating `PUT` stores `Stream-Seq` without checking it. `POST` never creates a stream. `?cursor=` is an echo of `Stream-Cursor`, not an alternative to `offset`, and `?stream-cursor=` is not an alias for it. A catch-up read at the tail answers `200` with an empty body, not `204`. SSE sends no heartbeat comments. A stale `Producer-Epoch` answers `403`, not `409`. `offset=-1` answers `410` once retention has trimmed the start of the stream. The 122-byte stream-ID limit is enforced. `Stream-Up-To-Date` is only ever sent as `true`; a read response without it is partial.
