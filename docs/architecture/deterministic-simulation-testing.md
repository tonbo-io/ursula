# Deterministic Simulation Testing

## 1. Purpose and scope

Deterministic simulation testing (DST) runs Ursula's Raft, runtime, stream state machine, cold store and in-process HTTP surface inside [madsim](https://github.com/madsim-rs/madsim), where time, task scheduling, the Raft network, the disk and the cold store are all driven by one `u64` seed. A failing seed replays the same schedule, so a bug found by a sweep becomes a checked-in regression. Unit tests cover single components on real Tokio. End-to-end tests (`crates/ursula/tests/static_cluster_cli.rs`) cover real processes, gRPC and TCP. Chaos runs cover real hosts, real S3 and long-running operational drift. DST covers the interleavings those layers reach only by chance: message ordering against timers, crash and power-loss points, retry races and storage faults at exact steps.

## 2. Test layers

**Property tests.** `crates/ursula-stream/src/state_machine/tests.rs` runs [proptest](https://github.com/proptest-rs/proptest) over generated command sequences against `StreamStateMachine::apply`. Properties cover offset monotonicity and snapshot round trips, producer retry idempotence and stale-epoch fencing, TTL expiry under generated `now_ms`, cold flush planning and restore, and stale cold flushes after delete and recreate. These run in the normal unit-test job.

**Raft unit tests under madsim.** Pull-request CI's Rust test job runs `cargo test --workspace --lib --bins` natively, which includes `ursula-raft`'s unit tests, and DST Nightly runs `RUSTFLAGS="--cfg madsim" cargo test -p ursula-raft --lib`, every test that compiles under `cfg(madsim)`, without a name filter. A pull request only checks that `ursula-raft` and `ursula-sim` build under `cfg(madsim)` (section 10).

| Fixture | Native coverage | Simulation coverage |
| --- | --- | --- |
| Journal storage contract | OpenRaft storage suite on a real temporary WAL: reopen, truncate, purge, vote and commit persistence | The same OpenRaft storage suite on `SimDisk`. `ursula-sim` disk/recovery tests exercise page loss, reordered writes, fsync failure and gated restart |
| Replication and linearizable reads | Real Tokio Raft actors, sockets and thread-per-core ownership | Raft unit strict append/read replay and partition/heal. Smoke corpus `snapshot_catch_up`, leader-failover and leader-read-linearizability families |
| Runtime-owned Raft and cold tier | Native factory, cold-index cache, compaction and object reference integration | Hosted runtime/Raft network, cold flush/restart and cold-write-failure smoke families |
| Snapshot publication and host concurrency | Native cancellation, install permits, OS threads and real filesystem metadata | Snapshot codec, state-machine install, prefetch and copy, holds and metadata publication failure contracts run on SimDisk. OS-thread concurrency stays native |
| Batch hot-capacity reservation | Native factory and append batch | The same unapplied-entry capacity assertions on a SimDisk-backed engine |
| Control state and wire formats | Pure state machines, log stores and codec tests | The same pure tests and in-memory OpenRaft meta actor startup |

A fixture that opens `tempfile`/`std::fs`, real sockets or OS threads is marked `cfg(not(madsim))` together with its private helpers. Starting a Tokio runtime does not simulate those dependencies. Simulator fixtures explicitly enter `MadsimOpenRaftRuntime::scope` and provision `SimDisk` paths. Do not gate pure tests with an entire mixed module, or remove native assertions to make the simulated suite pass. The ignored strict-replay diagnostic subprobes stay opt-in. The full strict append/read replay runs by default.

**Multi-node simulator.** `crates/ursula-sim` runs simulated nodes in one process, three in most families and two to five in `placement-move`, against seeded fault schedules, checks named invariants and records replayable artifacts. Sections 4 to 8 describe it.

Directed failpoints (`fail_point!`) are not used. Every fault is injected through the simulator seams, and the `layer2` audit keeps the count at zero.

## 3. Determinism mechanisms

- **`cfg(madsim)`.** Every simulation build sets `RUSTFLAGS="--cfg madsim"`. Simulation-only code and the simulated disk compile only under it, and code that touches OS threads, sockets or real files is gated `cfg(not(madsim))`.
- **`rt` shim.** `crates/ursula-runtime/src/rt.rs` and `crates/ursula-raft/src/rt.rs` re-export `spawn`, `sync`, `time` (and in `ursula-raft` also `select` and `task`) from Tokio in normal builds and from `madsim-tokio` under `cfg(madsim)`. Project code goes through the shim so virtual time and scheduling reach every call site.
- **HostedTokio only.** `RuntimeThreading::ThreadPerCore` does not exist under `cfg(madsim)`, and `RuntimeConfig::new` defaults to `HostedTokio` there (`RuntimeThreading` in `crates/ursula-runtime/src/runtime.rs`). Core workers spawn as madsim tasks.
- **OpenRaft runtime.** `MadsimOpenRaftRuntime` (`crates/ursula-raft/src/sim_runtime.rs`) is OpenRaft's `DeterministicRng` wrapper over a madsim-backed `AsyncRuntime`. The harness runs every workload inside `MadsimOpenRaftRuntime::scope(seed, ...)` so OpenRaft's randomness, including election timeouts, derives from the seed.
- **Watch channel.** Tokio's `sync::watch` parks receivers on one of eight `Notify`s chosen by tokio's thread-local RNG, which a process-wide counter seeds, so the wake order of several receivers would depend on what ran earlier in the process. Under `cfg(madsim)` the `ursula-raft` `rt` shim's `sync::watch` is `sim_watch` (`crates/ursula-raft/src/sim_watch.rs`), a channel with Tokio's API that parks every receiver on one `Notify` and wakes them in the order they started waiting. OpenRaft's `MadsimWatch` (`sim_runtime.rs`) wraps it.
- **Biased Tokio `select!`.** A Tokio `select!` without `biased;` starts at a branch drawn from the same process-seeded RNG. Every sim-reachable one is `biased;`, so its branch order is fixed in the source.
- **`select!` patch.** The workspace patches `futures-macro` with `third_party/futures-macro` (`Cargo.toml` `[patch.crates-io]`). Under `cfg(madsim)` the `select!` and `stream_select!` branch shuffle draws from a hash of madsim's simulated clock and a per-call-site counter instead of futures-util's thread-local RNG (`third_party/futures-macro/src/shuffle.rs`). The `sim-patches` audit checks that `Cargo.lock` builds the vendored copy at the same version as `futures-util`.
- **A thread per run.** A run must not depend on what ran before it in the process. madsim runs a simulation on the calling OS thread and does not reset its thread-locals, and lazily seeded ones draw from madsim's intercepted `getrandom`, so from the run's own random stream, only on their first use on a thread: `rand`'s thread RNG and std's `RandomState` keys. A later run on the same thread skips those draws, every later draw of madsim's RNG shifts, and the run schedules otherwise (#638). In the schedule corpus the draw comes from `generate_cluster_id` (`crates/ursula-raft/src/log_store/topology.rs`), which a journal-backed node calls with `rand::random` when it starts without a cluster id. `ursula_raft::run_isolated` (`crates/ursula-raft/src/sim_runtime.rs`) therefore starts each madsim runtime on a fresh thread, and `run_with_madsim` (`madsim_harness/mod.rs`), the one entry point of every scenario and of the `smoke` sweep, `replay` and `minimize`, hands the run's output, recorded trace and panic back to the caller through it. The `ursula-raft` madsim tests use it too. A fresh thread does not reset process-wide state, so none may reach the schedule: the nonce in cold object names comes from a generator seeded with the run's seed under `cfg(madsim)` (`crates/ursula-runtime/src/cold_store.rs`), which never draws from madsim's own generator and starts its sequence again with each runtime, and Tokio's process-seeded RNG decides nothing (see the two entries above). `thread_isolation_tests.rs` runs each schedule-corpus seed twice on one thread, sweeps the corpus seeds in sequence against each seed alone, and checks that the hash keys follow the seed.
- **Strict replay.** `madsim::runtime::Runtime::check_determinism` runs a workload twice with one seed and fails at the first diverging draw of madsim's RNG. `strict_replay_tests.rs` applies it to a three-node cluster on the per-core journal: no fault, follower restart, leader failover, and segment rotation with purge and disk reads. Outcome-level replays cannot see such divergence.
- **Nondeterminism audit.** The `nondeterminism` audit scans sim-reachable source for `SystemTime::now`, `std::time::Instant`, Tokio runtime builders, `std::thread::spawn`, `std::thread::sleep`, `tokio::sync::watch` and Tokio `select!` without `biased;`. Every finding must match an entry in `scripts/dst/nondeterminism_whitelist.json` with a reason, and stale entries fail the audit. It also fails when any crate builds a madsim runtime outside `run_isolated`.

## 4. Harness architecture

```
seed (u64)
  |
  v
SimSchedule::generate / generate_*        scenario + SimFaultPlan
  |                                         steps: [SimFaultStep { phase, action: SimFaultAction }]
  v
ThreeNodeRaftSim::run_schedule            fresh OS thread, madsim Runtime::with_seed_and_config(seed), 30 s virtual limit
  |                                         MadsimOpenRaftRuntime::scope(seed, workload)
  v
+--------------------------------------------------------------------------+
| node 1 .. n                                                              |
|   Raft group engine or ShardRuntime (HostedTokio)                        |
|   journal  SimNodeWal -> per-core journal -> JournalDisk = SimDisk       |
|   network  InProcessRaftNetworkFactory + Policy + FaultScript            |
|   cold     ColdStore::memory + fault policy + delay fn                   |
|   http     router_with_http_state + injected WallClock                   |
+--------------------------------------------------------------------------+
  |
  v
SimTrace (SimEvent stream) -> invariant helpers -> SimReport { scenario, outcome }
```

`crates/ursula-sim/src/madsim_harness/` module map:

- `mod.rs`: `SimScenario`, `SimSchedule::generate`, seed range constants, `SimReport`, regression record types and the madsim runner.
- `generators.rs`: `SimSchedule::generate_*`, one per seed family.
- `faults_inner.rs`: `SimFaultPlan`, `SimFaultStep`, `SimFaultAction` and the seeded workload plans (`RuntimeInterleavingPlan`, `RuntimeRaftNetworkWorkloadPlan`, `HttpProtocolSurfacePlan`).
- `dispatch.rs`: routes a schedule to its scenario runner and wraps the result in a `SimReport`.
- `introspect.rs`: fault-plan predicates and trace helpers shared by dispatch and the minimizer.
- `raft_scenarios.rs`, `runtime_scenarios.rs`, `cold_path.rs`, `http.rs`, `leader_reads.rs`, `write_keys.rs`, `history.rs`, `accepted_loss.rs`, `routing.rs`, `immutable_reads.rs`, `immutable_reads_loss.rs`, `membership_rollback.rs`, `deleted_data.rs`, `engine_restart.rs`, `snapshot_objects.rs`, `cold_upload_fence.rs`, `placement_move.rs`, `identity_fence.rs`, `stream_usage.rs`: scenario runners.
- `usage_meter.rs`: the metering consumer of the per-stream usage export that `stream_usage.rs` runs, by the export's contract (operations, "Per-stream usage").
- `journal_cluster.rs`: `JournalCluster`, journal-backed nodes on the simulated disk with the production recovery gate and the recovery tool's plan. `meta_cluster.rs`: `MetaCluster`, the production meta runtime on each of those nodes over its meta journal. `placed_hosting.rs`: the production hosting driver on each node of a placed `MetaCluster`. `placed_moves.rs`: the moves, cancels, retargets and held reconcile steps the `placement-move` family drives.
- `meta_checks.rs`, `snapshot_checks.rs`: the invariant checks the meta and placement scenarios and the snapshot ownership scenarios share.
- `runtime_network.rs`: `MadsimRuntimeRaftNetworkFactory`, the runtime's three-node OpenRaft group over the in-process network, and its front-door registry.
- `trace.rs`: `SimTrace` and `SimEvent`, the stable observation surface.
- `sim_wal.rs`, `recovery_wiring.rs`: the production journal and recovery gate wired onto simulated nodes.
- `disk_tests.rs`, `recovery_tests.rs`, `recovery_regression_tests.rs`, `poison_marker_tests.rs`, `foreign_entry_tests.rs`, `rolling_restart.rs`, `strict_replay_tests.rs`, `thread_isolation_tests.rs`, `cold_object_names_tests.rs`, `snapshot_store_harness.rs`, `tests.rs`: `#[test]` scenarios outside the seed-family CLI.

A schedule is pure data. `SimSchedule::generate(seed)` routes a few fixed seeds and seed ranges to dedicated scenarios and maps the remaining seeds onto Raft and cold-path scenarios by `seed % 12`. The `generate_*` functions build one family each. Seeded workload plans use `SplitMix64` so a seed fixes the plan before the run starts, and the plan is stored in the schedule.

Simulation seams:

- **Raft network.** `crates/ursula-raft/src/in_process.rs` (compiled for `cfg(any(test, madsim))`) implements OpenRaft's `RaftNetworkFactory`/`RaftNetworkV2` over `InProcessRaftRegistry`. `InProcessRaftNetworkPolicy` applies a virtual-time delay and directional partitions, and records each decision as an `InProcessRaftNetworkEvent`. `InProcessRaftFaultScript` applies `InProcessRaftFaultAction` (`SetDelay`, `PartitionBidirectional`, `HealBidirectional`, `Clear`) at named workload phases. Production uses `GrpcRaftNetworkFactory` in `grpc.rs`.
- **Disk.** The per-core journal performs every file operation through `JournalDisk` (`crates/ursula-raft/src/log_store/disk.rs`). Under `cfg(madsim)` it is `SimDisk` (`log_store/sim_disk.rs`), a path-keyed in-memory disk scoped to one madsim runtime that keeps the page cache apart from synced pages and directory entries. `SimDisk` also stands in for the host boot id, so a power loss starts a new boot. Under `cfg(madsim)` the journal rotates segments at 4 KiB and caches 1 KiB of entries per group (`JournalTuning::DEFAULT_SEGMENT_BYTES` and `DEFAULT_GROUP_CACHE_BYTES` in `log_store/writer.rs`), so scenarios rotate segments and read evicted entries from disk. No scenario uses an in-memory Raft log store.
- **Cold store.** `ColdStore::memory()` builds an OpenDAL memory operator through the private `ColdStore::from_operator`. `set_fault_policy` returns a `ColdStoreFaultEffect` (delay, error or `truncate_read_to`) per operation, and `set_delay_fn` routes delays through `madsim::time::sleep`. Observers emit `ColdStoreEvent`s into the raw event log.
- **Wall clock.** `ursula::WallClock` (`crates/ursula/src/lib.rs`) supplies protocol-visible `now_ms`. HTTP scenarios build the router with `HttpState::with_wall_clock` and advance a simulated clock for TTL and expiry.
- **Runtime.** Sim-only methods `shutdown_group_engine_for_simulation` and `install_group_engine_for_simulation` let a hosted `ShardRuntime` swap its group engine after an OpenRaft leader change.
- **Leadership view.** `MadsimRuntimeRaftNetworkFactory` registers the replica the runtime hosts in a `RaftGroupHandleRegistry` through the madsim-only `register_engine_for_simulation`, the first leader when it builds the group and each successor the runtime takes, and removes it with `unregister_group`, which a node that stops hosting a group also calls, when a scenario kills the leader. The HTTP scenarios that use `write_keys::Cluster` build `HttpState` over that registry, so the front door routes writes before their body through the production lock-free leadership view (`RaftGroupHandleRegistry::leadership`).
- **Group formation.** Every simulated replica starts behind its recovery gate, with the production recovery drivers. The static families start it over a `FixedPlacement` whose initializer is node 1, as the placed engine factory starts one (`recovery_wiring::start_gated_replica`, which `JournalCluster` mirrors). The `placement-move` family starts it over its node's `MetaPlacement`, through the production hosting driver (`placed_hosting::SimHost`), with the initializer that the kernel's seed rule names. The initializer initializes a fresh group once every voter reported it empty, and no scenario initializes a group by hand. Only `ursula-raft`'s unit tests, which run no recovery driver, initialize a group themselves.

## 6. Fault vocabulary

`SimFaultAction` (`madsim_harness/faults_inner.rs`) is the schedulable fault and workload step set. Each `SimFaultStep` binds an action to a named phase of the scenario.

- **Network:** `PartitionSeededFollower`, `HealSeededFollower`.
- **Node:** `StopSeededFollower`, `RestartStoppedFollower`, `StopCurrentLeader`, `RestartStoppedLeader`.
- **Raft snapshot and membership:** `CreateLeaderSnapshot`, `PurgeLeaderLog`, `AddLaggingLearner { node_id }`, `CorruptRuntimeRaftSnapshotAppendCounts`.
- **Cold store:** `WriteColdChunk`, `PublishColdFlush`, `FailNextColdRead`, `FailNextColdWrite`, `FailNextColdDelete`, `RetryColdWriteAfterFailure`, `RetryColdReadAfterFailure`, `DelayNextColdWrite { delay_ms }`, `DelayNextColdRead { delay_ms }`, `TruncateNextColdRead { returned_len }`, `VerifyHotReadAfterColdWriteFailure`, `CorruptColdLiveReadExpectation { node_id }`.
- **Runtime:** `StartRuntimeWaitRead`, `DelayRuntimeAppend`, `StartRuntimeConcurrentClients`, `DelayRuntimeClientAppends`, `RunRuntimeColdFlushAllGroups`, `VerifyRuntimeColdLiveReads`.
- **Seeded workloads:** `RunRuntimeSeededInterleaving { plan }`, `RunRuntimeRaftNetworkWorkload { plan }`, `RunHttpProtocolSurfaceWorkload { plan }`. Their plans carry the seeded branches and the `corrupt_*_expectation` flags.
- **HTTP expectation corruption:** `CorruptHttpProducerDuplicateExpectation`, `CorruptHttpLiveSseNextOffsetExpectation`, `CorruptHttpLiveLimitBackpressureExpectation`, `CorruptHttpSnapshotBodyExpectation`.

Disk faults live in `SimDisk` (`crates/ursula-raft/src/log_store/sim_disk.rs`) and are driven directly by the disk and recovery tests:

- `SimDisk::inject_fault(path, SimDiskFault)` fails the next matching operation: `Write`, `PartialWrite` (half the bytes, then an error), `Sync`, `Remove` or `Rename`. A failed `fsync` marks pages clean without persisting them, as Linux does.
- `SimDisk::power_loss(prefix)` keeps or drops each unsynced 4 KiB page with madsim's RNG, which can leave zero-filled holes, and reverts directory entries not made durable by a directory `fsync`. `power_loss_losing_unsynced` drops every unsynced page.
- `SimDisk::write_back(prefix)` makes every page under the prefix durable, as a host's page cache writes pages back on its own. A scenario whose power loss must keep what it wrote before its fault calls it before the fault instead of relying on a segment rotation to `fsync` those pages.
- `SimDisk::move_volume(prefix, name)` moves a volume away from the process on it and attaches it on the same host as another device, under a new root that holds what was durable. The old process keeps its page cache: its writes through files it opened land there, and its syncs and directory changes fail.
- `SimDisk::process_crash(prefix)` keeps the page cache. `RaftGroupFileLogStore::pause_simulated_writer` and `abort_simulated_writer` hold or discard queued journal writes.

### Snapshot store faults

The S3 snapshot store does not exist under madsim. `ursula_runtime::snapshot_harness` stands in for it in simulations and in unit tests of snapshot object ownership (#687). It compiles under `cfg(madsim)`, under `cfg(test)` and with the `test-support` feature, and never in a production build.

`MemorySnapshotBucket` is one bucket that every node of a test shares: a map behind a mutex. `bucket.store(node_id)` is a node's `MemorySnapshotStore` on it, which implements the whole `SnapshotStore` trait, owned-key methods included. A simulation gives it to a node's engines as their snapshot store, as `JournalCluster` does below. The store keeps no reference records, and its GC is the owner's pass over `list_own` and `delete_own` that the server runs (#687). Each request waits a drawn delay before it acts on the map and another after it, before it answers, so the requests of several nodes interleave in simulated time. `SnapshotStoreFaults` sets the faults per test, and `SnapshotStoreFaults::from_seed` draws the PUT fault rates per seed:

- **Late PUT:** the PUT answers an error and the object lands a drawn delay after the PUT acted, so it may land before the client sees the error, as a write whose answer was lost. A late PUT checks If-None-Match again when it lands and writes nothing if an object has the name by then.
- **Lost PUT:** the PUT answers an error and nothing lands.
- **Collided retry (opt in):** `with_collided_retries` makes a PUT create its object and answer `NameCollision`. The S3 store does this when its resilience layer times out a create that landed and retries it: the retry finds its own object.
- **Stale LIST:** among the `stale_window` most recent creates and deletes that are younger than `stale_for`, the LIST leaves out each created key and lists each deleted key again, with even odds. The bucket keeps a fixed history whatever the faults, so stale LISTs turned on later have recent changes to misreport. Once `stale_for` passed, a quiet bucket lists every key. `from_seed` leaves stale LISTs off, for liveness checks, and `with_stale_lists` turns them on. A check of the #669 bound then allows the bound plus `stale_for`.
- **Conditional create:** a write whose name exists answers `NameCollision` and changes nothing.
- **Opt-in failures:** `with_failed_requests` adds DELETEs that fail, DELETEs that delete and answer an error, and transient LIST, GET and HEAD errors.
- **Nonces:** each node draws the nonces of its object names from a sequence seeded by the bucket's seed, a constant and the node id. The sequence lives in the bucket, so a restarted node does not draw its earlier names again. `with_nonces` replaces it, as on the S3 store, for example to force a collision.
- **I2 assertion:** a DELETE of a key outside the deleting node's own directory panics in the deleting task, with one admitted exception: the removed-node sweep's DELETE (`delete_node_object`) of a key of another node that its listing (`list_node_group`) returned. The bucket logs that DELETE as `DeleteKind::Swept` with the node it names, and I2 admits it only for a key of that node, never for one of the deleting node's own. A bucket built with `recording_foreign_deletes` records the attempt instead, for a negative control, and panics when dropped unless `foreign_deletes` took the recorded attempts.

Every fault, delay and nonce comes from the bucket's own seeded generator, never from a thread or process RNG. One seed and one order of requests therefore log the same requests, which `snapshot_store_harness` under `madsim_harness::tests` checks by running each seed twice. Reading the bucket (`view`, `keys`, `pending_late_puts`) changes nothing in it, so a checker can run at any step without changing the replay. A recording bucket's foreign deletes are read only through `foreign_deletes`. `events` returns the bucket's request log, and `view` returns what the checkers read, with each object's age since it landed. A late PUT enters the stale-LIST history at its landing time.

Quiescence, which I5 needs, comes from `wait_for_late_puts`: it advances simulated time until every pending late PUT landed. `settle` lands them at once instead, which pulls future landings forward and hides the second GC pass a node runs one install timeout after a failed write, so a simulation does not use it. For quiescence to model the protocol, `late_put_delay.max` must stay at or below that second-pass delay.

`GatedSnapshotStore` wraps a node's store and gives each owned-key operation (stage, `write_staged`, `list_own`, `delete_own`, `list_node_groups`, GET and HEAD) and each operation of the removed-node sweep (`list_node_group` and `delete_node_object`) of that node a gate before it reaches the store and one after the store answered. A held gate keeps the operations that arrive and releases them one at a time in arrival order. A waiter whose future is dropped, by a timeout, a shutdown or a killed node, gives up its turn, and the log records it as abandoned. Releasing a gate that is not held is an error. Tests use the gates to force one order of a build's lease, PUT and commit against a GC pass's LIST, read of the holds and DELETE. The gate after `list_own` and the one before `delete_own` are the seams of a pass. The wrapper builds the wrapped store's future before the first gate, so a store that works outside its future would do that work before the gate.

`JournalCluster` gives its nodes this store when a scenario calls `set_snapshot_store` before it starts the cluster, along with the snapshot drivers. All nodes share one bucket. Each node process gets its own `GatedSnapshotStore` with fresh gates, which its engines and its registry use, and a node that stops or is wiped gets a new one when it starts again, while the work of its stopped engines keeps the old one. The nodes run with an install timeout of one second (`raft.install_snapshot_timeout`), so a write that failed and a restore owe their second GC pass one second later, and `late_put_delay.max` stays at 80 ms, well inside it. The cluster reads what each node names from its snapshot records on the simulated disk, a stopped node's included, with `persisted_snapshot_pointer`, which decodes a record as a restore does. The in-process network brackets each full snapshot it delivers with `FullSnapshotStarted` and `FullSnapshotEnded`, the second sent before the sender's hold on the object drops, and the cluster opens a send window in the bucket for each. A GET of the sent object by the receiver that finds nothing inside a window is logged as `SentObjectMissing`. The opt-in DELETE, LIST, GET and HEAD failures stay off in these scenarios: a failed pass backs off 30 s, past a run's 30 s of virtual time, and `JournalCluster` builds its engines without the runtime's open path, so a restore that fails is not retried. The runtime's back-off after a transient restore error is covered only by the unit tests of #746.

`madsim_harness/snapshot_checks.rs` holds the checks the scenarios share. `step` runs after every action and every 25 ms of a wait: I1 over every node's records, I2 over every DELETE, and I3 over the GETs the bucket logged since the last step, where a GET of a node's own object is a restore, the only reader of its own objects, and `SentObjectMissing` is a read inside a send. `bound` checks I4. `quiesce` is the only route to I5: it turns the faults off, waits until every replica applied its leader's last index with no build in flight, waits for every late PUT, then waits an install timeout and three driver intervals, checks I1 and I2, then I5, and puts the faults back.

The madsim cases in `snapshot_store_harness` exercise the store, the gates and the checkers with a toy owner's pass. The server's ownership protocol runs on the same store and gates in `ursula-raft`'s `snapshot_ownership_tests`, outside madsim, and on journal-backed clusters in the `snapshot-objects-stay-owned` and `engine-restart-leaves-no-work` scenarios. The madsim cases of `snapshot_store_harness` are:

- The three-node case runs each node's build and pass one after the other, so a node never races itself, and every node deletes through its own store, so I2 cannot fail. I5 is checked right after a fault-free pass.
- The gated case runs a build against a pass on one node in one order the gates force. Its seeds change only the delays and explore no other order.
- The concurrent case runs a build and a pass on one node with no gates, so the seed picks the order, and I1 must hold on every seed.

The negative controls (a lease taken after the PUT, gated and concurrent) switch the toy pass of the test, not production code. The concurrent control breaks I1 on a pinned seed.

The checkers take a `SnapshotStoreView` and what each node names, which the caller reads from the node's state through `NodeSnapshotNames`. They assume no protocol:

- **I1** `check_named_keys_exist`: every key a node's metadata names exists.
- **I2** `check_no_foreign_delete`: no DELETE targets a key outside the deleting node's directory.
- **I3** `check_committed_reads_found`: no restore, no committed install and no read inside a send's RPC read `NotFound`.
- **I4** `check_superseded_without_marker`: past the bound, no object that no node names holds the marker. That covers orphans, such as a late PUT's object or an abandoned build's, aged from their landing, as well as replaced objects, aged from the later of their landing and their supersession.
- **I5** `check_quiet_prefixes`: once quiet, each node's directory holds only the keys its metadata names.

## 8. Corpus, replay and minimization

The corpus lives in `crates/ursula-sim/corpus/`. `smoke_corpus_replays` (`madsim_harness/tests.rs`) replays all three files.

- `smoke.json`: 5 `SimRegressionRecord`s (scenario, seed, stream, outcome with trace) for the base Raft and cold scenarios.
- `schedule-smoke.json`: 30 `SimScheduledRecord`s. Replay asserts that each stored schedule still equals `SimSchedule::generate(seed)` and that the outcome matches.
- `failure-smoke.json`: 18 minimized `SimFailureRegressionRecord`s. Each replays as an expected panic and asserts its invariant, with an exact panic string or stable `panic_contains` substrings when the message names seed-dependent objects.

On failure, `smoke` writes three files per seed to `--failure-dir`: `seed-N-failure.json` (seed and schedule), `seed-N-stable-trace.json` (the comparison surface, with nondeterministic raw cold-store events filtered and metric counters reduced to presence bits) and `seed-N-raw-events.json` (every event, including per-RPC network decisions and cold-store operations). The command refuses a seed listed under two generators (`--seed-range` and a family, or two families of different generators), so each run's files are named by its seed alone and no run overwrites another's. A failing seed does not stop the sweep: the seeds after it still run, each failure writes its files and prints them, and at the end the command fails listing every failed seed. With `--expect-failures` the command fails only if no seed failed. `--shard INDEX/COUNT` runs every COUNT-th seed of the sorted, deduplicated list from INDEX on, so the COUNT shares of one command run each of its seeds once. It does not combine with `--expect-failures`.

`ursula-sim` subcommands (all require `--cfg madsim`):

- `record <seed> [output]` writes a `SimScheduledRecord`.
- `replay --seed N | --artifact PATH` reruns a schedule. `--expect-invariant`, `--expect-panic-contains` and `--expect-artifact-panic` turn an intentional panic into a pass.
- `minimize --artifact PATH` shrinks a schedule while a target holds: `--invariant`, `--panic-contains`, `--event` with `--event-min-count`, `--stable-prefix` or `--stable-exact`. The report embeds `minimized.record` for a passing target or `minimized.failure` (schedule, panic, stable trace, raw event log) for a reproduced panic.
- `assert-shape --artifact PATH --steps-exact A,B,...` checks the minimized fault steps by `SimFaultAction` variant, so a rename is a compile error.

Shrink operations:

- remove a fault step, or an orphan heal or retry, and add a missing heal to test whether the invariant still needs the partition
- remove runtime interleaving clients and remap the corrupt-read target, zero timing delays, lower the flush group limit
- remove or lower cold read and write delays, truncation lengths and corrupt-read node ids
- drop runtime/Raft workload branches (cold/live verification, restart during flush, leader failover, partial and tail reads, close, snapshot, producer sub-features) and `corrupt_*_expectation` flags
- shrink append and failover payload counts to one and collapse multi-stream workloads to one stream
- drop HTTP plan branches and move or drop `panic_after` targets

## 9. Audits and tools

`python3 -m scripts.dst <cmd>`. `all` runs every entry in `AUDITS` (`scripts/dst/audits.py`).

- `nondeterminism`: sim-reachable code has no wall clock, real `Instant`, Tokio runtime builder, OS thread call, Tokio `watch` or unbiased Tokio `select!` without a whitelist entry, and no crate builds a madsim runtime outside `run_isolated` (`--report`, `--json`, `--update-baseline`).
- `pipeline-smoke`: every corpus record carrying a `corrupt_*_expectation` field falls in a `pipeline-smoke-*` seed range.
- `layer2`: no `fail_point!` macro exists under `crates/`.
- `ci-shape`: no workflow asserts multi-element fault-step lists with strict-equality `jq`. Use `assert-shape` instead. The nightly workflow also runs every test in `madsim_harness/` named `*_replays` that is not `#[ignore]`d, through some `cargo nextest run -p ursula-sim` filter. Every `--shard` takes its share from its leg's matrix index, and every `DST_SHARD:` in the workflow is that index, with no shell assignment overriding it. The `report` job runs `if: always()`, needs every other job, and has an `Every DST job passed` step, with no `if:` or `continue-on-error:`, that fails unless each succeeded.
- `modularity`: `madsim_harness/mod.rs` stays within `LINE_BUDGET = 2_500` lines.
- `seed-inventory`: the nightly workflow runs the expected families and ranges, every family exists in `SEED_FAMILIES`, and the seed total stays within budget.
- `failure-guards`: every `failure-smoke.json` record has a nightly minimize command, an embedded-trace assertion and a minimized-artifact replay.
- `sim-patches`: each vendored crate under `third_party/` is the version `Cargo.lock` builds.
- `defences`: every `Defence` variant of `ursula_stream::sim_controls` is named in production code outside `ursula-sim`, and a simulation turns it off with `set_off`, so no negative control switches a defence that does nothing.
- `seed-report`: writes the nightly seed inventory to `target/ursula-sim-seed-inventory/`.
- `result-summary`: summarizes `seed-*-failure.json` artifacts under `target/` into `target/ursula-sim-result-summary/`.
- `coverage-report`: counts distinct stable trace events across a sweep into `target/dst-coverage-report.{json,md}`.
- `throughput`: times `ursula-sim smoke` per seed and suggests a nightly seed count.

## 10. CI

Deterministic simulation runs only in `.github/workflows/dst-nightly.yml`, daily at 03:17 UTC and on dispatch. Pull requests run no simulation: the `rust-lint` job of `ci.yml` runs the `scripts.dst` audits, and the `madsim-check` job of the same workflow checks that `ursula-raft` and `ursula-sim` build under `cfg(madsim)` with every target. A regression in simulated behaviour therefore shows up in the next nightly run. The cron runs only on the default branch, so dispatch DST Nightly on the release HEAD before releasing. The Stable Release workflow refuses a commit without a successful DST Nightly run unless its dispatch waives that gate with a reason (`dst_waiver`), which the run summary and the GitHub Release body record. A failed scheduled run opens or comments on the issue titled "DST Nightly failing on main", naming each failed or cancelled step with its job, or a job's result when none of its steps failed.

A run is a set of jobs that start together. The simulation jobs run on RunsOn runners (`family=m7a+m8a`), and each stops after 30 minutes.

- `audits` runs `python3 -m scripts.dst all` with the nondeterminism and seed reports and uploads both.
- `sweep` runs the smoke sweep of `--seed-range 60..=199` and `--seed-range 503..=504` with every family marked nightly above that does not expect failures, among them `runtime-raft-network-randomized-extended` and the `-extended` variants. Its seven legs each run one share of that one command (`--shard "$DST_SHARD"`, from the leg's index in its matrix): every seventh seed of the sorted, deduplicated list, so each seed runs once and each family of seven or more seeds spreads over every share. A failing seed does not stop the leg, so a failing night reports every failed seed of every share.
- `negative-controls` runs every negative control and every either-defence check (`negative_control either_defence`). A negative control switches off the defences one bug needs gone and asserts its scenario fails the invariant they keep. Where two defences each stop the bug alone, an either-defence check runs with each one off and asserts the remaining one fires.
- `recovery-gate` runs `recovery_tests` and the poison-marker tests.
- `replays` runs the scenario replays (filter `_replays`). Each scenario test named `*_replays` runs its scenario twice per fixed seed and asserts the same report, and the thread-isolation checks run under the same filter.
- `scenarios` runs the `ursula-raft` unit tests under madsim, a two-seed `ursula-sim smoke` with an injected panic on the first seed that checks the second still runs and the command fails listing the first, `smoke_corpus_replays`, the unit tests of `ursula-sim smoke` (`smoke::tests`) and the minimization, `assert-shape` check and replay of corpus seeds 146, 147 and 155, the bounded-state tests at their default seeds and then over wider ranges, the cold upload fence scenario (`cold_uploads_stay_fenced_under_leader_churn`) over a wider range, the journal segment tests, `snapshot_metadata_`, the deleted-data scenarios (`scrub_`), the snapshot store harness (`snapshot_store_harness`) and `strict_replay`.
- `expected-failures` runs every expected-failure family. For each it minimizes a checked-in seed, checks the minimized steps with `assert-shape` or `jq`, asserts the embedded trace carries the `invariant_failed` event, and replays the minimized artifact with `--expect-invariant`.
- `report` runs after the others, also when one failed. It fails unless every other job succeeded, so a successful run means every job ran and passed. It merges the jobs' `target/ursula-sim-*` outputs, writes and uploads the result summary and coverage report, uploads the failure artifacts when the run failed, and files the issue for a scheduled run. Each simulation job uploads its `target/ursula-sim-*` outputs as a `dst-part-*` artifact on every run. GitHub keeps it for 7 days, and anyone who can see the run can download it.

Simulation tests run under cargo-nextest, pinned by version and SHA-256 in `.github/actions/cargo-nextest`. It runs each test in its own process, so the tests of one job run side by side. In one process they would run one at a time: every scenario test holds `sim_test_guard`, because madsim keeps process-global state. Environment variables widen the test seed ranges (`SNAPSHOT_STORE_HARNESS_SEEDS`, `RECOVERY_GATE_SEEDS`, `POISON_MARKER_SEEDS`, `EXTERNAL_LOCATOR_AMBIGUITY_SEEDS`, `EXTERNAL_LOCATOR_SNAPSHOT_SEEDS`, `AMBIGUOUS_COMPACTION_SEEDS`, `COLD_UPLOAD_FENCE_SEEDS`).

The `seed-inventory` audit caps the seeds the nightly names at `NIGHTLY_SEED_BUDGET = 1500`. The cap bounds the sweep's cost, and the number of `sweep` legs bounds its wall clock. When the legs near their timeout, add legs. Each seed runs once whatever their count, so the count decides only each share's mix and run time. A count that shares a factor with a modulus a generator picks a script with (each `seed % N` under `crates/ursula-sim/src`: 2, 3, 4, 7, 8, 9, 11, 12 and 17 today) gives each share only some of that choice's scripts. Seven does this for the `seed % 7` choices, so all of one such script's seeds run in one share. Prefer 13 when adding legs.

## 11. Out of scope

- tonic wire encoding and production gRPC (`GrpcRaftNetworkFactory`), covered by end-to-end tests
- real TCP and multi-process routing
- `ThreadPerCore` threading, CPU affinity and OS-thread concurrency, covered by native tests and benchmarks
- real S3 semantics such as consistency, throttling and multipart behavior, covered by the S3 integration tests in CI
- network message reordering and duplication: the in-process network delays and partitions but never reorders or duplicates RPCs
